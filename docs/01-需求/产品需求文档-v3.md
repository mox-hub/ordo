# PRD V3：Agent 时代的工程治理平台

> 本文档是 Agent Project Manager 的需求真相源（V3）。
> **V3 取代 V2 作为需求真相源**；[[产品需求文档-v2|V2]] 保留为历史归档，其模块文档体系（13 个 Feature 模块 v2.1.0）仍有效，V3 在其之上叠加新范式。

## 1. 文档定位与版本

### 1.1 V3 相对 V2 的范式转变

V2.1.0 建立了完整的 13 模块体系，核心定位是「AI 原生的项目管理平台」，原子单位是 **Task（任务）**。这套基础仍然有效，是 APM 的底盘。

V3 在此基础上发生一次**范式转移**：

| 维度 | V2（任务中心）| V3（验收导向）|
|------|--------------|--------------|
| 原子单位 | Task（工作单元）| **Acceptance（验收契约）** |
| 衡量对象 | 人的劳动产出 | 资源→结果的转化效率 |
| 核心指标 | velocity / cycle time | 验收首次通过率 / 单位验收成本 |
| 产品定位 | AI 原生项目管理平台 | **Agent 时代的工程治理平台** |
| 与 Linear 的关系 | 对标竞争 | **共生（数据源）** |
| 稀缺资源假设 | 人力 | token + 代码质量 + 验收信用 |

### 1.2 为什么不修改 V2 而新建 V3

范式转移触及产品定位、核心对象、指标体系的根。在 V2 原地改会留下「任务中心」与「验收导向」两套逻辑并存的混乱。V3 作为独立真相源，清晰地以新范式为脊柱重组，V2 保留供追溯。

### 1.3 V2 资产的继承关系

V3 不废弃 V2 的成果：
- **13 模块体系**（Core/Project/Task/Team/AI Hub/Git/Notification/Runtime/Auth/Plugin/Integration/Execution/Document）全部继承
- **双表面架构**（Human Surface / Agent Surface）继承并扩展
- **执行治理三件套**（ExecutionRun/ApprovalRequest/审计）继承
- **ContextPack 四层策展**继承并注入验收标准

V3 新增的是：**Acceptance 作为新原子单位** + **工程治理的四个面** + **生态共生策略**。

## 2. 产品愿景与价值主张

### 2.1 一句话愿景

> **让任何团队——哪怕没有资深项目经理——都能交付工程上靠谱的 AI 辅助软件。**

### 2.2 核心痛点（正在发生的损失，不是潜在的好处）

引入 AI 编码后，成熟开发团队面临四个「正在流血」的痛点：

| 痛点 | 表现 | 谁在痛 |
|------|------|--------|
| **成本黑箱** | 每月烧 $5000-30000 AI 编码费，无法回答「花在哪、值不值」| EM、CFO |
| **质量静默劣化** | Agent 倾向打补丁不重构，技术债加速积累，半年后才暴露 | Tech Lead、架构师 |
| **验收定义不完整** | 新手 PM 写的验收标准漏了日志/监控/依赖，即使 100% 通过也交付失败项目 | PM、全团队 |
| **团队活动黑箱** | 五个开发者各自跑 agent，互相不知对方改了什么 | PM、EM |

> 关键判据：这四个痛点都满足「**不装就在亏钱/担风险**」的标准，不是「有了更好」的锦上添花。

### 2.3 范式转移：从 Task 到 Acceptance

Linear 的原子单位是 Task（工作单元），整套数据模型围绕「人在做什么工作」构建——velocity、cycle time、assignee。这些指标的共同前提：**劳动是稀缺资源**。

但 agent 时代，劳动不再稀缺（token 才是）。这时候衡量「人做了多少工作」越来越失真——velocity 还在涨，没人知道这些任务质量如何、花了多少 token、是不是下次还得重做。

> **Agent 时代的 PM 原子单位不该是 Task，而是 Acceptance——一个交付物通过验收的事件。**
>
> 成本、质量、风险全部从 Acceptance 自然派生，而不是外挂字段。

这是 APM 与 Linear 的**结构性分界**：Linear 的 task 模型根上是「人做工作」，它的 acceptance 是人类主观动作（Loop 的 accept/reject）；APM 的 acceptance 是**工程对象**，有标准、有证据、有成本——这是范式差异，不是功能差异。

### 2.4 差异化定位（与四类玩家分别错位）

| 玩家 | 定位 | APM 如何错位 |
|------|------|-------------|
| **Linear / Jira** | 任务管理（人做工作）| APM 不竞争录入体验，做 **Linear 的治理层**（共生：数据从 Linear 来，治理在 APM）|
| **Orca（ADE）** | 本地 agent 编排器（单机并行）| APM 不做 TUI/本地执行体验，做 **团队的治理与上下文层**（Orca 看不到团队，APM 看不到本地体验）|
| **RAG / 知识库** | 模型原生知识存储 | APM 不做 RAG，**消费**知识库作为 Layer 3 数据源 |
| **AI 网关（Bifrost/Cloudflare）** | 成本追踪（看到 cost 看不到 context）| APM 看到的是「**这个 cost 买到了什么验收结果**」——网关只看钱，APM 看钱买到了什么 |

**一句话错位总结**：

> **Linear 是任务来源，Orca 是执行器，RAG 是知识底座，网关看到 cost——APM 是唯一同时掌握「执行全链路 + 团队维度 + 代码维度 + 验收结果」的工程治理层。**

## 3. 竞品定位

### 3.1 与 Linear 的关系：共生而非对抗

Linear 的 PM 录入体验已极致成熟，APM 追三年也追不上，而且**追上了也不是差异化**。

APM 的策略：
- **不竞争录入体验**：用户继续用 Linear 录入任务、定义验收标准
- **做 Linear 的治理层**：同步任务与验收标准到 APM，APM 赋予它们**完整性审计 + 成本归因 + 风险预测**
- **应对 Linear Loop 的吸收风险**：Loop 是「人类接受任务结果」，APM 是「工程验收契约」——两个轴，Loop 不会延伸到工程方法论

### 3.2 与 Orca 的关系：互补而非竞争

Orca 验证了「agent 编排」需求真实存在。但 Orca 是**单机本地工具**，没有团队/治理概念。

APM 吸收 Orca 的两个设计：
- **Worktree 任务级隔离**：每个 ExecutionRun 独立 worktree，多 agent 并行不冲突
- **外部任务同步**：从 Linear/Jira 拉任务

但 APM 不做 Orca 的 TUI 体验——那是 Orca 的主场。

### 3.3 开源定位的结构性优势

开源对 APM 不是「免费」，是**「成为 agent 时代工程治理的事实标准」**。

类比 Prometheus：它难被取代不是因为 UI 最好，而是成了监控的标准数据格式。APM 如果把「验收事件的数据模型 + 成本归因口径 + 工程完备性清单」做成开源标准，让 agent 工具/CI 工具/观测工具按这个标准上报数据，就建立了基础设施级护城河。

**Linear 和 Orca 都不会开源自己的数据模型——这是开源相对闭源的结构性优势，不是价格优势。**

## 4. 目标用户画像

### 4.1 核心用户：经验不足但需要工程治理的团队（V3 新增重点）

- **谁**：引入 AI 编码但缺乏资深项目经理/架构师的小型团队（5-20 人）
- **场景**：让 agent 写代码，但不知道该验收什么、不知道工程标准、看不见 AI 在花什么钱
- **痛点**：验收定义不完整（漏日志/监控/依赖）+ 成本黑箱 + 质量不可见
- **期望**：APM 帮他们定义靠谱的项目，不只是管理项目

> 这类用户是 V3 的**战略重点**——他们是 Linear/Jira 用户中增长最快、最焦虑、最愿意尝试新工具的群体。

### 4.2 高价值用户：成熟团队的管理层（EM/CTO/CFO）

- **谁**：已经在用 AI 编码的成熟团队的管理层
- **场景**：需要向 CFO 回答 AI 花费、向 Tech Lead 保证质量、向 PM 保证交付
- **痛点**：成本黑箱 + 团队活动黑箱 + 质量静默劣化
- **期望**：APM 是团队 AI 的「财务系统 + 质量系统 + 仪表盘」

### 4.3 协作用户：外部 AI 开发工具（Codex / Claude Code）

- **谁**：通过 CLI/MCP 接入的开发型 agent
- **场景**：读取结构化上下文（含验收标准）、执行、提交审批、回写结果
- **期望**：获得 ContextPack（含验收标准事前对齐），高效通过验收

## 5. 产品目标与成功指标

### 5.1 V3 目标层次

1. **第一目标**：让任何团队能定义并验证**工程上完整**的交付（验收完整性审计）
2. **第二目标**：让团队看清 AI 编码的**成本、质量、风险**（工程治理四个面）
3. **第三目标**：成为 Linear/Jira 的**治理共生层**，降低切换门槛

### 5.2 成功指标（量化 KPI，阈值待运营确认）

| 指标 | 衡量维度 | 目标方向 | 对应痛点 |
|------|---------|---------|---------|
| **验收首次通过率** | agent 交付物首次通过验收的比例 | 高 | 质量/定义完整性 |
| **单位验收成本** | 通过一次验收平均花多少 token/钱 | 低 | 成本黑箱 |
| **验收定义完整度** | 完整性审计前后，验收标准覆盖率的提升 | 高 | 定义不完整 |
| **AI 编码 ROI** | (验收通过价值) / (token 成本) | 高 | 成本黑箱 |
| **风险预警提前量** | 交付失败前被预警的时间窗 | 长 | 风险不可见 |
| **Linear 同步覆盖率** | 通过同步获得数据的用户比例 | 高 | 切换门槛 |

> V2 的 KPI（闭环完成率/审批通过率等）降级为基础设施指标，不再是 V3 的核心衡量。

## 6. Acceptance 范式（V3 核心）

> 本章是 V3 的灵魂。V3 所有产品设计都从这里派生。

### 6.1 Acceptance 的本质：可验证的交付契约

传统软件里「验收」是一个**社会事件**——一个有权的人看一眼，点头或摇头。Linear Loop 做的就是这个数字化。

但 agent 时代三个变化同时发生，让验收必须升级：

| 变化 | 对验收的影响 |
|------|------------|
| Agent 产出是结构化的（代码/diff/测试）| 验收从主观判断变成**客观检查** |
| Agent 执行是高频的（一天几十次）| 人类不可能每次都看，**必须自动化大部分验收** |
| Agent 失败是廉价的（重试成本低）| 验收从「一次性裁决」变成**迭代收敛过程** |

> **Acceptance = 一个交付物与其验收标准之间的可验证契约**，有状态机（待验收→通过/放弃）、留下证据、消耗成本、可追溯。

### 6.2 Acceptance 作为流转原子单位

Acceptance 不是 APM 内部私产，它是跨越四个主体的**契约枢纽**：

```
        需求方（PM/客户/Linear）
            ↓ 定义验收标准
        ┌───────────────┐
        │  Acceptance   │ ←── 模型（AI 评估验收是否满足）
        │   （契约）     │ ←── 外部工具（CI/PR 提供验收证据）
        └───────────────┘
            ↓ 触发执行 + 事前对齐
        执行方（人类/agent）
            ↓ 产出交付物
        验收方（人类/自动化/模型三方共审）
            ↓ 裁决
        通过 / 失败 / 有条件通过
```

**关键设计**：APM 不自己做所有验收，它是**验收状态的单一真相源**——CI 在外部跑，结果回流；PR review 在 GitHub 做，结果回流；模型评估在 APM 内跑。不管验收发生在哪，最终都在 APM 看到完整图景。

### 6.3 验收标准分层

验收标准分两层，来源和验收方式不同：

```
Acceptance
├── 功能标准（Functional）
│     ├── 来源：Linear 同步 / 人工定义 / Document（需求文档）
│     ├── 验收：人类判断 / 模型语义评估
│     └── 示例："用户能通过邮箱注册并收到验证邮件"
│
└── 技术标准（Technical）
      ├── 来源：技术栈标准模板 / CI 绑定 / 人工定义
      ├── 验收：自动化（CI/测试/lint）/ 模型评估
      ├── 按技术栈差异化：
      │     Java → JUnit pass / checkstyle / spotbugs
      │     TS → Jest pass / eslint / tsc strict
      │     前端 → 设计图还原度比对 / a11y / Web Vitals
      └── 示例："API 响应 p95 < 200ms / 覆盖率 >= 80%"
```

**技术栈标准模板是 APM 的核心资产**——它是「工程经验编码化」，是护城河（详见第 8 章）。

### 6.4 验收的分形聚合

Acceptance 是**分形**的——每个层级验收逻辑相同，只是粒度不同：

```
项目验收（Project Acceptance）
  ├── 里程碑验收（Milestone Acceptance）
  │     ├── 任务验收（Task Acceptance）
  │     │     ├── 执行验收（Execution Acceptance）  ← 原子层
```

- **自下而上**：执行验收结果聚合为任务/里程碑/项目验收状态（带权重的状态计算）
- **自上而下**：宏观风险向下传播（里程碑标准收紧 → 相关任务阈值提高）

这让 APM 能回答**任何现有工具都回答不了**的问题：
- 「这个项目离能验收还差多远？」
- 「哪个里程碑验收风险最高？」
- 「这次迭代首次验收通过率多少？」

### 6.5 验收完整性审计（L2 风险治理——V3 最核心能力）

> 这是 APM 最独特的能力，也是「不装不行」感受的发生点。

**两类验收定义风险（L2 风险）**：

| 类型 | 问题 | 发现方式 |
|------|------|---------|
| **隐性依赖风险** | 用户要 A，A 依赖 B，但验收标准里没有 B | 项目内部推断（A 引用 B 的接口）|
| **工程完备性风险** | 用户完全不知道自己不知道（日志/监控/错误处理缺失）| 外部工程经验比对（按技术栈）|

**L2 风险 vs L1 风险**：
- L1（执行风险）：交付物没满足验收标准 → APM 的执行治理（V2 已有）
- **L2（定义风险）：验收标准本身不完整 → APM 的完整性审计（V3 新增）**

> Linear/Orca/RAG/网关都不会碰 L2——它们假设「用户知道要验收什么」。APM 是唯一处于「能识别验收定义缺口」位置的工具。

**完整性审计的响应（强制执行 + 可自定义清单）**：

```
用户定义的验收标准（可能不完整）
        ↓
    强制审计（执行前阻断）
    ├── 依赖完备性检查（项目内部推断）
    └── 工程完备性检查（外部经验比对，按技术栈）
        ↓
    完整性报告
    ├── 红色：强阻断（必须补全才能执行）
    ├── 黄色：提议补全（agent 自动建议，人类一键确认）
    └── 绿色：验收标准完备
```

## 7. 工程治理的四个面

> 四个面共享 Acceptance 原子单位，所以数据天然贯通，不是四个孤立 feature。

### 7.1 成本可观测性

回答「这次验收花了多少 token/钱」：

- 现有 `AIUsageLog` 已记录 token/cost（代码地基已存在）
- 补 `executionRunId` 关联，把成本归因到执行
- 执行成本聚合到 Acceptance（一次验收多次执行的成本总和）
- 项目/团队/开发者维度 roll-up

**差异化于网关玩家**：网关只看到 cost，APM 看到「这个 cost 买到了什么验收结果」。

### 7.2 AI 代码质量可观测性

回答「AI 改动是重构还是补丁？复杂度在哪个模块漂移？」：

- Git diff（已有）× 验收结果 → 代码变更质量维度
- 追踪：改动范围合理 vs 散弹枪 / 测试覆盖率升降 / 复杂度漂移

**差异化于 Linear/Orca**：它们不看代码，只看任务/执行。

### 7.3 交付风险预测（钩子能力）

回答「哪些交付正在滑向失败/超支？」：

- 基于执行失败率上升、重试次数多、成本超支的**事前预警**
- APM 拥有完整执行链路 + 代码 diff + 成本数据，是唯一能做这个预测的位置

> 这是最能产生「不装不行」感受的能力——EM 看到「原来还能提前知道哪个交付要崩」的瞬间。

### 7.4 团队 AI 活动透明度

回答「团队这周 AI 一共做了什么？谁的任务卡住？」：

- 作为 Web 平台 + 全员执行记录中心，天然是团队 AI 活动的统一仪表盘
- 这是平台形态红利，Linear（任务维度）和 Orca（单机维度）都吃不到

## 8. 工程完备性清单（核心资产）

### 8.1 定位

工程完备性清单是「成熟开发者工程经验」的**编码化**。它让新手 PM 也能定义出资深架构师级别的验收标准。

### 8.2 清单示例

```
项目类型：后端服务 + 技术栈：Java/Spring
└── 工程完备性清单
    ├── 结构化日志（logback/结构化输出）     ← 验收标准里没有 → 风险
    ├── 错误追踪（Sentry/异常上报）          ← 没有 → 风险
    ├── 健康检查端点（/actuator/health）     ← 没有 → 风险
    ├── 数据库迁移管理（Flyway/Liquibase）   ← 没有 → 风险
    ├── API 文档（OpenAPI/Springdoc）        ← 没有 → 风险
    └── ...

项目类型：前端应用 + 技术栈：React
└── 工程完备性清单
    ├── 错误边界（Error Boundary）
    ├── 原型还原度对比（设计图 vs 实现）
    ├── 性能监控（Web Vitals）
    ├── 可访问性（a11y 基础）
    └── ...
```

### 8.3 清单的三个特征

1. **强制审计**：执行前阻断，保证「不装 APM 就裸奔」的安全性
2. **可自定义**：团队可修改、覆盖预置清单
3. **社区共享**：优秀开发者维护的清单可被全球新手采纳（开源生态核心机制）

### 8.4 清单 schema（方向性，细节留执行阶段）

清单是结构化对象，按维度组织：
- **项目类型维度**：后端服务 / 前端应用 / 移动端 / 库 / ...
- **技术栈维度**：Java/Spring、TS/Node、React、Python、...
- **检查项**：每项有名称、检查方式（自动/人工/模型）、严重级别、验证方法

## 11. 接入策略与生态共生

### 11.1 生态角色分工

```
Linear/Jira ──任务+验收标准──→ APM ──验收标准──→ ContextPack ──→ Agent
                                   ↑                                ↓
                            CI/PR review ──验收证据──→ Acceptance ←──执行结果
                                   ↑
                            工程完备性清单 ──审计──→ 完整性报告
```

| 生态角色 | 职责 | 与 APM 的关系 |
|---------|------|-------------|
| Linear/Jira | 任务录入、功能标准定义 | 数据源（共生）|
| Orca/本地 agent runner | 本地 agent 执行 | 执行器（互补）|
| RAG/知识库 | 模型原生知识 | Layer 3 数据源 |
| AI 网关 | 成本拦截 | 提供 cost 原始数据，APM 归因 |
| CI/CD | 自动化测试/部署 | 提供技术验收证据 |
| **APM** | **验收完整性 + 成本归因 + 风险预测 + 团队治理** | **治理层（唯一位置）**|

### 11.2 接入优先级

长期：`MCP > CLI > API/Plugin`
Phase 1 实施顺序：`CLI → Linear/Jira 同步 → MCP`

## 13. Phase 划分（重写）

### 13.1 Phase 1：Acceptance 基础 + 验收完整性审计（范式验证）

目标：**打穿 Acceptance 范式，2-3 周出第一个 demo**。

- ContextPack 注入验收标准

成功标志：一个新手 PM 定义验收，APM 自动指出「漏了日志、漏了 A 依赖的 B」。

### 13.2 Phase 1.5：共生与获客验证

目标：**降低切换门槛，验证共生策略**。

- 验收中心 UI

- 验收证据汇聚（CI/PR 回流）

成功标志：一个 Linear 用户「不迁移」就能用上 APM 的治理能力。

### 13.3 Phase 2：治理深化

- 交付风险预测
- AI 代码质量可观测性

### 13.4 Phase 3：演进

- 分形聚合（里程碑/项目级验收）

## 14. Phase 1 MVP 与验收标准

### 14.1 MVP 目标

做出可感知的「验收完整性审计」demo——一个新手 PM 定义验收，APM 自动审计并指出缺失。

### 14.2 MVP 必须包含

- Acceptance model + 状态机
- 功能/技术标准分层定义
- 至少 3 套技术栈完备性清单（Java/TS/前端）
- 依赖完备性检查 + 工程完备性检查
- 三级响应（阻断/提议/标注）
- 成本归因（AIUsageLog → ExecutionRun → Acceptance）

### 14.3 MVP 验收标准

1. 能为 Task 创建 Acceptance，定义分层验收标准
2. 完整性审计能识别依赖缺失（A 依赖 B，B 未在验收范围）
3. 完整性审计能识别工程完备性缺失（后端项目缺日志验收）
4. 强阻断项阻止执行，提议项可一键补全
5. 能查看一次 Acceptance 的总成本（token + 钱）

## 23. v3.1 增补记录

### 23.1 AI 同事 = 治理录入手段（2026-09-08 裁决，原「增补预告」正式化）

治理条件的生产从「人写标准 → AI 审计挑错」升级为「**AI 同事代写 → 人确认 → 完整性审计把关**」，主轴（验收导向工程治理）不变。详见 [[能力清单-v1]] §二。

### 23.2 用户前提修订：双入口（2026-09-17 需求重审裁决 2）

用户调研显示**非专业用户占比提升**，成为核心考虑对象（专业程度是**具体任务上的差异，不是用户标签**，不做不可逆的功能裁剪）。原「假设用户已有 Linear/Jira」前提与该事实不兼容，§18 已修订为**双入口、共享同一套验收与证据规则**（独立使用 + 生态接入）。

配套两条已确认基线：**工程化可信度是下一阶段主轴**——系统能否保证做的是对的、能证明做成了、变化之后仍然可信；**AI Native 内生于功能设计**——每项功能设计之初同时回答「工程上如何可信」与「AI 如何让用户有能力完成它」，且「人确认」不得成为责任转移（AI 不得自己生成标准、自己宣称符合、再把自己的结论当独立证据）。重审全账见 [[需求重审-总纲-v1]]。
