# 需求入口流程 v1

> 配套 [[能力清单-v1]] 与 [[测试映射矩阵-v1]]；skill 化实现：`.zcode/skills/requirement-intake/SKILL.md`（入库，团队共享）。
> **解决的历史问题**：2026-08/09 的新想法走「设计纪要 → 直接开发」路径，跳过需求层，导致 PRD 失效、功能无追踪（背景见 [[能力清单-v1]] §一）。

## 一、触发条件

会话中出现以下意图时**必须**走本流程（AI 会话由 skill 自动触发，人类协作者自觉遵守）：

- 新功能想法（"要不要加一个…"/"如果能有…就好了"）
- 既有功能变更（改语义、改交互、改数据形状）
- 功能废弃或降级

## 二、五步流程

| 步 | 动作 | 产出 |
|----|------|------|
| 1 | **一行声明**：把想法压成「价值 + 影响域」一句话 | 声明文本 |
| 2 | **冲突检测**：对照 [[能力清单-v1]] 全量卡——已有什么？改谁的？与四线裁决/分工声明是否冲突？ | 重叠/冲突报告 |
| 3 | **裁决归档**：三选一——立即开工 / 进候补区（[[能力清单-v1]] §六）/ 明确放弃（写一句理由，防复读） | 裁决记录 |
| 4 | **更新清单**：候补区加一行，或新建/修改能力卡（ID 按线段分配，状态置 `planned`） | 清单 diff |
| 5 | **开工登记**（仅"立即开工"）：卡状态置 `doing`；补三段式验收标准 + 测试映射占位（[[测试映射矩阵-v1]] 缺口表加行）；如涉 C 线，先过供血判据（§三）；**新卡必答六问**（见下），老卡复审时补答 | 卡 + GAP 行 |

### 六问评审标准（2026-09-17 需求重审裁决 1 增）

每张新卡开工登记时必须回答，老卡复审时补答（口径详见 [[需求重审-总纲-v1]] §三）：

| 评审项 | 必须回答 |
|--------|---------|
| 用户任务 | 用户最终要完成什么，而不是打开什么页面？ |
| AI 职责 | AI 在哪个环节提供不可替代的帮助？不需要 AI 也可明确说明 |
| 可信依据 | 建议与结论依赖什么事实、规则、版本与证据？ |
| 人类控制 | 哪些事需要人决定？怎样保证人真正理解而非机械确认？ |
| 失败与降级 | AI 错了、不可用、信息不足时，用户怎么继续？ |
| 跨模块闭环 | 输入从哪里来，输出交给谁，变更后如何重新对齐？ |

> 关键约束：**「人确认」不得成为责任转移**——让非专业用户面对二十条技术验收标准点「全部同意」，不等于完成了可信的人审。AI 明确禁止：自己生成标准、自己宣称符合、再把自己的结论当作独立证据。

## 三、C 线供血判据

> 同事线是手段，治理线是目的（主轴裁决，见 [[能力清单-v1]] §二）。

**每张 C 线能力卡必须能回答："它为哪条治理能力供血？"**（格式：`†供血 CAP-B-xx`）

- 答得上来 → 合法，开发。
- 答不上来 → **同事功能自我膨胀**，强制进候补区，不得直接开工。

## 四、硬规则

1. **未进清单的功能不得开工**——本规则取代「设计纪要直通开发」。设计纪要仍可写（架构真相），但纪要开工前必须完成清单登记。
2. 废弃/降级功能**不删卡**：状态置 `gap` + 一句理由，保留追溯。
3. 清单状态词表仅 `planned / doing / done / gap`；变更写入 [[能力清单-v1]] §七变更记录（含触发 commit/PR 号）。

## 五、治理骨架分工（裁决 2026-09-08，新功能不得越界）

- `acceptance` = **验收证据层**，管"交付物符合标准吗"。
- `contract` = **文件绑定层**，管"改的文件是该改的吗"。
- 二者互不吞并；新需求若横跨，经 `runtime.execution.result` 事件联动，不得在任一模块内复制对方职责。

## 六、增量测试惯例（每张新卡的验收含测试义务）

1. 标准验收 = ①正常流 + ≥1 条③异常流 + 涉及的④联动场景。
2. bug 修复必配⑤回归用例（同 PR）。
3. 新控件登记进控件清单（[[测试映射矩阵-v1]] §五模板）。
4. **两类质量（2026-09-17 需求重审裁决 1 增）**：①-⑤按场景分类之外，每张卡的用例须显式回答两类质量——**工程规则是否守住**（不能越权、不能误用旧证据、不能绕过必要门禁、状态守卫口径与数据模型一致）；**AI 是否真的帮上忙**（能否识别信息不足、说明依据、接受纠正并调整，而不是只测「成功生成一段文本」）。

## 七、流程图

```
新想法
  → [1] 一行声明
  → [2] 对照能力清单冲突检测
  → [3] 裁决：立即开工 / 候补 / 放弃（留理由）
  → [4] 更新能力清单（候补行 or 新卡 planned）
  → [5] 开工卡：doing + 验收标准 + 测试映射 + 六问 + （C 线）供血判据
  → 开发 → 完成置 done（附测试用例名）
```
