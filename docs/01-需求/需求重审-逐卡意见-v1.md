## 一、A 底盘线（19 卡）

> 线定位（重审后）：**不变，但停止无边界扩张**——向深度要价值，不向广度要。A 线绝大多数卡判断为「保留」，故本节只对**有实质意见**的卡展开；判断为「保留，无意见」的卡合并为一表。

#### CAP-A-01 认证与访问 ｜判断：保留
- **用户任务**：安全地进入团队，且知道谁能做什么。
- **AI 职责**：低。登录本身不应引入 AI；可延伸的是**权限解释**（「为什么我看不到这个项目」）——归 [[#CAP-C-07]] 覆盖域，本卡不新建入口。
- **可信要求**：JWT/PAT/RuntimeSession 三态边界清晰；审计不可篡改（架构 §8）。
- **冗余/缺口**：无冗余。缺口见 A-02（role 无卡）。
- **建议**：本卡不动。**P2**。

#### CAP-A-02 用户 / 团队 / 成员 ｜判断：保留 + 补边界
- **用户任务**：（非专业用户）知道「这个人/这个 AI 能做什么、能批什么」。
- **AI 职责**：角色分配建议（基于历史执行表现）、权限差异的人话解释。**注意**：不得让 AI 静默授予权限。
- **可信要求**：Member 三态（human / platform_ai_member / external_agent）贯穿全系统；角色定义职责、等级定义放权（PRD §12 原则 2）。
- **冗余/缺口**：**缺口——`role` 模块全仓无能力卡**（40 目录中唯一无卡登记的角色相关模块）。角色的「谁可批卡 / 谁可发版 / 谁可改契约」对治理产品是治理面问题，不是用户管理细节。
- **建议**：**先补边界声明**（role 归 A-02 还是独立小卡），再由用户裁决是否新建卡（[[需求重审-总纲-v1]] §八-4）。**P1**（仅登记，不实现）。

#### CAP-A-03 项目与工作区 ｜判断：保留 + 补缺口
- **用户任务**：项目数据可靠存放、可带走、不会丢。
- **AI 职责**：低。
- **可信要求**：每工作区一库物理隔离（既有）；**数据生命周期可兜底**（缺）。
- **冗余/缺口**：**[已核实] 无备份 / 恢复入口**——`apps/server/src` 无 backup/restore 服务，唯一「初始化」是 `core/database/workspace-registry.util.ts:90-117` 复制 `template.db`（仅**新建**工作区时发生，不是恢复）。
- **建议**：登记「工作区备份与恢复」为 A-03 切片或新卡；与 A-14 桌面升级迁移合并考虑（同一「长期安全使用」命题）。**P1**。

#### CAP-A-04 工单族（Issue）｜判断：深化
- **用户任务**：看懂「要做什么、做完没有、能不能现在开始」。
- **AI 职责**：创建时补全字段、解释类型与字段含义、**在信息不足时提问而不是猜**（现在 grill 仅覆盖 project 类型，见 A-18）。
- **可信要求**：**依赖必须真正约束执行**——**[已核实] 当前依赖仅被组装进上下文提示**（`context-builder.service.ts:265-311`），派发门禁只查验收契约（`dispatch.service.ts:288` `assertDispatchGate`），建依赖无环检测（`issue.service.ts:2076-2170`）。这造成体验落差：用户标了「B 依赖 A」，系统仍允许先执行 B。
- **冗余/缺口**：缺陷降级为类型视角是**正确的收拢**（消一个导航位，不丢能力）——本轮**肯定**此改动。缺口：GAP-T-01 详情页交互矩阵；依赖约束缺失。
- **建议**：依赖约束与 B-03/A-19 的执行前门禁**合并设计**（同一用户流程，不做成两个功能）。**P0**。

#### CAP-A-05 元数据与业务配置 ｜判断：控制扩张
- **用户任务**：（非专业用户）开箱能用，不被配置淹没。
- **AI 职责**：配置项的人话解释、「不确定就用默认」的建议；**不替用户改全局配置**。
- **可信要求**：配置改动的后果可见（改状态定义影响哪些工单）。
- **冗余/缺口**：**投入冗余风险**——类型/字段/状态定义持续丰富，对非专业用户是天书。既有 A-04「类型管理面重设计」是正当需求，但**后续不应继续新增配置面**。
- **建议**：明确「默认可用、配置可选」原则；设置页补 AI 解释入口（复用 C-07）。**P2**。

#### CAP-A-06 文档管理（基础面）｜判断：深化
- **用户任务**：把「我们到底要什么」写下来，且它一直是当前有效的。
- **AI 职责**：代写/更新（analysis-draft 已有）、发现文档之间与文档和执行之间的冲突。
- **可信要求**：文档类型（需求/分析/规范/纪要）与审批状态边界清晰；**正式规范与 AI 推断必须区分**（不得让 AI 起草稿静默成为执行依据）。
- **冗余/缺口**：2026-09-17 frontmatter 属性面板重建（GAP-T-33）为正当增强，**不改判断**。缺口：**文档与执行/验收的关联未成链路**——「哪份文档是本次执行的依据」「它改了要不要重审」无承载。
- **建议**：与 P-01 的「需求修订」链路绑定，作为变更传播的载体之一。**P0**（作为 G1 的一环）。

#### CAP-A-07 动态 / 通知 / 订阅 / 邮件 ｜判断：保留 + 修边界
- **用户任务**：该知道的别漏，不该打扰的别烦。
- **AI 职责**：**通知降噪**（哪些必须打断人、哪些该汇总成简报）——这是非专业用户的关键体验，也是 C-06 简报的天然上游。
- **可信要求**：通知不得静默失败（A-19 正在补）；受众解析去重。
- **冗余/缺口**：**[据清单] 状态不一致**——卡标 `done`，但 A-19 余留明确列「邮件渠道空壳」。建议在卡内补注记澄清边界（done 指站内闭环，邮件外发未实现）。
- **建议**：修正卡内状态说明；「通知降噪 + AI 摘要」作为观察项登记（非本期）。**P2**。

#### CAP-A-08 Git 集成 ｜判断：保留 + 登记远期缺口
- **用户任务**：（开发/独立开发者）看懂改了些什么、有没有风险。
- **AI 职责**：diff 影响分析、变更解释——**这是 PRD §7.2「AI 代码质量可观测性」的落点，全仓无承载**。
- **可信要求**：PR/CI 证据真实（归 B-08）；仓库只读展示与证据回流边界不混（2026-09-13 增强已做对）。
- **冗余/缺口**：PR 列表服务端回源（GAP-T-23）为正当增强。缺口：PRD §7.2（改动范围合理 vs 散弹枪 / 覆盖率升降 / 复杂度漂移）**无能力卡**。
- **建议**：登记为远期能力卡或 A-08 增强行（**非本期**，PRD 中列为 Phase 2）。**P3**。

#### CAP-A-09 外部集成 ｜判断：保留 + PRD 前提修订
- **用户任务**：（专业团队）沿用既有工具，同时获得 APM 治理。
- **AI 职责**：同步冲突解释、来源归属说明。
- **可信要求**：同步数据不得与 APM 原生数据产生双真相。
- **冗余/缺口**：**[据清单+PRD] 前提不兼容**——PRD §18「假设用户已有 Linear/Jira」与「非专业用户为核心对象」冲突。
- **建议**：PRD 前提修订为双入口（[[需求重审-总纲-v1]] §2.4）。**P1**（文档级，须显式裁决）。

#### CAP-A-10 运维管理 ｜判断：保留
- 无实质意见。**P3**。

#### CAP-A-11 workflow 执行引擎基座 ｜判断：保留技术投资，停止产品层扩张
- **用户任务**：（小白视角）**不关心 workflow**——只关心「系统按规矩把事做完了」。
- **AI 职责**：设计期生成/修订模板（已有，工具四件套）。
- **可信要求**：suspend/resume 跨重启不可恢复已**诚实降级**（400 + 「请重新触发」）——本轮**肯定**此诚实处理，优于伪造恢复。AIUsageLog 记账已接。
- **冗余/缺口**：**概念负担**——workflow 是内部机制，不应成为用户必须理解的入口（与 R4 同源）。
- **建议**：产品定位明确为「**内置流程的执行底座**」；不新增产品层概念入口。**P1**（收口，非扩张）。

#### CAP-A-12 工作流节点画布与产品动作节点 ｜判断：收拢（降低优先级）
- **用户任务**：高级用户编排自定义流程——**但这不是完成项目的必经之路**。
- **AI 职责**：代写流程定义（已落，走决策卡）。
- **可信要求**：节点输入输出契约由注册表治理（既有设计正确）。
- **冗余/缺口**：四切片已合并但曾列 GAP-T-14 测试赤字（后由代理批偿）。**投入冗余**——相对主轴，继续扩节点类型/模板库的优先级应低于主流程可靠性。
- **建议**：**完成既有切片收口，不新增扩张**（不扩节点类型、不扩模板库）。资源转向 P0 批次。**P2**。

#### CAP-A-13 底部协同交互面（Dock）｜判断：保留
- **用户任务**：常用入口随手可达。
- **AI 职责**：**Dock 是 AI 同事的常驻入口**，其价值随「AI 能做的事是否可信」上升——不是独立价值来源。
- **可信要求**：退出判定契约（面内不关闭）已明确且实现到位。
- **冗余/缺口**：无冗余。多轮微调（默认收起/头像/状态点）已收口。
- **建议**：**停止交互微调投入**，随 C 线价值提升自然受益。**P2**。

#### CAP-A-14 桌面壳发布级打包与运作 ｜判断：保留 + 补两项缺口
- **用户任务**：（非开发用户）装上就能用，且长期放心用——**不丢数据、升级不炸**。
- **AI 职责**：首启向导的目标解释（已落）；**不替用户决定工作目录**。
- **可信要求**：安装→首启建库→服务健康→登录→主流程（GAP-T-19/20 余留：真干净机冒烟）。
- **冗余/缺口**：**[已核实] 升级迁移路径存疑**——证据 `apps/desktop/src-tauri/src/setup.rs:89-95` 注释自认「升级场景 schema 演进另行走 migrate deploy（v0.6.1 后再议）」，但该文件属 **Tauri 路径**，Electron 当前路径**[待核实]**。另 **[已核实]** 无备份/恢复（见 A-03）。
- **建议**：**先核实 Electron 路径**，再据实登记「升级迁移 + 数据备份」切片（或新卡）。**P1**（核实本身 P0 成本低）。

#### CAP-A-15 控制面导航信息架构 ｜判断：保留 + 深化方向调整
- **用户任务**：**沿导航走 = 沿正确流程走**（对非专业用户是主要引导机制）。
- **AI 职责**：每站给「你现在该做什么、为什么」——**导航即引导**，而非页面枚举。
- **可信要求**：六站语义与管道①-⑥一一对应（已裁决）。
- **冗余/缺口**：管道项目聚焦切片已落（GAP-T-27 清偿）。余留=实机验收。
- **建议**：与 [[#CAP-C-08]] 叙述能力结合，把导航从「页面清单」升级为「当前该做什么」。**P1**。

#### CAP-A-16 里程碑与发布：计划-交付轴整合 ｜判断：保留
- **用户任务**：一眼看到「走到哪、何时交、交了什么」。
- **AI 职责**：进度解释、里程碑风险提示（可复用 C-06）。
- **可信要求**：Iteration=时间盒 / Milestone=计划节点 / Release=交付物 三层语义已裁决（2026-09-13）。
- **冗余/缺口**：主体已落（GAP-T-28 清偿），余留实机验收。
- **建议**：不动，待实机验收定 done。**P2**。

#### CAP-A-17 快捷键体系 ｜判断：保留，停止扩张
- **用户任务**：（专业用户）高频操作键盘可达。
- **AI 职责**：无。
- **可信要求**：注册表单一真相源、冲突检测（已落）。
- **冗余/缺口**：**投入冗余**——纯前端 localStorage 方案已足够，继续收编页面内键位收益递减。
- **建议**：**不扩大收编范围**（页面级上下文键位维持现状）。**P3**。

#### CAP-A-18 统一创建面板双界面 ｜判断：深化（**AI Native 正面样板**）
- **用户任务**：（非专业用户）一句话建实体，不必先学会字段体系。
- **AI 职责**：**AI 代理面板全字段代写 → 人确认落库**——这是「AI 建议 → 人确认 → 可展开细节」的完整实例。
- **可信要求**：确认前可审、可改；Esc 脏表单保护；连续创建不丢上下文。
- **冗余/缺口**：面板级「手动 × AI 代理」顶级平行是**正确的口径扩展**（对 ADR-011）。缺口：该交互范式目前只在本面板成立，**未推广**。
- **建议**：**作为 AI Native 交互样板**，把「AI 建议 → 人确认 → 可展开细节」推广到验收标准、发布说明、角色分配等场景。**P1**。

#### CAP-A-19 执行侧兜底改造（批 5）｜判断：深化（**P0 主战场之一**）
- **用户任务**：执行失败后**知道为什么、知道怎么办**，而不是只看到「失败了」。
- **AI 职责**：**当前缺**——批 1-5 补的是感知（通知/对账）与重试（血缘），**未补诊断**。重试若只是同输入再跑一次，对用户没有增加理解。
- **可信要求**：悬挂对账、取消语义、重试血缘已落；**执行前门禁只查验收契约，未查依赖**（见 G4）。
- **冗余/缺口**：批 5 重试语义升级（新建执行 + 血缘）是**正确方向**——保留失败现场优于原地覆盖。缺口：①失败诊断（为什么失败、建议继续/调整/请人介入）②执行前约束（依赖门禁）③并行隔离（G5）。
- **建议**：**批 6 = 失败诊断 + 执行前约束**，与 B-03 合并设计。**P0**。

## 二、B 治理线（8 卡）—— 本轮主战场

> 线定位（重审后）：**升级为核心**——「工程化可信度」主要由 B 线兑现。

#### CAP-B-01 验收契约 ｜判断：**深化（P0）**
- **用户任务**：（非专业用户）知道自己究竟要验收什么，且**标准变了之后知道要重来**。
- **AI 职责**：代写标准（已落）+ **解释标准含义与后果**（「这条标准在防什么风险」）；**不替用户判定通过**。
- **可信要求**：**[已核实] 标准无版本、无修订标记**——`Acceptance`/`AcceptanceCriteria`/`AcceptanceEvidence` 三表无版本字段（`schema.prisma:1851-1939`）；`acceptance-criteria.service.ts:83-123` 改内容后不重置 `status`/`passedAt`，不标记既有证据失效。→ 用户看到「通过」但无法追溯对应对哪版标准。
- **冗余/缺口**：卡自 2026-09-08 起 `doing`（「骨架在，前端入口薄」）久悬，且**主轴产物已大量落 acceptance**——契约本体反而薄。缺口=版本对应 + 证据充分性规则。
- **建议**：**批一核心**。定义「标准修订 → 既有证据标记待复核 → 完成门禁要求逐条有证据」。**P0**。

#### CAP-B-02 完整性审计与完备性清单 ★ ｜判断：**深化（P0）**
- **用户任务**：别漏了我不知道要验的东西。
- **AI 职责**：审计已有（PRD 自称 V3 灵魂能力）；**须保证审计结论本身有有效期**——标准改了，旧审计结论不应继续生效。
- **可信要求**：审计清单选择器已补（GAP-T-03 清偿）；人工执行闸门提示已随 B-08 二期收口。
- **冗余/缺口**：缺口=**审计结论与标准版本的绑定**（与 B-01 同源）。
- **建议**：与 B-01 **同一链路设计**，不拆成两个功能。**P0**。

#### CAP-B-03 执行与审批 ｜判断：保留 + 补执行前约束
- **用户任务**：确定的规则在执行前生效，而不是事后追责。
- **AI 职责**：派发前判断「信息是否足够、依赖是否满足」，并向用户提出补充请求。
- **可信要求**：**[已核实] 派发门禁只查验收契约**（`dispatch.service.ts:288`），**不校验 blockedBy**；**并行无隔离**——cwd 恒为项目级共享工作区根（`dispatch.service.ts:887-912`→`cli-executor.service.ts:120`），`worktree` 在 server/cli/shared 零命中；`Execution` 无「同一 issue 仅一个活跃执行」约束。
- **冗余/缺口**：缺口=依赖门禁 + 最小执行隔离 + 成果合入归属。
- **建议**：与 A-04/A-19 合并设计成**一条用户流程**。**P0**。
- **边界澄清**：PRD §15 非目标「不做多 agent 协同调度编排」**继续有效**——最小执行隔离与依赖约束**不属于**协同调度编排。

#### CAP-B-04 本地运行时 ｜判断：保留
- 无实质意见；单实例、注册/心跳、能力上报属稳定地基。**P3**。

- **用户任务**：（开发用户）换 provider 成本低。

#### CAP-B-06 上下文策展 ｜判断：深化（待核实后定级）
- **用户任务**：agent 执行前拿到**正确且当前有效**的依据。
- **AI 职责**：这本身就是 AI 上下文能力。
- **可信要求**：ContextPack 四层策展（既有）。**[待核实]** `ContextPackSnapshot.freshness` 是否恒写 `realtime`（若成立，则「新鲜度」字段失真，用户与 AI 都会误以为上下文是当前的）。
- **冗余/缺口**：缺口=上下文时效性校验。

#### CAP-B-07 信任与扩展 ｜判断：澄清定位
- **用户任务**：（非专业用户）「我能信任这个 AI 到什么程度」，并据此决定放权。
- **AI 职责**：信任等级应**影响放权**（PRD §12 原则 4「渐进放权」）；非专业用户需要的是**可理解的分级授权**，不是抽象评分。
- **可信要求**：放权与「哪些操作必须人确认」联动；信任变化可追溯。
- **冗余/缺口**：缺口=信任评分与决策卡/审批门禁的实际联动关系不明。
- **建议**：从「评分」转向「用户可理解的分级授权」，与 [[#CAP-C-04]] 结合。**P1**。

#### CAP-B-08 验收证据回流 ｜判断：**深化（P0，含缺陷修复）**
- **用户任务**：证据能证明「这次交付过了」，且通过之后不会被悄悄改写。
- **AI 职责**：整理证据、指出证据缺口（不做「AI 宣布成功」）。
- **可信要求**：**[已核实] 守卫状态名过期**——`github-evidence.subscriber.ts:70` 守卫 `status === 'accepted' || 'abandoned'`，而 schema 口径为 `draft|pending|in_review|passed|failed|waived`（`schema.prisma:1855`）。**`passed` 契约不会被拦住**，后续 merged/closed 事件仍写 `completionEvidence`（仅 open 覆盖被 `:78-83` 乱序防御挡住）。→ 「通过后证据被改写」，可信度硬伤。
- **冗余/缺口**：另 **[据核查]** 发布门禁 CI 检查取最近 200 条 `ci_result` 证据，**不按时间窗/版本过滤**（`release-gate.service.ts:129-146`）；系统回流证据**不改 criteria.status**，故失败的 CI 不自动拦截验收。
- **建议**：**先修守卫口径（缺陷）→ 再补证据与标准的版本绑定 → 最后接完成门禁**。**P0**（守卫修复成本极低，建议独立小 PR 先行）。

- **可信要求**：当前供给链已闭环（grill → 分析 → 拆解 → 任务族 + 验收清单 → 审计）。**缺口在修订侧**：需求改动后，哪些任务要改、哪些执行基于旧需求、哪些标准要更新、哪些证据过期、哪些发布审批需重认——**无承载**。
- **冗余/缺口**：四期落地（GAP-T-29 清偿）。**缺口 = 全过程修订链路**，这是本轮最重要的缺口之一。
- **建议**：**从「首次生成」扩展为「持续维护」**：需求/标准修订 → 影响分析（复用 K 线契约绑定范式）→ 人确认处理方式 → 相关验收标记待复核。**不新建模块**（复用 document/playbook/ai-hub 既有承载）。**P0**。

## 七、跨卡结论

### 7.1 六张最关键的卡（P0 批次）

| 卡 | 缺什么 | 为什么关键 |
|----|--------|-----------|
| B-01 | 标准版本与证据失效 | 用户的「通过」无法追溯对应对哪版标准 |
| B-02 | 审计结论有效期 | 灵魂能力，但结论会过期 |
| B-08 | 守卫口径缺陷 + 版本绑定 | 通过后证据仍被改写（硬伤，修复成本极低） |
| B-03 / A-04 | 依赖门禁 + 最小执行隔离 | 规则在执行前生效，而非事后追责 |
| C-04 | 批准与内容版本绑定 | 知情选择；与 B-01 同源 |
| P-01 | 需求修订修订链路 | 把需求/工单/执行/文档/契约/验收/发布串起来 |

### 7.2 本轮明确「不应被削弱」的卡

**C-08（AI 表面）、C-07（AISlot）、C-04（决策卡）、C-03（Playbook）、A-18（统一创建面板）**——对专业用户是辅助，**对非专业用户可能是完成工作的主要界面**。

判定标准（[[需求重审-总纲-v1]] §3.3 末条）：**它有没有减少理解成本、帮助作出正确决策、推进实际工作？**
应砍的是**没有作用的表现形式**，不是 AI 介入本身。

### 7.3 本轮明确「应停止扩张」的卡

A-05（配置面）、A-12（画布节点类型/模板库）、A-17（快捷键收编范围）、C-02/C-05/K-01（价值待证者不扩）。

### 7.4 需澄清的两处边界

1. **G5 最小执行隔离 ≠ PRD §15 非目标「多 agent 协同调度编排」**——前者是「别让两个执行改坏同一个目录」，后者是编排能力。前者应补，后者仍是非目标。
2. **C-04 决策卡 / C-08 AI 表面「界面变多」≠ 冗余**——判定标准是「是否帮用户理解与推进」，见 §7.2。
