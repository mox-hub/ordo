# 需求重审总纲 v1

> 本文档是 2026-09-17 需求重审讨论的一致性产出，与 [[需求重审-逐卡意见-v1]]、[[能力清单-v1]]、[[需求入口流程-v1]] 配套。
> **定位**：不是新的需求真相源，也不是对 [[产品需求文档-v3]] 的取代——它是**下一次逐卡开工前的评审基线**，回答「按新的轴心，现有功能哪些该深化、哪些该收拢、哪些缺口必须先补」。
> **效力**：§二 基线为用户已确认方向；§三 起为**建议**，逐项须经 §八 待裁决流程确认后方可开工（遵守 [[需求入口流程-v1]] 硬规则：未进能力清单的功能不得开工）。

### 1.1 触发

2026-09-17 需求讨论，用户提出三问：现有功能哪些冗余、哪些缺失、模块完善程度如何。讨论过程中用户给出三个方向性确认（见 §二），并要求据此做**需求重审**，逐能力卡出具审核意见。

## 二、重审基线（用户已确认）

### 2.1 轴心一：工程化可信度是下一阶段的主轴

用户原话：「保证系统的工程化可信度，这点非常重要。」

**推论**：产品竞争力不在于「功能更多」，而在于**系统能否保证做的是对的、能证明做成了、变化之后仍然可信**。据此，下一阶段的投入优先级从「让 AI 更方便地帮我做事」转向「让交付过程与结论具备可追溯的可信度」。

这与 [[能力清单-v1]] §二 的主轴裁决**不冲突**，而是把「AI 同事是手段，工程治理是目的」中的「目的」具体化为可检验的能力。

### 2.2 轴心二：AI Native 必须内生于功能设计

用户原话：「我希望同步的推进是 AI 能力的介入。我理解现在摊大饼的设计是不合适的，但是 AI Native 的能力应该在一个功能设计的时候就纳入考量范围。」

**推论**：不是「先补工程治理，再加 AI」，而是**每项能力从设计之初就同时回答「工程上如何可信」与「AI 如何让用户有能力完成它」**。

两个极端都被否决：

- 工程规则齐全，但非专业用户不会用，只能机械点「确认」；
- AI 什么都能代办，但用户不知道它依据什么、改了什么、结果是否可靠。

**关键约束（本轮明确）**：**「人确认」不得成为责任转移**。让非专业用户面对二十条技术验收标准点「全部同意」，不等于完成了可信的人审。因此每个需要人决策的点必须回答：为什么现在需要我决定 / 推荐哪个及依据 / 不同选择的影响 / 哪些是已验证哪些是假设 / 不知道时如何获取证据。

**AI 的三重角色**：解释者（把工程语言翻译成用户目标语言）、协作者（推进工作）、验证助手（整理与提示证据缺口）。**明确禁止**：AI 自己生成标准、自己宣称符合、再把自己的结论当作独立证据。

### 2.3 轴心三：用户定位扩展——非专业用户是核心考虑对象

用户原话：「这个项目最开始的目的当然是做给专业的开发团队或者有经验基础的独立开发者，但是后续随着用户调研的增加，非专业性用户的占比也在提高，所以这块也是我核心考虑的对象。」

**推论**：不做「专业版 / 小白版」两套产品，而是**同一套对象、规则、事实，提供渐进展开的交互**——默认讲目标与后果，需要时展开技术细节。

**重要限定**：专业程度是**具体任务上的差异，不是用户身上的标签**。熟悉后端的人可能不懂发布，懂业务的人可能擅长判断体验。不得据此给用户贴永久标签或做不可逆的功能裁剪。

| 用户群 | 主要需要 AI 帮什么 | 必须保留什么 |
|--------|-------------------|-------------|
| 专业开发团队 | 减少重复工作、分析影响、整理证据、发现遗漏 | 精确配置、原始证据、团队规则、可追溯性 |
| 有经验的独立开发者 | 补足无人协作的角色（需求/研发/测试/发布兼顾） | 快速操作、低管理负担、随时接管 |
| 非专业用户 | 把目标翻译成工程任务、解释选择与后果、带着完成交付 | 易懂的决策、可体验的成果、失败后的明确下一步 |

### 2.4 对 PRD V3 的一处前提修订建议

[[产品需求文档-v3]] §18 约束假设声明「**假设用户已有 Linear/Jira**：APM 不要求用户迁移，V3 主路径是共生」。

本轮用户调研结论（非专业用户占比提升）与该前提**不兼容**——非专业用户没有也不会有 Linear/Jira 工作流。

**建议修订为双入口，共享同一套验收与证据规则**：

- **独立使用**：在 APM 内从目标走到交付（服务非专业用户与独立开发者）；
- **生态接入**：专业团队继续使用既有工具，由 APM 提供治理与 AI 协作（原有共生策略）。

> 该修订触及需求真相源，**须经用户显式裁决**（见 §八 待裁决 2），本轮不直接改 PRD。

## 三、能力卡评审标准 v1（建议）

### 3.1 六问（新卡必答，老卡复审补答）

| 评审项 | 必须回答 |
|--------|---------|
| 用户任务 | 用户最终要完成什么，而不是打开什么页面？ |
| AI 职责 | AI 在哪个环节提供不可替代的帮助？不需要 AI 也可明确说明 |
| 可信依据 | 建议与结论依赖什么事实、规则、版本与证据？ |
| 人类控制 | 哪些事需要人决定？怎样保证人真正理解而非机械确认？ |
| 失败与降级 | AI 错了、不可用、信息不足时，用户怎么继续？ |
| 跨模块闭环 | 输入从哪里来，输出交给谁，变更后如何重新对齐？ |

### 3.2 测试义务扩为两类质量

现有惯例（[[需求入口流程-v1]] §六）覆盖正常流/异常流/联动，本轮建议**显式分成两类**：

- **工程规则是否守住**：不能越权、不能误用旧证据、不能绕过必要门禁、状态守卫口径与数据模型一致。
- **AI 是否真的帮上忙**：能否识别信息不足、说明依据、接受纠正并调整，而不是只测「成功生成一段文本」。

### 3.3 冗余判定标准（避免误砍）

| 判定 | 含义 | 处理 |
|------|------|------|
| 真冗余 | 同一事实被两处独立维护，口径可能不一致 | 收拢为单一真相源 |
| 合理多视图 | 同一数据不同范围/粒度/视角，且已显式声明分工 | 保留，但要保证同读口径 |
| 概念负担 | 后端分工合理，但前端暴露为多个需理解的名词 | 保留技术分工，收拢产品表达 |
| 投入冗余 | 功能本身正当，但相对主轴优先级过高 | 降低优先级，不删功能 |
| 表现冗余 | 只展示形式，不帮用户理解或推进 | 砍表现形式，不砍 AI 介入本身 |

> 末条为本轮新增且重要：**应砍的是没有作用的表现形式，不是 AI 介入本身**。对非专业用户，某些界面（AI 表面 / 决策卡 / 就地问答）可能是完成工作的**主要界面**，而非辅助。

## 四、总体诊断

### 4.1 阶段判断

> **现在不是「功能太少」，而是「可操作的对象和入口很多，但把这些对象串成可靠交付的规则还不够完整」。**

- 冗余主要在**入口、概念与投入优先级**；
- 缺失主要在**变更传播、证据有效性、执行约束、成果交接**。

## 六、优先级建议（三批）

> 排序依据：①是否直接支撑「工程化可信度」主轴；②是否阻塞其他能力；③是否服务非专业用户完成闭环。

### 批一：工程可信闭环（P0）

1. **B-01/B-02**——标准—证据—判定有效性（G1/G3），含版本对应与「证据充分性」规则。
2. **B-08**——先修守卫口径（G2），再谈版本绑定。
3. **C-04**——批准有效性：批准对象/版本/范围明确，实质变更后不得沿用旧批准（与 G1 同源）。
4. **A-04/B-03**——依赖约束进入执行前门禁（G4）。
5. **P-01**——需求修订 → 影响分析 → 重新确认链路。
6. **A-19**——从「失败兜底」延伸到「失败诊断 + 执行前约束」。

### 批二：AI 内生与概念收拢（P1）

7. **C-07**——就地问答质量门槛（能解释后果、指出缺失依据、给下一步者留；只复述字段者砍）。
