# 测试映射矩阵 v1

> 配套 [[能力清单-v1]] 与 [[需求入口流程-v1]]。
> **定位**：功能点 → 测试用例的追踪账本。测试按"实现单元"组织是既有事实，本文档补上"按用户价值索引"的反向入口。
> 数据基线：2026-09-09 盘点（server 单测 59 spec、server e2e 50 套件、前端 e2e 10 spec ≈ 101 用例）。

## 一、背景与根因

现有前端 e2e 为"页面导向 + 正常流（happy path）导向"——验证"页面能走通"，不验证"功能在所有操作下正确"。典型缺口（用户 2026-09-08 指出）：issue 详情页每个按钮、属性修改、下拉菜单取数等交互细节无覆盖；模块间联动操作无场景级用例。

**缺的不是测试代码，是覆盖登记账。** 先建账再补测，按支线二节奏（约两成精力）滚动清偿，不做一次性冲刺。

## 二、五类覆盖模型

每个功能点的用例按五类登记，替代单一 happy path 口径：

| 类 | 名称 | 说明 | 现状 |
|----|------|------|------|
| ① | 正常流 | 主路径走通 | 已有，保留 |
| ② | 交互覆盖 | 每个可操作控件一条：按钮/下拉取数/输入校验/右键/拖拽 | **缺失大头** |
| ③ | 数据边界 | 空态/加载失败/错误响应/分页边界/超长文本 | 普遍缺 |
| ④ | 模块联动 | 跨模块因果：改 issue 状态 → 看板列移 → 通知产生 → 动态出现 | 无场景级 spec |
| ⑤ | 回归保护 | 每个已修 bug 固定一条回归用例 | 零散，未成惯例 |

> **两类质量（2026-09-17 需求重审增，裁决 1）**：①-⑤按场景分类之外，每张卡的用例须同时回答两类质量——**工程规则是否守住**（不能越权、不能误用旧证据、不能绕过必要门禁，状态守卫口径与数据模型一致）与 **AI 是否真的帮上忙**（识别信息不足、说明依据、接受纠正并调整，而非只测「成功生成一段文本」）。已写入 [[需求入口流程-v1]] §六。本轮重审核出的实例：守卫状态名过期（B-08，passed 契约不被拦截）、批量判定零证据（B-01/G3）、依赖仅提示非约束（A-04/G4）。

## 五、控件清单模板（支线二标准武器）

**格式**：`PG-{页面}-CTRL-{两位序号}`，一行一控件；复杂说明下沉小节，表格保持 ≤6 列。首次盘点在支线二工作会话中实机完成，**不凭记忆预填**。

```markdown
### PG-ISSUE-DETAIL 控件清单（issue 详情页）——试点

| ID | 控件 | 类型 | 预期行为 | 覆盖①-⑤ | 用例名 | 状态 |
|----|------|------|---------|----------|--------|------|
| PG-ISSUE-CTRL-01 | （首次盘点填写） | | | | | todo |
```

**盘点规则**：遍历页面全部可操作元素（按钮/下拉/输入/右键菜单/快捷键/拖拽区），逐项登记；已有用例填名，未覆盖置 `todo`。完成后复制模板推广至看板/验收中心/契约面板等复杂页。

**试点进展（2026-09-09 夜航）**：issue 详情页已完成**代码级静态盘点**——92 项控件全量登记于独立文件 [[控件清单-issue详情页-v0]]（依据能力清单维护纪律「配套数据放独立文件」），用例名留空待支线二排期；含 8 项静态推断待确认点与 task-detail-tabs 疑似死代码发现。**实机校验待用户**。

## 六、增量惯例（防新增欠债，写进需求入口流程）

1. 新功能卡标准验收 = ①正常流 + **至少 1 条③异常流** + 涉及的④联动场景。
2. 每修一个 bug 必配一条⑤回归用例（修复合入同一 PR）。
3. 新控件进页面即登记控件清单，不留"未登记的可操作元素"。

## 七、维护纪律

- 本文档随测试资产增减**同 commit 更新**；GAP 行清偿置 `done` + 用例名。
- 数据基线（套件数量）每次全量巡检后刷新；套件名与 `apps/server/test`、`apps/frontend/e2e` 实际文件保持一致。
