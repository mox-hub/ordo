# Local Runtime 通信协议草案

## 1. 文档目的

本文件定义平台控制面与 Local Runtime 之间的通信契约，回答以下问题：

1. Runtime 如何注册到平台
2. 平台如何识别和鉴权 Runtime
3. Runtime 如何上报能力和环境信息
4. 执行任务如何下发与回传
5. 连接状态、失败与恢复如何处理

本文件是 Local Runtime 设计、CLI 接入、ExecutionRun 落地和后续桌面壳实现的上游文档。

## 2. 协议目标

平台与 Runtime 的通信协议必须满足以下目标：

- 让平台可以发现并识别本地执行节点
- 让 Runtime 可以安全获取任务、上下文与执行请求
- 让执行结果、证据、错误和审批状态可回传
- 让平台对连接状态、能力范围和版本状态可观测

## 3. 角色划分

### 3.1 控制面

控制面负责：

- 生成和维护任务
- 下发执行请求
- 管理审批流
- 记录执行历史
- 展示 Runtime 状态

### 3.2 Local Runtime

Runtime 负责：

- 注册本地节点
- 上报环境能力
- 拉取或接收执行请求
- 与文件、Git、Terminal、CLI 交互
- 回传执行状态和证据

## 4. 通信模式建议

### 4.1 总体建议

优先采用：

- `HTTP + WebSocket`

其中：

- `HTTP` 负责注册、拉取、配置查询、结果提交等请求响应型操作
- `WebSocket` 负责状态推送、审批回执、长任务事件流和心跳

### 4.2 不推荐作为第一阶段主线的模式

- 纯 IPC
  - 更适合桌面壳内部通信，不适合作为当前平台主协议
- 纯轮询 HTTP
  - 对执行流、审批回执和长任务可观测性不够友好

### 4.3 原因

采用 `HTTP + WebSocket` 的原因：

- 对现有 NestJS 后端最友好
- 同时适配未来桌面壳和独立 Runtime
- 易于跨平台
- 更适合先做 Web 控制面 + Local Runtime 方案

## 5. Runtime 注册协议

### 5.1 注册目标

平台需要知道当前有哪些可用 Runtime，以及它们属于谁、能做什么、在哪个项目范围内工作。

### 5.2 注册最小字段建议

- `runtimeId`
- `userId`
- `deviceId`
- `hostPlatform`
  - `windows`
  - `macos`
  - `linux`
- `runtimeVersion`
- `protocolVersion`
- `workspaceRoots`
- `availableProviders`
- `cliProviders`
- `connectionMode`

### 5.3 注册流程建议

1. Runtime 启动
2. Runtime 使用用户凭证或设备令牌请求注册
3. 平台返回：
   - `runtimeSessionId`
   - `accessToken`
   - `websocketEndpoint`
   - `heartbeatPolicy`
4. Runtime 建立 WebSocket 长连接
5. 平台将 Runtime 标记为可用

## 6. 鉴权与信任模型

### 6.1 鉴权原则

- Runtime 不是匿名节点
- 每个 Runtime 必须绑定到明确的人类用户或受管设备
- Runtime 的权限上限不能超过绑定用户和项目策略允许范围

### 6.2 建议鉴权维度

- 用户身份
- 设备身份
- Runtime 会话身份
- 项目级授权

### 6.3 Token 建议

建议至少区分：

- `userAccessToken`
- `runtimeSessionToken`

其中：

- 用户令牌用于用户授权安装和绑定 Runtime
- Runtime 会话令牌用于短期执行通信

## 7. 能力上报协议

### 7.1 为什么需要能力上报

平台不能假设所有 Runtime 都具备相同执行能力。

Runtime 需要显式上报：

- 当前可访问的工作区
- 支持的 CLI Provider
- Git 是否可用
- Terminal 是否可用
- 文件系统是否可用
- 权限限制与安全策略

### 7.2 建议字段

- `workspaceRoots`
- `providers.file`
- `providers.git`
- `providers.terminal`
- `providers.process`
- `providers.credentials`
- `cliProviders`
  - `codex`
  - `claude-code`
- `capabilityFlags`
- `policyConstraints`

### 7.3 设计原则

- 平台按照实际上报能力决策执行分配
- 平台不能向不具备能力的 Runtime 下发对应执行

## 8. 执行下发协议

### 8.1 下发对象

平台下发给 Runtime 的不是随意命令，而是结构化执行请求。

建议对象：

- `ExecutionDispatch`

### 8.2 最小字段建议

- `executionRunId`
- `projectId`
- `taskId`
- `contextPackRef`
- `requestedActions`
- `toolScopes`
- `policySnapshot`
- `approvalState`

### 8.3 下发方式

建议支持两种：

- Runtime 主动拉取待执行任务
- 平台通过 WebSocket 推送新执行通知

第一阶段优先：

- 平台推送通知
- Runtime 再通过 HTTP 拉取完整执行数据

## 9. 状态与事件回传协议

### 9.1 回传目标

Runtime 必须让平台知道：

- 执行是否开始
- 当前执行到哪一步
- 是否进入审批等待
- 是否成功或失败
- 产生了哪些证据

### 9.2 建议事件类型

- `runtime.connected`
- `runtime.disconnected`
- `runtime.heartbeat`
- `execution.started`
- `execution.step.updated`
- `execution.pending_approval`
- `execution.resumed`
- `execution.completed`
- `execution.failed`
- `execution.cancelled`

### 9.3 事件字段建议

- `eventType`
- `runtimeId`
- `executionRunId`
- `stepId`
- `timestamp`
- `status`
- `summary`
- `artifactRefs`
- `evidenceRefs`
- `errorCode`

## 10. 审批协同协议

### 10.1 审批与 Runtime 的关系

Runtime 不能绕过平台审批。

当执行进入待审批状态时：

1. Runtime 回传 `pending_approval`
2. 平台创建或更新 `ApprovalRequest`
3. 人类在控制面处理审批
4. 平台通过 WebSocket 通知 Runtime 审批结果
5. Runtime 恢复或终止执行

### 10.2 设计原则

- 审批结果必须由平台下发，不由 Runtime 自行推断
- Runtime 在待审批期间不得继续执行受限动作

## 11. 心跳与连接治理

### 11.1 心跳目标

平台需要知道 Runtime 是否仍然在线、可响应、可执行。

### 11.2 心跳建议

- 使用 WebSocket 心跳或显式 `heartbeat` 事件
- 平台记录最近活跃时间
- 若超时，Runtime 标记为 `unreachable`

### 11.3 断线处理

当 Runtime 断线时：

- 已在执行中的任务标记为 `blocked` 或 `disconnected`
- 平台通知相关人类成员
- 等待 Runtime 恢复或人工接管

## 12. 错误与恢复

### 12.1 错误分类建议

- `auth_error`
- `capability_mismatch`
- `workspace_unavailable`
- `provider_unavailable`
- `approval_timeout`
- `network_error`
- `runtime_crash`

### 12.2 恢复策略

- 短时网络抖动：自动重连
- Runtime 重启：重新注册并恢复可恢复执行
- 工作区丢失：阻断执行并要求人工处理

## 13. Phase 1 约束

Phase 1 中，本协议重点支持：

- 单用户绑定 Runtime
- CLI 主线执行
- Codex / Claude Code 首批适配
- 任务级 `ExecutionRun`
- 基础心跳、事件流与审批回执

Phase 1 暂不要求：

- 多 Runtime 编排调度
- 复杂离线同步
- 跨设备抢占执行
