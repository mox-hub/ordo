# 控制面与本地执行面架构草案

## 1. 文档目的

本文件用于回答一个关键架构问题：

> 产品是否要从网页端整体切换到客户端，还是采用分层过渡方案。

当前结论是：

- 不将产品整体改造成纯客户端
- 采用 `Web 控制面 + Local Runtime` 的 C 方案先落地
- 再逐步演进到 `Web 控制面 + Local Runtime + Desktop Shell` 的 D 方案

## 2. 总体判断

### 2.1 为什么不能停留在纯 Web

如果平台要深度支持 Codex、Claude Code 以及其他本地 CLI Agent，则纯 Web 形态存在天然限制：

- 对本地文件系统访问不自然
- 对 Git / Terminal / 进程通信支撑不足
- 对本地工作区和本地凭证的接入成本高
- 难以承载真实研发执行场景中的高价值动作

### 2.2 为什么现在不直接整体转客户端

如果直接把产品主形态切成纯桌面客户端，会带来新的问题：

- 跨平台开发与发布复杂度显著提升
- 会削弱 Web 在协作、审批、远程访问上的优势
- 与当前已有的项目管理底盘不匹配
- 容易把问题从“执行能力缺失”误判为“UI 形态错误”

### 2.3 当前推荐路线

推荐路线：

1. 先保留 Web 作为控制面
2. 新增 Local Runtime 作为本地执行面
3. 在 Runtime 验证成功后，再增加 Desktop Shell 提升体验

## 3. 三层结构

### 3.1 Web 控制面

职责：

- 项目管理
- 任务管理
- 迭代管理
- 成员与权限
- 审批流
- 执行回放
- 审计与通知
- 配置与策略管理

设计原则：

- 控制面保持平台中心化
- 面向协作、监督、审批和回放
- 不承担本地高权限执行

### 3.2 Local Runtime

定义：

Local Runtime 是运行在用户本机的执行层，负责平台与本地工程环境之间的能力桥接。

职责：

- 本地文件系统访问
- Git 操作
- Terminal 命令执行
- 本地 CLI Agent 通讯
- 工作区扫描与环境感知
- 执行结果和证据回传平台

设计原则：

- Runtime 是执行层，不是项目管理 UI
- Runtime 应通过统一协议与平台通信
- Runtime 负责吸收平台差异，不把系统细节泄漏给上层业务

### 3.3 Desktop Shell

定义：

Desktop Shell 是对 Web 控制面和 Local Runtime 的桌面封装层。

职责：

- 提供桌面入口
- 托管或管理 Local Runtime
- 降低本地连接和执行门槛
- 提供更自然的一体化交互

设计原则：

- Shell 是体验增强层，不是新的业务核心
- 不应把所有业务能力重新实现在桌面壳中
- Web 控制面仍然保留独立存在价值

## 4. 方案对比

### 4.1 方案 A：纯 Web

优点：

- 交付成本最低
- 跨平台最简单
- 部署最轻

缺点：

- 无法很好承载本地研发执行场景
- 与 CLI Agent 协作能力不足

结论：

- 不满足长期目标

### 4.2 方案 B：全面转纯客户端

优点：

- 本地能力最强
- 文件、Git、Terminal、CLI 集成自然

缺点：

- 改造跨度过大
- 跨平台成本高
- 远程协作与审批体验会变差

结论：

- 当前阶段不建议

### 4.3 方案 C：Web + Local Runtime

优点：

- 在保留现有底盘的前提下补齐本地能力
- 技术与产品风险可控
- 更适合先验证外部 AI 工具深度参与

缺点：

- 体验不如桌面壳一体化
- 本地安装和连接管理需要额外设计

结论：

- 当前阶段推荐方案

### 4.4 方案 D：Web + Local Runtime + Desktop Shell

优点：

- 兼顾平台协作与本地执行
- 同时支持远程控制面和本地高能力执行
- 更适合长期演进

缺点：

- 复杂度高于方案 C
- 需要在 Runtime 稳定后再进入

结论：

- 推荐作为中长期目标方案

## 5. 关键职责边界

### 5.1 控制面负责什么

- 定义任务
- 分配执行主体
- 下发执行策略
- 处理审批
- 展示历史与结果

### 5.2 Runtime 负责什么

- 与本地工程环境交互
- 执行受控工具动作
- 收集执行证据
- 回传执行状态

### 5.3 Shell 负责什么

- 提供更顺滑的使用入口
- 管理 Runtime 生命周期
- 封装平台与本地能力的连接体验

## 6. 协议层要求

无论是 Web、Runtime 还是未来的 Desktop Shell，都必须复用统一协议层。

协议层至少包括：

- `AgentIdentity`
- `ContextPack`
- `ToolDefinition`
- `ExecutionRun`
- `ApprovalRequest`
- `ExecutionArtifact`
- `ExecutionEvidence`

设计原则：

- 协议层优先于 UI 形态
- 同一执行模型同时服务 Web 和本地执行
- UI 改变不应破坏执行契约

## 7. 跨平台抽象要求

为避免把 Windows / macOS / Linux 差异直接暴露给业务层，Runtime 应尽早抽象以下 Provider：

- `FileProvider`
- `WorkspaceProvider`
- `ProcessProvider`
- `TerminalProvider`
- `GitProvider`
- `CredentialProvider`

这些 Provider 负责吸收：

- 路径格式差异
- shell 差异
- 权限模型差异
- 进程启动与管理差异
- 文件监听差异

## 8. 技术路线建议

### 8.1 当前阶段

先做：

- Web 控制面
- Local Runtime
- CLI 接入
- 文件 / Git / Terminal 抽象

### 8.2 后续阶段

验证 Runtime 价值后，再做：

- Desktop Shell
- Runtime 内置与连接体验优化
- 更强的本地执行与观察能力

### 8.3 桌面壳技术建议

如果后续进入桌面壳阶段，优先考虑：

- Electron

原因：

- 更适合当前 TypeScript / Node 技术栈
- 更容易复用现有前端和本地 Node 能力
- 适合先验证桌面一体化体验

Tauri 可作为后续评估项，但不建议当前阶段就把 Rust 引入主路线。

## 9. Phase 1 约束

Phase 1 的产品形态约束如下：

- 控制面仍以 Web 为主
- CLI 是首条接入主线
- Local Runtime 是首个新增的本地执行组件
- Desktop Shell 不进入 Phase 1 必须交付

## 10. 演进路径

### 10.1 Phase 1

- 保持 Web 控制面
- 打通 Local Runtime
- 优先支持 Codex / Claude Code CLI 接入

### 10.2 Phase 2

- 深化 Git / Terminal / Workspace 能力
- 补强 MCP 接入
- 完善 Runtime 的跨平台抽象

### 10.3 Phase 3

- 增加 Desktop Shell
- 优化本地一体化体验
- 视验证结果决定桌面端是否成为主入口之一

## 11. 待确认问题

1. Local Runtime 是否作为独立安装程序交付，还是作为桌面壳内置组件先行
2. Runtime 与平台的通信是否优先采用本地 HTTP、WebSocket 还是 IPC 桥接
3. CLI 工具的会话管理是否由 Runtime 统一抽象
4. Desktop Shell 是否需要支持部分离线能力
