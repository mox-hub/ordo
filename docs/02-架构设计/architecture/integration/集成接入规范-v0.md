# 集成接入规范 v0（草案）

> 本文是第三方集成（GitHub / Linear / GitLab / Jira / MCP …）接入的**规范草案**：基于 2026-09-11 全量盘点给出事实基线，收敛 Provider 抽象、前端一致性、事件回流与 AI 工具面四条规范，并给出分期落地建议。

> 关联文档：[CLI/MCP 接入现状](../CLI-MCP-接入现状.md)、[后端模块结构](../backend/modules.md)、[技术架构总览](../技术架构总览.md)。
>
> 行号证据基于分支 `feat/acceptance-audit-frontend`（2026-09-11），后续漂移以符号名为准。

## 二、Provider 规范（v0 收敛目标）

### 2.1 Provider 接口草案

每个第三方系统实现一个 `IntegrationProvider`，由注册表统一收口：

```ts
// apps/server/src/modules/integration/provider.types.ts（建议位置）

/** 连接状态统一口径（§2.4） */
export type IntegrationStatus = 'connected' | 'disconnected' | 'error' | 'syncing';

export interface ProviderIdentity {
  id: string;                       // 'github' | 'gitlab' | 'mcp' …，全仓唯一
  name: string;                     // 展示名
  description: string;
  capabilities: Array<'issue-sync' | 'pr-sync' | 'webhook' | 'mcp-tools'>;
  defaultScopes?: string[];         // 建议申请的凭据权限（供 Connect 流展示）
}

export interface ProviderCredentialsSchema {
  /** zod schema：声明凭据字段及其敏感性；敏感字段永不出网（对齐 integration.service.ts 恒脱敏） */
  schema: ZodType<Record<string, unknown>>;
  sensitiveFields: string[];        // 如 ['token', 'webhookSecret']
}

export interface SyncResult {
  status: 'ok' | 'partial' | 'failed';
  pulled?: number;
  pushed?: number;
  skipped?: number;
  errors?: Array<{ entity: string; id?: string; message: string }>;
  /** 同步明细写各 link 表（IssueProviderLink / ExternalProjectLink），此处只回摘要 */
}

export interface IntegrationProvider {
  readonly identity: ProviderIdentity;
  readonly credentials: ProviderCredentialsSchema;

  /** 连接测试：用已存凭据探活（服务端内部调用，替代散落的 test-inline 逻辑） */
  testConnection(config: Record<string, unknown>): Promise<{ ok: boolean; error?: string; detail?: unknown }>;

  /** webhook 校验：raw body + headers + 已存 secret；无 secret 或校验失败必须返回 false（见 §2.5） */
  verifyWebhook?(rawBody: Buffer, headers: Record<string, string>, config: Record<string, unknown>): boolean;

  /** webhook 事件 → 领域事件名的映射（供事件回流，§四） */
  listWebhookEvents?(payload: unknown): Array<{ name: string; payload: unknown }>;

  /** 手动/定时同步入口（替代 integration.controller.ts:144 绑死 LinearSyncService） */
  sync?(configId: string, option?: { direction?: 'pull' | 'push' | 'both' }): Promise<SyncResult>;

  /** 事件回流声明：本 provider 会经 socket 推给前端的事件名（'github.pull_request.updated' 风格） */
  emittedEvents(): string[];

  /** 健康探活：供状态页与降级判断 */
  healthCheck?(config: Record<string, unknown>): Promise<{ status: IntegrationStatus; latencyMs?: number }>;

  /** （P2）本 provider 暴露给 AI 的工具，三同源注册（§六） */
  listTools?(): IntegrationToolDefinition[];
}

export interface ToolExecContext {
  workspaceId: string;
  userId: string;              // 发起人（human 或其代理 AI member）
  integrationConfigId: string; // 已过 assertIntegrationAccess 的配置
  /** MemberToolGrant 授权在 execute 外层统一校验，provider 内不重复实现 */
}
```

### 2.2 注册表：消灭手工 imports 与硬编码名单

```ts
// apps/server/src/modules/integration/provider.registry.ts（建议位置）
export const INTEGRATION_PROVIDERS = Symbol('INTEGRATION_PROVIDERS');

@Injectable()
export class IntegrationProviderRegistry {
  constructor(@Inject(INTEGRATION_PROVIDERS) private readonly providers: IntegrationProvider[]) {}

  get(id: string): IntegrationProvider;            // 未知 id 抛 NotFoundException
  require(id: string, cap: ProviderCapability): IntegrationProvider;  // 能力不齐抛 BadRequest
  list(): IntegrationProvider[];
  /** 取代 ALLOWED_PROVIDERS：名单即注册表，永不漂移 */
  allowedIds(): string[];
}
```

- **注册方式**：`integration.module.ts` 改为 `providers: [{ provide: INTEGRATION_PROVIDERS, useValue: [GitHubProvider, LinearProvider] }]`（或 barrel 导出数组，一处追加）。现存的手工 imports（`integration.module.ts:8`）与 `ALLOWED_PROVIDERS`（`integration.service.ts:19-29`）一并删除，`createIntegrationConfig` 的校验改为 `registry.has(dto.provider)`。
- **语义修正**：注册表是唯一名单后，"gitlab 可建配置但无实现"的假可用自然消失——未注册即不可建。
- github/linear 现有三层结构不强制推翻：`GitHubProvider` 作为**门面**包住现有 `GitHubSyncService/SDKService/Client`，`LinearProvider` 包住 `LinearSyncService`，存量逻辑渐进内迁。

### 2.3 assertIntegrationAccess 单点收敛

- 现存三份实现（B5）收敛为 `IntegrationService.assertIntegrationAccess(integrationId, userId)` 一份（建议放在 integration.service，github/linear controller 改为调用它）。
- 统一异常口径：配置不存在 → `NotFoundException`；project scope 无成员资格 → `ForbiddenException`。`github.controller.ts:354-361` 的 BadRequestException 与 linear 的 global 分支空壳按此修正。
- linear 的 global 分支空壳（`linear.controller.ts:48-69`）要么补齐 workspace 级校验，要么显式注释"global scope 全 workspace 可见"为既定语义。

### 2.4 状态枚举统一口径

统一连接态 `IntegrationStatus = connected | disconnected | error | syncing`，同步明细态统一 `pending | synced | error`。存量映射（读侧映射、写侧新口径，不强制数据迁移）：

| 现状口径 | 位置 | 映射到 IntegrationStatus |
|---|---|---|
| `IntegrationConfig.status` | `integration.service.ts:104` | 直接纳管，增 `syncing` |
| 前端自加 `pending` | `integrations-section.tsx` STATUS_CFG | `disconnected`（凭据未就绪）或 `syncing`（连接中），按语义取一 |
| `McpServerConfig.lastStatus` | `schema.prisma:2185` | online→connected、offline→disconnected、unknown→disconnected |
| `IssueProviderLink.syncStatus` | schema.prisma | 连接态取 provider config；pending→syncing、synced→connected、error→error |
| `ExternalProjectLink.syncStatus` | schema.prisma | active→connected、paused→disconnected、error→error |
| `Repository.validationStatus` | schema.prisma | valid→connected、invalid→error、unknown→disconnected |

> 前端徽章只消费统一口径（§三.3）；各 link 表的细粒度同步态作为 detail 展示，不再各自发明连接语义。

### 2.5 错误与鉴权基线

| 规则 | 内容 | 修复对象 |
|---|---|---|
| R1 | 任何 test 连接端点必须落在 JWT/PAT guard 内；匿名 test-inline 属安全缺陷 | `github.controller.ts:80-87`（补 guard 或并入受保护端点） |
| R2 | webhook 校验：配置了 secret → HMAC 必验；**未配置 secret → 一律拒绝（403）**，绝不因"带任意 signature"放行 | `github.controller.ts:406-410` 的 `return signature !== undefined` 改为 `return false` |
| R3 | webhook 入口统一走 `provider.verifyWebhook`，controller 不自写校验逻辑；`WebhookEventLog` 审计模式推广为通用要求 | `github.controller.ts` 私有校验段 |
| R4 | 凭据仅 configJson 加密存储、响应恒脱敏；敏感字段永不出网、永不回显（对齐 `integration.service.ts:44-66,152-155`） | §三.4 前端配合；MCP/CliProvider 凭据加密化见 §八裁决点 |

## 三、前端一致性规范

### 3.1 集成页面骨架五段式

每个已支持 provider 的设置页统一五段，缺段显式标注"未提供"而不是另起炉灶：

| 段 | 内容 | 现状落点（参照/缺口） |
|---|---|---|
| ① 卡片目录 | 集成卡片（状态徽章 + Connect 入口 + coming_soon 标注） | `integrations-section.tsx` INTEGRATION_CATALOG 已有；onConnect 断裂待修（F2） |
| ② Connect 流 | 凭据采集表单 → testConnection 校验 → **保存 IntegrationConfig（必须落库）** | linear 已有；github 仅「测试不保存」，须改造 |
| ③ 配置表单 | scope（global/project）、启用开关、同步方向、事件订阅选项 | linear 已有；github 缺 |
| ④ 状态与同步面 | 统一状态徽章 + 手动同步按钮 + 最近同步时间 + 错误摘要 | linear 已有（9 组件）；github 只有 PR 轮询列表 |
| ⑤ 日志与审计 | sync-logs（走通用端点）+ webhook 事件日志 | linear 有；github 有 WebhookEventLog 但前端未消费 |

- 修复 F2 断裂：github 卡片 `onConnect` 必须指向真实 Connect 流（创建 IntegrationConfig 并保存凭据），GithubSetupCard 的「仅测试不保存」只允许作为 Connect 流内的**校验步骤**，不得作为终态；空态引导链接必须指向真实存在的路由。
- 五段式适用于新 provider（如 GitLab）：②③ 按凭据 schema 通用渲染，④⑤ 复用 linear 的组件骨架，不逐家手写。
- linear 五段已基本齐备，作为参照实现；github 补齐 ②③⑤。

### 3.2 供应商目录单源化

- **推荐方向**：目录元数据以后端为单源——`IntegrationProviderRegistry` 新增 `GET /integrations/providers` 端点下发 identity（id/name/description/capabilities/status: available|coming_soon），前端 `INTEGRATION_CATALOG` 改为消费该端点，本地仅保留**展示性资源映射**（图标组件、渐变色）。BUILTIN_PROVIDERS（`builtin-providers.tsx`）与硬编码 6 家目录一并退役。

  响应形态（示意，进 openapi.json 走 `contract:export`）：

  ```json
  {
    "providers": [
      {
        "id": "github",
        "name": "GitHub",
        "description": "PR 同步与证据回流",
        "capabilities": ["pr-sync", "webhook"],
        "status": "available",
        "emittedEvents": ["github.pull_request.updated"]
      },
      { "id": "gitlab", "name": "GitLab", "status": "coming_soon", "capabilities": [] }
    ]
  }
  ```

- 备选：纯前端单文件 manifest（`modules/integration/providers.manifest.ts`），后端注册表仍独立——代价是名单仍有两份、需 CI 校验一致。
- 未实现的 provider（如 jira coming_soon）由 manifest 标注，后端注册表永不收录，杜绝 `ALLOWED_PROVIDERS` 式漂移。

### 3.3 状态徽章单一组件

- 收敛为 `shared/components/integration/integration-status-badge.tsx` 一个组件，入参统一 `IntegrationStatus`（§2.4），内部维护唯一的颜色/文案映射表。
- 四套现状（F4）迁移顺序：settings STATUS_CFG 与 linear-status-badge 先并（二者语义最近），ai-agents-section mcpServerStatus、git-tool-status 随 §2.4 口径落地后跟进。
- toast 双轨（F5）在集成域内统一走 `@/hooks/use-toast`（与全站主流一致），不再新增 `@/components/ui/toast` 引用。

### 3.4 凭据表单规范

- 凭据输入一律 `type="password"` + autocomplete 关闭；**永回显明文**——保存成功后仅显示掩码（`ghp_****`）与「已配置，更新于 x」状态。
- 「测试连接」与「保存」分离：测试可用未保存的草稿凭据（服务端受保护 test 端点，§2.5 R1），保存必须显式确认。
- 前端任何组件不得把 configJson 内容打进日志/埋点。

## 四、事件回流规范

目标形态：**socket 实时为主、轮询仅降级兜底**，对齐 linear 已验证的回推链路（B9），消灭 github 的"发布无订阅"（B8）。

统一事件流转（webhook 类）：

```
第三方 webhook 入站
  → provider.verifyWebhook(rawBody, headers, config)   [失败即 403，写审计]
  → provider.listWebhookEvents(payload)                [映射为领域事件]
  → messageBus.publish('{provider}.{entity}.{action}') [审计：WebhookEventLog 模式]
  → events.gateway 统一订阅（按 registry.emittedEvents 声明）
  → socket 按 workspace 房间转发 integration.{provider}.event
  → 前端订阅刷新（linear-integration-section 为参照实现）
```

| 规则 | 内容 |
|---|---|
| E1 | provider 在 `emittedEvents()` 声明事件名，命名 `{provider}.{entity}.{action}`（对齐既有 `linear.sync.*`、`github.pull_request.updated`）；未声明的事件不得出网 |
| E2 | webhook 类集成必配 socket 转发：webhook → `provider.verifyWebhook` → messageBus 发布 → `events.gateway` 统一订阅并按 workspace 房间转发。gateway 侧做**一次通用实现**，按 registry 声明订阅，而非每 provider 手写 |
| E3 | 领域事件必须有订阅者：发布事件前在 `emittedEvents()` 登记 + 前端对应订阅（或 CI/测试断言"零订阅事件"报错），杜绝 `github.pull_request.updated` 式空转 |
| E4 | 前端：socket 在线时停用轮询；断线降级到既有 30s 轮询（github-integration-section 现状作为降级路径保留），socket 重连成功后立即做一次全量同步再停轮询 |
| E5 | 无 webhook 的 provider（如 linear 现状）允许手动/定时同步触发事件，E2 的 gateway 转发逻辑复用；webhook 能力具备后补 `verifyWebhook` 即可 |
| E6 | webhook 处理须幂等：以投递 ID（如 GitHub `X-GitHub-Delivery`）去重，重复投递不重复同步；审计日志保留原始 payload 摘要供回放 |

> 轮询降级兜底的取值：轮询间隔维持各 section 现状（github 30s）；仅当 socket 断开超过一个轮询周期才认为降级生效，避免 socket 抖动期间双通道风暴。

## 五、mcp/servers 与 integration 两条平行体系

现状：`McpServerConfig`（外部 MCP 消费，明文凭据，探活即断开，工具不进 buildTools）与 `IntegrationConfig`（加密凭据，无 provider 抽象）互不相通（B11/B12）。

- **推荐方向 A（provider 化合并）**：把"外部 MCP server"注册为一种 provider（`identity.id = 'mcp'`），凭据（headers/env）入 configJson 加密；`healthCheck` 即探活，`listTools` 即工具发现；发现的工具经 §六注册表进 assistant buildTools，`MemberToolGrant` 的 mcp_server scope 在执行链上真正消费。`McpServerConfig` 渐进迁移为 `IntegrationConfig(provider='mcp')`（是否带数据迁移见 §八）。mcp-server 模块保留**服务端暴露**职责（SSE transport），仅此一职。
- **备选 B（平行对接）**：两模块保持独立，仅打通两点——凭据加密化（McpServerConfig 增 configJson 或迁 EncryptionService）+ 工具引用（assistant 注册表登记 MCP 工具）。改动小，但 provider 接口出现第二套"探活+工具"语义，长期两套心智。
- 无论 A/B：SSE → StreamableHTTP 迁移独立推进（SDK 弃用 SSE 是外部约束，不因本规范延宕），时机见 §八。

若走方向 A，迁移按三步走、每步独立可回退：

| 步 | 内容 | 回退方式 |
|---|---|---|
| S1 | 凭据加密化：McpServerConfig 的 env/headers 写入改走 EncryptionService（读侧兼容存量明文） | 读侧兼容层保留即可回退 |
| S2 | provider 化：注册 `McpClientProvider`（healthCheck=listPing、listTools=工具发现），新配置一律建 IntegrationConfig(provider='mcp') | 旧 McpServerConfig 读路径仍在，双读期不破坏 |
| S3 | 收口：存量 McpServerConfig 数据迁移（若 D3 裁决迁移）后，mcp-servers.controller 的配置 CRUD 退役，探活/刷新走通用 provider 端点 | 删除前冻结写入口 |

## 六、AI 接入规范

### 6.1 集成工具三同源注册

现状三同源（A1）靠人肉同步三处；目标一份定义、三个出口：

```ts
export interface IntegrationToolDefinition {
  name: string;              // 'github.list_open_prs'，{provider}.{verb_object}
  provider: string;          // 所属 provider id
  description: string;       // LLM 可读，中英皆可但唯一
  parameters: JSONSchema;    // 与 zod schema 单源生成
  requiredScopes: string[];  // 所需凭据权限，供 MemberToolGrant 校验
  execute(ctx: ToolExecContext, args: unknown): Promise<unknown>;  // ctx 携带 integrationConfigId/workspace/user
}
```

| 出口 | 消费方式 |
|---|---|
| `ASSISTANT_TOOL_CATALOG`（HTTP 目录） | registry.listTools() 渲染目录项，替代手写目录 |
| `buildTools()`（LLM 工具，`assistant-tools.service.ts`） | 按 member 授权过滤后 `tool({...})` 包装 |
| MCP 服务端暴露（`modules/mcp-server`） | listTools() 注册进工具表，替代巨型 switch（A2） |

约束：一个工具三处同名同参同语义；`execute` 内必须先过 `assertIntegrationAccess`（§2.3）与 MemberToolGrant 授权；工具产生的副作用走既有审批/审计链路（ApprovalRequest / audit）。

### 6.2 首个示例工具

以 `github.list_open_prs` 为例（数据源现成：`RemotePullRequest` 表，schema.prisma:961）：

| 字段 | 值 |
|---|---|
| name | `github.list_open_prs` |
| provider | `github` |
| description | 列出指定仓库的开放 PR（含状态、作者、最近更新），供 AI 掌握待审/待合进度 |
| parameters | `{ repo?: string, state?: 'open'\|'changes_requested', limit?: number }` |
| requiredScopes | `['repo:read']`（映射 MemberToolGrant 校验） |
| execute | 查 `RemotePullRequest`（workspace 隔离 + `assertIntegrationAccess`），不直连 GitHub API |
| 三出口 | HTTP 目录项 / buildTools LLM 工具 / MCP 服务端工具，同名同参 |

### 6.3 落地顺序

1. 先在 mcp-server 内建工具注册表替换巨型 switch（不改行为，纯结构）；
2. `assistant-tools.service.ts` 的集成类工具改从 provider registry 读取；
3. 第一个集成工具（即上例 `github.list_open_prs`）走通三出口后，再批量补齐。

## 九、实施分期建议

v0 规范不强求一次到位，按"先堵安全与断链、再立抽象、最后接 AI"分三期：

| 期 | 主题 | 内容 | 主要涉及 | 验收 | 风险 |
|---|---|---|---|---|---|
| **P0** | 收敛性修复（不动架构，可立即做） | ① github 卡片 onConnect 断裂修复（F2）；② test-inline 补 JWT guard（B6/R1）；③ webhook 无 secret 拒绝（B7/R2）；④ assertIntegrationAccess 收敛 + 异常口径统一（B5）；⑤ 旧页面删除（F6，若 D6 通过） | github.controller.ts、github/linear 两个 controller、integrations-section.tsx | 越权/匿名面清零；github 可从前端完整创建配置 | D8 webhook 行为变更影响现网未配 secret 的仓库 |
| **P1** | provider 注册表重构 | ① IntegrationProvider 接口 + registry（§2.1/2.2）；② github/linear 门面化；③ 状态枚举统一 + 徽章单组件（§2.4/§3.3）；④ 目录单源化 + `GET /integrations/providers`（§3.2）；⑤ 事件回流：gateway 通用转发，github 事件接上订阅者（§四）；⑥ 通用 sync-logs 解绑 linear（B4） | integration 模块、events.gateway、settings 三 section、openapi.json | 新增 provider 仅动 provider 目录 + 图标；零订阅事件清零；providers 端点上线 | linear 1100 行引擎门面化需回归双向同步；涉及契约变更须跑 `contract:check` |
| **P2** | AI 工具面接入 | ① IntegrationToolDefinition + 三同源注册（§六）；② mcp-server 工具注册表化（A2）；③ 外部 MCP 工具进 buildTools + MemberToolGrant 执行链接通（B12，随 D2 裁决）；④ mcp/CliProvider 凭据加密化（D4）；⑤ 首批集成工具（github PR 查询、linear issue 查询）上线 | ai-hub assistant-tools、mcp-server、integration provider 接口扩展 | assistant 与 MCP 出口工具同名同参；AI 可经工具读取集成数据 | 依赖 P1 registry 就绪；MemberToolGrant 授权语义需与 trust 域对齐 |

> 依赖关系：P0 独立可先行；P1 是 P2 的前置（工具注册表消费 provider registry）；P1 的 ④⑤ 涉及 API 契约与前端类型生成，须遵守 AGENTS.md §九契约驱动流程（先 openapi.json/DTO，后 `contract:export`）。
>
> 本规范为架构文档，其落地涉及的功能变更（如集成类 AI 工具、GitLab 支持）开工前仍须按 `requirement-intake` 流程登记进 `docs/01-需求/能力清单-v1.md`。
