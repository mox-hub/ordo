# Agent Project Manager 产品架构愿景

> 本文档是项目的主架构文档，描述产品愿景、双表面架构、模块体系与核心建模原则。
> 与 [[产品需求文档-v3|PRD V3]]（需求真相源）和各 Feature 模块文档（v2.1.0）对齐。
> v2.1.0 版本完全重写，对齐三类主体模型、12 模块架构、ContextPack 四层策展与执行治理主线。

## 一、产品愿景与定位

Agent Project Manager（APM）是一个 **AI 原生的项目管理平台**，核心目标是让人类项目经理通过平台协调外部 AI 开发工具（如 Codex、Claude Code）完成项目开发。

### 1.1 核心差异化

**与传统 PM 工具的区别**：不是"项目管理工具 + AI 功能"，而是从底层重新设计为"双表面系统"——AI 是一等公民，不是附加模块。

| 维度 | APM | Linear / Jira | 纯 AI 工具 |
|------|-----|---------------|-----------|
| AI 定位 | 原生一等公民 | 附加功能 | 自身能力 |
| 执行治理 | 审批门 + 审计 | 无 | 无 |
| 结构化上下文 | ContextPack 四层策展 | 无 | 各自抓取 |
| 外部 Agent 接入 | 统一平台（CLI/MCP/API/Plugin）| 无 | - |

### 1.2 系统服务对象（三类主体）

平台显式区分三类主体，统一建模：

- **人类成员（`human`）**：项目经理、开发者、Tech Lead、测试、架构
- **平台内 AI 成员（`platform_ai_member`）**：平台内部长期存在的 AI 组织成员（Phase 2/3 演进）
- **外部接入 Agent（`external_agent`）**：通过 CLI/MCP/API/Plugin 接入的外部 AI 工具（Phase 1 主要服务对象）

> 必须显式区分的原因：生命周期不同、所属关系不同、权限授予方式不同、审计展示方式不同。详见 [[角色级权限模型-v1|角色-等级-权限模型]]。

### 1.3 核心价值主张

- 将分散的工具链（IDE、Terminal、Git、CI/CD）通过 AI 智能中枢整合
- 任务、文档、代码、沟通不再割裂，形成完整的工作流闭环
- AI 不仅是聊天助手，而是有身份、权限、审批链的操作主体
- 上下文不再让 Agent 自己抓取，而是分层策展后结构化提供（ContextPack）

## 二、双表面架构（Dual Surface Architecture）

双表面是 APM 的核心架构特征：人类与 AI 各有专属的交互入口，共享同一套执行核心。

### 2.1 架构总览

```
┌─────────────────────────────────────────────────────────┐
│                    Human Surface                         │
│         Web UI — 监督、审批、观察、干预                    │
│    (Dashboard, Task Board, Approval Center, Replay)     │
└────────────────────────┬────────────────────────────────┘
                         │
┌────────────────────────┼────────────────────────────────┐
│              Execution Core（执行核心）                    │
│   12 个 Feature 模块 · 可授权、可审计、可组合              │
│   Subject → ExecutionRun → ApprovalRequest → Audit      │
│   ContextPack 四层策展 → Agent 执行 → 结果回写            │
└────────────────────────┬────────────────────────────────┘
                         │
┌────────────────────────┼────────────────────────────────┐
│                   Agent Surface                          │
│      CLI + MCP + (API/Plugin) — AI 原生接入              │
│    SubjectMapping → ToolDefinition → ContextPack        │
└─────────────────────────────────────────────────────────┘
```

### 2.2 Human Surface（人类界面）

保留 Web UI，但角色从"操作界面"转为"监督与干预界面"：

- **项目仪表盘**：项目健康度、风险摘要、目标约束、AI 风险预警
- **任务看板**：任务分配、执行观察、结果确认、列表/看板视图
- **审批中心**：对 AI 执行计划的审批/拒绝（含通知内嵌动作）
- **执行回放**：查看 Agent 运行轨迹、步骤、上下文快照、产物证据
- **Agent Console**：查看 Agent 身份、执行队列、审批请求、信任等级

### 2.3 Agent Surface（Agent 界面）

面向通用 Agent 的原生接入层。Phase 1 主线为 CLI，MCP 紧随其后：

**A. CLI Surface（Phase 1 主线）**
- 面向 Codex / Claude Code 的命令入口
- 列出工具、获取上下文、提交执行计划、请求审批、查询执行状态
- Agent 凭 API Token 接入（见 [[Feat013-Auth-登录注册|Auth 模块]]）

**B. MCP Surface（Phase 1 紧随）**
- Resources：project、task、repo、doc-link、integration-state
- Tools：list_tasks、get_task_context、update_task_status、request_execution、run_git_diff、get_context（Layer 4 按需加载）
- Prompts/Templates：面向常见工作流的上下文模板

**C. API / Plugin Surface（Phase 2）**
- 程序化接入与插件扩展机制

**D. Skills Surface（Phase 2/3 演进方向）**
- 高层任务模板：task-executor、code-reviewer、project-operator
- Skills 只声明使用的工具、需要的上下文、产出格式、必须人工确认的步骤
- > Skills 不在 Phase 1 交付，作为 Agent Surface 的演进方向保留

### 2.4 Execution Core（执行核心）

12 个 Feature 模块从"页面功能"重构为"可授权、可审计、可组合的能力"：

- 所有工具输入输出都必须 schema 化
- 所有写操作都必须带 subject、executionRunId、approval 信息
- 所有执行都必须可回放、可审计、可关联到 project/task
- 上下文通过 ContextPack 四层策展结构化提供

| 业务层 | **Task** | 执行载体、任务类型、状态机、依赖、评论 | [[Feat003-Task-任务]] |
| 执行层 | **Execution** | 核心执行对象语义（规格）：ExecutionRun/ApprovalRequest/Step/Artifact/Evidence | [[Feat015-Execution-执行与审批]] |
| 执行层 | **AI Hub** | 执行编排（引擎）、ContextPack 策展、Provider 路由 | [[Feat010-AIHub-人工智能]] |

| 能力层 | **Document** | 项目文档仓库（内容/索引/版本/关联）、ContextPack 知识层数据源 | [[Feat016-Document-文档管理]] |
| 扩展层 | **Plugin** | 扩展机制、Provider/View/Connector/Tool/Hook 扩展点 | [[Feat008-Plugin-插件]] |

> 已降级：CreatePanel（UI 交互模式，归入各模块创建入口）
> 已废弃：Terminal（命令执行能力降级并入 Runtime 作为 Provider Capability）

### 3.3 三条主线

模块体系支撑三条核心主线：

**执行主线**：
```
Execution(规格) → AI Hub(引擎/编排) → Runtime(承载/本地执行) → Task(挂载)
```

**上下文主线**：
```
Project(Layer1) + Task(Layer2) + Git(Layer3) + Document(Layer3) + Integration(Layer3补充)
  → AI Hub(策展) → ContextPackSnapshot(不可篡改) → Agent 执行
```

**治理主线**：
```
Auth(凭证签发) → 审批门(各模块 read/write/high-risk)
  → Notification(触达人类) → Core(审计不可篡改)
```

## 四、核心领域模型

### 4.1 三类主体统一模型

```
Subject（主体）
├── subjectType: human | platform_ai_member | external_agent
├── identitySource: internal | cli | mcp | api | plugin
├── 统一用于：任务分配、执行主体、操作审计、审批责任
```

详见 [[角色级权限模型-v1|角色-等级-权限模型]]。

### 4.2 核心执行对象

> 对象的需求语义由 [[Feat015-Execution-执行与审批|Execution 模块]] 定义，本节为架构层概览。

| 对象 | 说明 |
|------|------|
| `ExecutionRun` | 一次执行实例：9 态状态机、目标、上下文快照、步骤、结果 |
| `ApprovalRequest` | 审批治理节点：5 态状态机、动作级风险分级、多审批门 |
| `ContextPackSnapshot` | 不可篡改的上下文快照（四层策展结果）|
| `ExecutionStep` | 执行步骤记录（计划/上下文读取/工具调用/审批/结果写回）|
| `ExecutionArtifact` | 执行产物（计划、patch、测试报告）|
| `ExecutionEvidence` | 执行证据（diff 摘要、输出摘要、日志片段）|
| `ExecutionOutcome` | 执行结果归纳（是否完成、交付物、未完成项）|

### 4.3 ContextPack 四层策展（差异化核心）

> 这是 APM 对标 Linear 的核心差异化：上下文不再让 Agent 自己抓取，而是分层策展。详见 [[上下文管理设计|上下文管理系统设计]] 与 [[Feat010-AIHub-人工智能|AI Hub 第 7 章]]。

```
┌─────────────────────────────────────────────┐
│  Layer 4 扩展层（Extended）按需加载           │
│  完整文件源码、详细文档（Agent 通过 MCP 拉取）│
├─────────────────────────────────────────────┤
│  Layer 3 知识层（Knowledge）AI 策展           │
│  代码摘要、决策记录、历史执行、外部状态        │
├─────────────────────────────────────────────┤
│  Layer 2 任务层（Task Scope）按类型组装       │
│  任务信息、依赖、约束（bug→复现步骤，feature→需求）│
├─────────────────────────────────────────────┤
│  Layer 1 基础层（Foundation）固定             │
│  项目名片、技术栈、当前迭代、关键约束          │
└─────────────────────────────────────────────┘
```

**数据源分工**：
- Project 提供 Layer 1 数据（`ContextPack.project`）
- Task 提供 Layer 2 数据（`ContextPack.task`）
- Git / Document / Integration 提供 Layer 3 知识层数据
- **AI Hub 负责四层策展**（配方匹配、Token 预算、压缩、快照固化）

### 4.4 v1→v2 迁移要点

- Task 的 `aiExecutionSpec/Result/Status` 字段废弃 → 迁移到独立 `ExecutionRun`
- 主体模型 `ai_employee/temp_agent` → 统一为 `platform_ai_member/external_agent`
- Terminal 独立模块 → 降级为 Runtime 的 Provider Capability
- ContextPack 从「拼接文本」→ 升级为「四层分层策展」

## 五、技术架构

### 5.1 三层运行时

```
┌──────────────────────────────────────────┐
│         Web Control Plane                 │
│    NestJS + React + PostgreSQL            │
│    人类管理界面 + API Gateway + 事件总线   │
└──────────────────┬───────────────────────┘
                   │ WebSocket / REST
┌──────────────────┼───────────────────────┐
│         Local Runtime                      │
│    Runtime Core + Services + Providers    │
│    Provider 层（file/git/terminal/process/ │
│    credentials/cli）+ 审批门禁             │
│    CLI Provider (Codex / Claude Code)     │
└──────────────────┬───────────────────────┘
                   │ IPC
┌──────────────────┼───────────────────────┐
│         Desktop Shell（可选，Phase 2）     │
│    Electron / Tauri 容器                   │
│    本地系统集成 + 体验增强                  │
└──────────────────────────────────────────┘
```

当前阶段采用 **Web + Local Runtime**，Desktop Shell 作为可选容器 Phase 2 集成。

### 5.2 Control Plane（控制面）

技术栈：NestJS + PostgreSQL + React

职责：
- Human Surface 全部界面（仪表盘、任务看板、审批中心、回放）
- API Gateway，统一对外暴露接口
- 数据持久化、审计日志、事件总线
- 成员与权限管理（RBAC）
- ContextPack 策展（AI Hub）

### 5.3 Local Runtime（本地运行时）

四层架构：
- **Runtime Core**：注册、连接、会话、执行编排接收
- **Runtime Services**：工作区管理、执行生命周期、产物证据收集
- **Provider Layer**：file / git / terminal / process / credentials / cli 六类 Provider
- **Platform Adapter**：操作系统适配

通信协议：
- Control Plane ↔ Local Runtime：WebSocket + REST
- Runtime ↔ CLI Provider：stdin/stdout + 结构化协议
- Runtime ↔ MCP Provider：JSON-RPC over stdio

详细架构参见：
- `02-架构设计/architecture/控制平面-本地运行时-v1.md`
- `02-架构设计/architecture/本地运行时模块-v1.md`

## 七、安全与权限模型

### 7.1 AI 权限原则

- 默认"建议 + 待确认"，通过渐进式信任模型逐步放权
- 按工具级别和信任等级动态调整审批策略
- 所有执行必须可回放、可审计
- 信任可渐进提升，但可即时降级

### 7.2 渐进式信任模型（L0-L3）

> 详见 [[渐进式信任模型|渐进式信任模型设计]]。本节为架构层概览。

基于 (Agent × Role × Project) 三维粒度的动态信任体系：

| 信任等级 | 名称 | 审批策略 |
|---------|------|---------|
| **L0 见习** | Probation | 所有操作（含读取）需人工审批 |
| **L1 标准** | Standard | 读取自动放行，写操作需审批 |
| **L2 可信** | Trusted | 低风险写操作自动放行，高风险需审批 |
| **L3 自主** | Autonomous | 仅破坏性操作需审批 |

信任评估由三层来源驱动：自动化指标（代码质量、测试通过率）、AI 辅助评估、人类 PM 评判。支持跨项目经验迁移。

### 7.3 信任等级（L0-L3）与角色等级（Intern~Architect）的映射

> 两套体系正交：**角色等级**定义职责（静态），**信任等级**定义放权程度（动态）。

| 角色等级（职责） | 典型初始信任等级 | 说明 |
|----------------|----------------|------|
| Intern（实习生）| L0 见习 | 以读为主，不直接发起高风险动作 |
| Junior（初级）| L0→L1 | 可在明确边界内发起低风险写操作申请 |
| Intermediate（中级）| L1 标准 | 可承担常规任务闭环 |
| Senior（资深）| L1→L2 | 可处理跨模块复杂任务，更高配额 |
| Lead（主管）| L2 可信 | 可参与方案设计、复杂编排 |
| Architect-grade（架构级）| L2→L3 | 复杂评估与建议，仍不默认免审批 |

映射规则：
- 角色等级由 AI Hub 在 Agent 接入时映射（见 AI Hub 第 8 章）
- 信任等级由渐进式信任模型动态计算（基于执行表现）
- Agent 的实际权限 = 角色等级（职责边界）∩ 信任等级（放权程度）∩ 项目策略
- 所有 Agent 写操作仍受审批门约束（L3 也仅对破坏性操作审批）

### 7.4 权限分层

权限在各模块按 read / write / high-risk 三层分级，冲突取最严格：

| 模块 | read | write | high-risk |
|------|------|-------|-----------|
| Task | task.read | task.write | task.approve |
| Git | git.read | git.write | git.high-risk |
| Runtime（原 Terminal）| runtime.read | runtime.execute | runtime.high-risk |
| Integration | integration.read | integration.write | integration.high-risk |

基础权限模型见 `02-架构设计/策略/角色级权限模型-v1.md`。

## 八、实施路线图

> 与 [[产品需求文档-v2|PRD 第 18 章]] 对齐。

### Phase 1：任务执行闭环（M1-M4）

打通「人类 PM + 外部 AI 工具」围绕任务协作的最小闭环：
