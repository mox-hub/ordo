# Local Runtime 模块拆分草案

## 1. 文档目的

本文件用于定义 Local Runtime 的内部模块边界，避免把 Runtime 直接实现成一个难以维护的单体脚本或单体进程。

重点回答：

1. Runtime 应拆成哪些模块
2. 核心执行逻辑与 Provider 如何解耦
3. Codex / Claude Code 等 CLI 适配应放在哪一层
4. Phase 1 最小实现需要哪些模块

## 2. 设计目标

Local Runtime 的模块拆分必须满足以下目标：

- 让执行层可维护、可测试、可扩展
- 让 Provider 差异下沉
- 让跨平台差异集中在底层适配
- 让未来 Desktop Shell 可以复用 Runtime 核心

## 3. 总体分层

建议 Local Runtime 分成四层：

### 3.1 Runtime Core

负责：

- 注册与连接管理
- 执行编排
- 上下文拉取
- 审批等待与恢复
- 事件回传

### 3.2 Runtime Services

负责：

- 工作区管理
- Provider 调度
- 执行生命周期管理
- Artifact / Evidence 收集

### 3.3 Provider Layer

负责：

- 文件系统
- Git
- Terminal
- Process
- Credentials
- CLI Provider

### 3.4 Platform Adapter Layer

负责：

- HTTP Client
- WebSocket Client
- 协议序列化与反序列化
- 鉴权头与重连策略

## 4. 推荐模块清单

### 4.1 `runtime-core`

职责：

- Runtime 启动入口
- 配置加载
- 连接生命周期管理
- 执行调度总控

不负责：

- 具体 CLI 命令细节
- 具体 Git / 文件实现

### 4.2 `runtime-transport`

职责：

- HTTP 请求封装
- WebSocket 建连
- 心跳与重连
- 事件分发

### 4.3 `runtime-execution`

职责：

- `ExecutionRun` 本地生命周期管理
- 执行状态机
- 审批等待 / 恢复
- 结果与错误归档

### 4.4 `runtime-context`

职责：

- 拉取 `ContextPack`
- 管理上下文缓存
- 向具体 Provider 暴露统一上下文接口

### 4.5 `runtime-workspace`

职责：

- 工作区发现
- 工作区绑定
- 工作区有效性检测
- 路径规范化

### 4.6 `runtime-artifacts`

职责：

- 收集执行产物
- 收集执行证据
- 管理原始输出引用

## 5. Provider 模块建议

### 5.1 `provider-file`

职责：

- 文件读取
- 文件写入
- 目录扫描
- 文件存在性检测

### 5.2 `provider-git`

职责：

- Git 状态读取
- diff 获取
- branch / commit 基础查询
- 高风险写操作封装

### 5.3 `provider-terminal`

职责：

- 终端命令执行
- 输出流采集
- 命令状态管理

### 5.4 `provider-process`

职责：

- 进程创建
- 进程监控
- 进程终止

### 5.5 `provider-credentials`

职责：

- 读取平台允许访问的凭证
- 对 Provider 暴露受控凭证访问

### 5.6 `provider-cli`

职责：

- 定义统一 CLI 抽象
- 负责 Provider 注册和调度

子模块：

- `provider-cli-codex`
- `provider-cli-claude-code`

## 6. CLI Provider 结构建议

### 6.1 `provider-cli`

统一层负责：

- Provider 定义
- 会话接口
- 命令抽象
- 输出归一化
- 错误归一化

### 6.2 `provider-cli-codex`

负责：

- Codex 检测
- Codex 参数适配
- Codex 输出解析
- Codex 错误映射

### 6.3 `provider-cli-claude-code`

负责：

- Claude Code 检测
- Claude Code 参数适配
- Claude Code 输出解析
- Claude Code 错误映射

## 7. 跨平台模块建议

以下模块应优先隔离平台差异：

- `runtime-workspace`
- `provider-file`
- `provider-process`
- `provider-terminal`

原因：

- 路径模型不同
- shell 不同
- 进程模型不同
- 权限模型不同

## 8. Phase 1 最小实现建议

Phase 1 不需要一次性实现完整 Runtime 全貌。

最小必需模块建议：

- `runtime-core`
- `runtime-transport`
- `runtime-execution`
- `runtime-context`
- `runtime-workspace`
- `runtime-artifacts`
- `provider-file`
- `provider-git`
- `provider-terminal`
- `provider-process`
- `provider-cli`
- `provider-cli-codex`
- `provider-cli-claude-code`

Phase 1 可暂缓：

- `provider-credentials` 的复杂实现
- 大量高级 Git 写操作
- 多 Runtime 调度协调

## 9. 模块依赖原则

### 原则 1：Core 不依赖具体 Provider 细节

`runtime-core` 和 `runtime-execution` 只依赖统一接口，不依赖具体 CLI / Git 实现。

### 原则 2：Provider 不反向依赖平台业务

Provider 只关心能力执行，不应直接理解项目业务规则。

### 原则 3：协议与执行解耦

`runtime-transport` 负责通信，`runtime-execution` 负责本地状态机，两者分离。

### 原则 4：Artifact 收集独立

执行产物和执行证据不要散落在各个 Provider 中，应统一归档。

## 10. 与桌面壳的关系

后续如果加入 Desktop Shell：

- Shell 复用 `runtime-core`
- Shell 通过本地桥接方式管理 Runtime 生命周期
- Shell 不应重写 Provider 层
