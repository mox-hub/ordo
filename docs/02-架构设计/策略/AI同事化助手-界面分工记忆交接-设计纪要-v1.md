# AI 同事化助手 —— 界面 · 分工 · 记忆 · 交接 设计纪要 v1

> 日期：2026-09-05
> 性质：头脑风暴纪要 / 设计方向底稿（未实现，代码零改动）
> 关联文档：`渐进式信任模型.md`、`外部AI集成协议-v1.md`、`上下文管理设计.md`、`角色级权限模型-v1.md`、`执行审批模型-v1.md`、`CLI适配器模型-v1.md`
> 范围说明：本文档仅覆盖「AI 同事化助手」本次讨论。对话外的已认可方案（如「季节」等）不在本次记录范围。
> 续篇：`AI同事化助手-项目档案与双用户适配-设计纪要-v2.md`（双用户适配 / 项目档案底座 / 模板与档案管理界面）

## 1. 一句话共识

> 把 AI 从「用户召唤的一块悬浮工具」换成「同事」。统一的命题：**AI 是协作参与者，界面形态按"人与人的协作亲密度"分布**（低声问 → 工位长谈 → 走进办公室 → 开会）。

## 2. 现状盘点（已确认的可用资产）

- **两个入口、同一个面板**：`AssistantColleagueSlot`（侧栏"同事位"，头像+状态+待决数）+ `AssistantFab`（右下圆钮+悬浮窗）。两者都开同一个 `AssistantPanel`。
- **面板是 `fixed z-50` 悬浮**：默认 380×560，放大 ≈ 50vw×50vh，盖在内容上，内容不让位。
- **对话已支持"作用域"切换**：会话 key = `${projectId ?? 'workspace'}::${conversationId}`，消息水合自服务端 UIMessage；已有多会话历史、模型选择、作用域（项目↔全局）切换。
- **面板内职责混杂**：早报（OpeningReport）+ 待决（DecisionStrip）+ 消息流 + 执行行（RunLine）挤在同一滚动区。
- **AI 执行面已通**：cli-dispatch 把消息转派给真实 CLI 执行 Agent（Codex / Claude Code），`ProjectRoleDefinition.promptHint` / `Member.personalPrompt` 已注入派发 prompt。
- **契约工程已实践**：`openapi.json` 一份契约，前端 + apm-shared 双向生成。
- **UI 已全站打 AI 埋点**：`data-ai-component / data-ai-action / data-ai-role` + 前端 `PAGE_REGISTRY`（可作"软件能力"自描述来源）。
- **数据基座已具备**：`Member`（human|ai_agent 统一身份）、`ProjectRoleDefinition`（职能+执行角色）、`MemberToolGrant`（工具白名单）、`MemberActivity`（活动流水）、`Subscription`（订阅）、decisions（阻塞/建议）、executions + AIUsageLog、健康快照。

## 3. 统一心智模型：协作亲密度谱

| 亲密度 | 现实类比 | 界面形态 | 结论 |
|-------|---------|---------|------|
| 耳语 | 指给同事看某处，低声问 | **行内锚点问答（候选 B）** | ✅ 采纳（最认可） |
| 工位长谈 | 和同事就一件事深入 | inspector 同列切换为 AI 长谈 | 🔶 待定形态 |
| 走进办公室 | 看他在干嘛、忙不忙、还能接多少活 | **办公室页（候选 C）** | ✅ 采纳，进短期计划 |
| 开会 | 拉多人辩论一个议题 | **多 Agent 会议室** | 🔶 采纳为远期，需先解"剧场"风险 |
| —— | 一块盖在内容上的玻璃 | 悬浮覆盖窗（候选 A） | ❌ 对象页否决 |

## 4. 候选方案取舍明细

### 候选 A：内容卡内停靠右栏 / 悬浮窗
- 提议：把对话 dock 进内容圆角卡内部，内容 reflow 而非被盖。
- 弃因：任务详情页**已有**页内 inspector（属性+常用操作），再加右栏视觉上叠成 `[主区][inspector][AI]` 三列，冗余又挤。
- 最终结论：**在"有对象、有 inspector"的实体页，A 完全让位给 B + C，不出现**。仅无对象的聚合页（看板/列表/dashboard）可保留可折叠右栏。
- 替代形态（待定）："细聊模式"——同一列 inspector 在 `[属性 ⇄ AI 长谈]` 间**切换**，宽一点、带返回按钮，观感零增量。
- 右下 `AssistantFab`：到 C 落地后应**退役**（同事位+办公室语义完整替代；Fab 只教用户"这有块玻璃"）。可能降级为"非项目页的全局快捷入口"。

### 候选 B：行内锚定问答（用户最爱）
- 理念：低阻碍、不阻断"修改/聊天"的欲望；像 AI IDE 行内问答，快速定位与解决，不被迫单开页面。
- 三个设计要点：
  1. **锚点对象 = 显式上下文**：用户主动"指"给 AI 某个实体（`{kind,id,project}`），服务端精确 grounding；替代现在靠 viewing chip"猜"。
  2. **操作按钮贴着答案**：建议改状态/指派/补执行/起草验收标准 → 点一下就地落库+刷新（invalidateQueries）。"AI 提议、人落库"，改动永远回到领域模型。
  3. **必须有"升级"出口**：每条就地线程尾带"让我细聊 / 进办公室"，线程完整带入，避免浅对话是死胡同（复用 assistantOpenRequest 唤起机制）。
- 提示形态（渐进披露三层，见 §7）。

### 候选 C：办公室页（采纳，短期计划）
- 语义：走进他的办公室 = 先看得见他。首屏是"员工卡"不是输入框：
  - 他在干什么（当前执行/最近会话）
  - 忙不忙（复用 assistant-status 状态机）
  - 压着多少待决（decision strip 的 blocking/advisory）
  - **还能接多少活**（新增：从 execution 在途数、成本配额、信任等级派生的"可接活度"，非假日历）
- 入口就是现成的 `AssistantColleagueSlot`（"门已经有了，屋里是空的，填房间而不是再造门"）。

### 会议室（采纳为远期，需先解决两个问题）
- 闭环价值：跨领域议题 → 多 Agent 各执立场 → 收敛成方案 → 落 decisions 收件箱 → 人拍板 → 转 execution → 验收。
- **剧场风险**：喂同一份 transcript、只换 role prompt 的 LLM 产出相关但同质的观点。解法：制造信息/立场不对称（不同证据子集、专职魔鬼代言人/验证官）。
- **首用例应反转**：纯头脑风暴信息均匀分布、不值得烧 token；会议室黄金用例是**执行后的设计评审/复盘对账/验收会**（各 Worker 握着别人没有的现场信息）。
- 参与者分两类：辩论型（轻量、只发言、便宜）vs 执行型（贵、带工具真实干活）。默认只请辩论型。
- 收敛物 = 结构化提案（方案+风险+归属），不是聊天记录。
- 数据模型建议从当下就为"多参与者会话"留门（把 1:1 同事看成参与者数组=1 的特例）。

## 5. 角色 × Agent 分工

### 现状：两套角色轴（已被确认）
- 权限轴：`ProjectMember.role`（owner/maintainer/member/guest）+ 全局 admin → 给人用的 ACL。
- 职能轴：`ProjectRoleDefinition` = 岗位契约（key/name/**executionRole(coder|reviewer|pm|qa|general)**/**promptHint**/defaultCliProviderId/defaultAssigneeIds）。
- `Member` 把人类与 AI 统一进同一身份空间（type、trustScore、personalPrompt、defaultExecutionRole、costRatePerDay、aiModelConfigId、MemberToolGrant、MemberActivity）。

### 断点（需补的第一个洞）
- 岗位契约（Role）与雇员实例（Member）之间**没有"任职/绑定"关系**——现在靠 `Member.defaultExecutionRole` 游离字符串硬凑，无法表达"谁在哪个项目担哪个岗位"。
- 建议新增概念 **RoleHolding（任职）**：绑定 = Member 持 Role on Project，继承该岗位的 授权边界 + 工件接口 + 执行配置，叠加该雇员实例的 trust/cost/toolGrant → 得到该 AI 在该项目上的完整人格与权限。
- 身份跨项目连续（一个 Member 在 A 项目当 fullstack-dev、B 项目当 reviewer），岗位项目内生效。

### 分工原则（避免把角色当提示词堆料）
1. **授权边界**：coder 能写代码不能自行合并/不能动验收标准；reviewer 只读+审（落 MemberToolGrant + 动作白名单）。
2. **工件接口**：coder 交 diff+自测，qa 交验收报告，reviewer 交"打回/放行+理由"。AI 之间靠**工件**衔接不靠聊天。
3. **闸门依赖 + 信任演进**：trustScore 决定跳过哪些闸（低信任每次过闸，高信任常见变更放行）。
4. **生产与质检分离**：同一 Agent 自审最弱，reviewer 必须是可独立的另一身份。

### 管家（Coordinator/参谋）职责与边界
- 定位：**你私人的 EA，横跨你所有项目**；不是项目职能轴的一顶帽子。
- 职责（按现状核对）：
  - 感知汇报（早报/状态）——已有
  - 提炼待决、挡噪音——已有 decision-strip
  - 订阅实体变化主动提醒——🟡 Subscription 模型在，未成管家主动能力
  - 模糊意图→可执行任务/验收标准——已有 create-suggestion
  - **撮合派活**（意图→合适 worker：谁空/谁够格/谁便宜）——🟡 cli-dispatch 有，"选谁"仍靠人
  - 排期评估——🟡 办公室容量派生量
  - **质询把关**（拍板前顶住、问关键问题）——❌ 几乎没有（"参谋"区别于"传声筒"所在）
- **三不边界**：不做最终批准（闸门在人）；不跨项目授权乱动；不吞执行细节（细节属 worker 工件，只留结论与去重纪要）。

## 6. 让管家"更懂软件"：三个"懂"

| 懂 | 本质 | 机制 |
|----|------|------|
| 懂软件 | 操作知识/能力清单 | 从 UI `data-ai-*` 注解 + PAGE_REGISTRY + docs 自动生成**机器可读能力清单 manifest**（实体状态机/可用动作/入口路径）；被问先查清单再作答；**诚实边界**（不确定就说"我查一下/这步做不到"） |
| 懂现场 | 情境感知 | **情境摘要器**：领域事件（message-bus/ws、MemberActivity、Subscription、健康快照）→ 每用户一张"关注面"（负责的卡/订阅/最近浏览）→ 按相关度排序 |
| 懂你 | 主人档案 | 从浏览/编辑/提问/忽略学偏好；**静默学习**：被忽略 3 次的类别不再提，直到真变紧急 |

- 主动汇报一律是**结构化卡片**（可点、可忽略、可"以后别讲这类"），不是自由文本。
- **先侦查再开口**：答案依赖活数据时，先读一眼健康/待决/执行再作答；每句关于现状的话可溯源。

## 7. 候选 B 提示形式：渐进披露三层 + 规则

- **① 静止态 = 零装饰**：默认页面和今天完全一样，无常驻 AI 标。
- **② hover/聚焦态 = 幽灵暗示**：仅"已知可对话"实体（任务卡/文档块/待决，非每个单元格）从既有动作区滑出低饱和 `✨ 问 AI`，就近不遮内容。
- **③ 进阶可发现性 = IDE 肌肉记忆**：选中正文 → 右键 / Shift+Alt+A "就此内容问 AI"；一次性引导放办公室/同事位。
- 硬规则：
  - **不做主动弹 AI 提示**（Copilot 式内容浮层即"突兀"之源）；主动信号只出现在注意力本来就该去的地方（收件箱/待决/办公室）。
  - 提示 = 承诺要兑现速度：行内直接走流式，答案骨架先出（复用 silent-AI 快捷问答）。
  - 铺开面克制：一页最多几个可对话焦点；连续忽略后幽灵项自动收敛。
  - 就地展开 > 弹层：卡/行用下沉展开行（不遮邻居），密集内容才用指向锚点 popover；Esc 收起、零残留。
  - 交互三要点：① 锚点=显式上下文；② 操作按钮贴答案；③ 必有升级出口（细聊/办公室）。

## 8. 记忆架构（外部可配置模型 → 记忆必须长在应用侧）

### 背景
模型外部、可配置、无状态 ⇒ 记忆是产品一等公民（可版本化/审计/清空/跨模型迁移），不依赖任何供应商能力。

### 铁律
- **真相永远在数据库（事件/状态/执行记录），只有代码能写；模型只读。**
- 模型只允许写三类：偏好、纪要、决策结论；必须带 `sourceEventId`，人类可翻查/推翻/删除。
- 模型永不直接写状态，避免产生第二个会腐烂的真相源。

### 记忆四类（不要混成一个"记忆"）
| 回答什么 | 类型 | 组织 | 模型写？ |
|---------|------|------|---------|
| 软件现在什么状态 | 事实/事件 | 关系库+事件流（已有） | 绝不 |
| 上次怎么解决 X / 为何这决定 | 片段/纪要 | 对话留档+长摘要（vector 可召回） | 自动留档，摘要离线 |
| 用户偏好/关心 | 档案 | 原子记录+置信度+衰减 | 消化器推断后写，人可改 |
| 软件有哪些功能怎么操作 | 能力清单/软件手册 | manifest + 文档索引（版本化） | 开发流程生成 |

### 通用格式：收敛形状（无单一标准）
- 记忆原子通用壳：
```json
{
  "id": "mem_8f3a", "scope": "project:p1", "type": "preference|conclusion|summary|relationship|capability",
  "content": "…", "confidence": 0.8, "refs": ["decision:d-91","task:t42","user:u7"],
  "sourceEventId": "act_…", "lastUsedAt": "…", "hits": 12
}
```
- 质量关键 = 四字段：`scope`(隔离)、`confidence`(别拿低确信当真话)、`sourceEventId`(溯源)、`lastUsedAt/hits`(会腐烂)。
- 会腐烂 > 不错记：长期没被 hit、被行为反证的，置信度下降或归档。
- 本仓库 `.claude` 记忆目录 + CLAUDE.md（原子事实/文件 + frontmatter 元数据 + 索引 + [[链接]]）正是该形状的极简工作实例。

### 三层记忆架构
- **Store A · 事实/事件层**：已有，模型只读；事件流给 SQL 查，给模型的是派生"叙述"。
- **Store B · 长期记忆库（新增重点）**：原子记录；两条查询路径——小量按 scope+type+tag 扫（便宜），模糊回忆走 embedding。写入不在热路径：离线"消化器"批量沉淀/压摘要/更新置信度。
- **Store C · 上下文装配器（模型唯一看到的）**：
  - 系统给：身份 + 能力清单切片 + 档案摘要（很小）+ 现场快照（实时查）
  - 记忆工具：`recall(query, scope)`、`note(fact)`、`whatDoYouKnow(scope)`
  - 换模型零成本（格式与供应商无关）

### 横切四问（需定调）
1. **隔离与隐私**：记忆按 scope（全局 vs 项目）命名空间隔离，跨项目不可见；可一键清空某范围。
2. **召回纪律**：上下文包有 token 预算，先粗后细；**查无结果诚实说没有，绝不编**。
3. **软件记忆谁更新**：能力清单流程自动生成；运维性知识（这部署怎么跑、有哪些坑）需人可写运行手册位，可由自家执行 Agent 沉淀（dogfooding）。
4. **别重复存状态**：凡 DB 能实时查的（健康分/在途执行）只存指针不存值；档案只放"查不到的关系与偏好"，杜绝双写漂移。

## 9. 延伸一：记忆膨胀与整理

- 定调：Store A 涨到多大都没关系（机器真相只给 SQL 查）；会淹死新 AI 的是活跃记忆只增不减 → 问题不在总量在**召回边界没封顶**。
- 治本四板斧：
  1. **召回用梯子（resume 而非 archive）**：
  ```
  L0 现场快照(实时查DB, ~200 tokens) → L1 活跃简历(top-N有上限)
  → L2 滚动纪要(按主题有界) → L3 原始档案(仅显式 recall, 从来自动注入)
  ```
  2. **记忆生命周期**：`working → consolidated → archived(证据可查不注入) → pruned`；触发事件驱动（新事实到阈值/召回噪音变大/里程碑），非纯定时。
  3. **消化器做"升维"整理**：碎片聚类 → 提炼成"规律/结论"记录，碎片降级归档；**去重+归一化**（防不同写法绕晕 AI）。防漂移：摘要带 refs+sourceEventId、冷路径低温度生成、可"钉住"关键记录。
  4. **遗忘是功能**：按类型 TTL、久未 hit 衰减、冲突时新覆盖旧（superseded）；每作用域给"活跃记忆预算"旋钮，超了才整理。
- **handover brief（交接摘要）为一等公民**：每作用域维护一份"最近状态与约定"活文档（早报=日更版）；新连接（换模型/新 worker 首进）先读 brief，不吞历史。

## 10. 延伸二：派发到 CLI 的执行 Agent 也要"记忆"

- 结论：**底层复用同一套 truth store 与检索层，每个"角色"拿不同装配器 + 不同写回策略**。真相共享，视图分角色。Worker 不需要完整用户档案（浪费且泄漏）。
- 分工原则：**"让每个 Agent 读它脚边的地，从外面只喂它看不见的天"**：
  - 脚下：工作 repo 的 CLAUDE.md / docs/architecture —— 厂商本地能力原生可读，标准答案，别重造。
  - 看不见的天：app 平面事实——任务验收标准/阻塞原因/相关决策前因后果/其他 Worker 在途衔接/成本与信任门槛/项目健康。这些由 APM **派发时注入为"任务包"**（现成机制 promptHint/personalPrompt 升级为任务包）。
  - 任务包 = 任务+验收标准 + 相关决策摘录 + 项目约定切片 + 团队活动摘要 + 预算/信任约束。
- Worker 回忆"类似历史任务"：要，但召回 scope 锁在 project/任务类型，不进用户档案。
- **写回闭环**：Worker 不只交代码，还交"取舍/踩坑"增量 → 消化器沉淀项目记忆；Worker 不直接改 app 记忆（防双系统互咬）。
- 隐私：个人偏好档案是"用户↔管家"私产，Worker 只拿任务最小集；trustLevel 兼做"上下文可否给该 Worker 看"的闸。

## 11. AI 同事交接（前后端握手 / 异步协作）

### 定调
- **交接靠"工件+结构化状态机"，不靠聊天**；沟通桥 = 单一契约工件；消息只承载语境。
- 架构区分（关键）：**交接属于"工件/依赖"平面，会议室属于"同步思辨"平面**，两者不混用。
  | 模式 | 何时 | 载体 | 表面 |
  |------|------|------|------|
  | 同步思辨 | "这方案该不该这么做" | 观点/辩论 | 会议室（人主持） |
  | 异步交接 | "请提供这个接口/处理这段" | 工件+状态机 | 任务/依赖+契约 |

### 交接循环（建议落在任务+依赖上带 handoff 元数据，不另起新模块）
```
① 请求方(前端AI) 发起"接口协作卡"：结构化负载(endpoint形状/出处流程/期望进openapi/client/优先级/相关代码/验收口径)
   平台自动：建依赖任务(assign给后端AI成员)+通知
② 接收方(后端AI) 简短可行性侦察(读 spec/代码/上下文包) → 答复：能做(承诺)/有风险/拒绝+理由/需澄清；承诺落库
③ 提供方执行：改 spec → 实现 → 跑契约测试；事件回流：请求方解锁+通知
④ 请求方验证：消费 client/mock 联调 → 契约绿 → 关闭
```
- 每步是事件（进 Store A / MemberActivity / 通知），非聊天记录。

### 平台提供的 agent-facing 工具
- `requestCollaboration(...)` / `checkFeasibility(taskId)` / `respondToRequest(...)` / `verifyAgainstContract(...)`
- `checkFeasibility` 把"现有 spec + 相关代码 + 项目约定 + 对方能力/队列"打包 → 出评估（技术可行 + 容量可行，吃办公室数据）。

### 三根支柱 + 一条信任原则
1. 结构化交接实体（带状态/归属/验收口径，走看板与决策流）。
2. 单一契约工件（接口语言是 diff 不是对话）。
3. **mock/stub 先行解阻塞**：契约敲定后前端对 stub 先干，并行开发不互等。
- 信任原则：**"对话建立理解，工件建立信任。"** 验证靠跑契约测试/消费 mock，不靠对方口头。

### 角色分离防冲突
- spec 单 owner 写：**请求方提案、提供方拥有 spec 的写、请求方消费验证**。两端不会同时编辑同一份 openapi。

### 要堵的三个洞
- **澄清死循环**：轮次上限（如 2 轮），超出自动升级人类 decisions 拍板或按默认执行。
- **成本纪律**：交接默认结构化负载（便宜），仅结构化路走不通才降级自然语言；"能契约说清的不写小作文"写进两端派发约束。
- **容量维度**：后端队列满则请求排队，办公室产能数据可见积压，人据此决定是否加 worker。

## 13. 待定清单（需定夺）

1. B 的首个落地对象：文档段落（贴 IDE 直觉）还是 任务/执行（贴近业务）？
2. "细聊模式"（inspector 同列切换）保留为 A 替代品，还是彻底不要、深聊一律上楼去办公室？

4. 管家能力优先级：先做"质询把关"还是"撮合派活"（决定办公室首版长什么样）？

8. 交接模型：作为"带依赖方向的任务形态"（融入看板）还是独立"协作/交接"模块？

## 14. 建议的短期切片

1. **办公室（短期计划内）**：同事位=门；先做"看得到他在干什么/忙不忙/压着多少待决/还能接多少活"（可接活度为派生量），不急着让每个 Worker 可对话（先"替他看"）。
2. **行内锚点 B 试点**：用"打开项目详情页的情境卡"或"文档/任务"最小场景验证（融合懂现场+懂你+结构化卡片，失败可逆）。
3. **记忆 Store B 原子壳 + 消化器**：先在管家对话结束沉淀"纪要/偏好"（人可改可见），配 recall 工具验证"应用侧记忆+工具拉取"主架构。
4. **交接试点**：把仓库真实发生的"前端要新端点"手工链路（issue→改 openapi→apm-shared→联调）包成"接口协作卡"状态机，让两端 AI 走一遍，人在闸口验收。
