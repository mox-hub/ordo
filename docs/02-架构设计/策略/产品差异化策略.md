# 产品差异化战略

> 本文档定义 Agent Project Manager 的核心竞争力——不是"项目管理工具 + AI 功能"，而是为 AI 参与的项目管理重新设计度量体系、决策流程和 PM 角色。

## 一、核心洞察

### 1.1 市场现状

市面上的项目管理工具结合 AI 的方式停留在表面：
- AI 生成任务描述、总结会议记录、推荐优先级
- 本质上 AI 只是文本生成器，不参与项目执行
- 项目管理流程本身没有因为 AI 的存在而改变

### 1.2 我们的差异化

Agent Project Manager 的核心假设是：**当 AI 成为项目参与者（而非旁观者）时，项目管理的度量单位、规划方式、风险感知和决策逻辑都需要重新设计。**

这不是渐进改良，而是范式转变。

### 1.3 设计原则

1. **双轨并行**：AI 的 token 成本和人类的时间成本同等重要，共同构成项目预算
2. **数据驱动**：任务估算从主观经验转向基于历史执行的客观预测
3. **PM 作为决策者**：PM 不做跟踪和催办，做判断和决策
4. **渐进实现**：核心能力优先落地，前沿能力定位为实验性功能

## 二、差异化层一：双轨成本模型（Dual-Cost Model）

### 2.1 核心概念

Sprint 的规划单位不是单一维度（人天或 token），而是**双轨预算**：

```
Sprint 5 预算:
├─ Token 预算: 500K tokens（约 ¥150）
├─ PM 时间预算: 8 小时（审批和决策）
├─ 人类开发者时间: 20 小时（高复杂度 / 合规任务）
└─ 总预算: ~¥3,500
```

### 2.2 任务成本估算

系统为每个任务提供两种成本估算，PM 根据情况选择执行方式：

```
任务 T-142: 实现 ExecutionService
├─ AI 执行估算:
│   ├─ Token: ~15K (上下文 8K + 执行 5K + 扩展 2K)
│   ├─ 成本: ~¥4.5
│   ├─ 预计耗时: 3 分钟
│   ├─ 成功概率: 82%（基于 Agent C 的历史数据）
│   └─ 人工干预概率: 25%
├─ 人类执行估算:
│   ├─ 工时: 4 小时
│   ├─ 成本: ~¥400（按开发者日薪折算）
│   ├─ 预计耗时: 0.5 工作日
│   └─ 成功概率: 95%
└─ 系统建议: AI 执行（性价比 89×，成功概率可接受）
```

### 2.3 成本预测数据来源

| 数据 | 来源 | 计算方式 |
|------|------|---------|
| Token 消耗 | ExecutionRun.history | 同类型任务的平均 token 消耗 |
| 成功概率 | ExecutionEvaluation + AgentTrustProfile | Agent 在同角色同模块的历史通过率 |
| 人工干预率 | ApprovalRequest | 非 auto_approved 的比例 |
| 人类工时 | Task.estimate | PM 手动填写或系统从历史数据推断 |
| 上下文成本 | ContextPackSnapshot.tokenEstimate | 配方的 token 预算 |

### 2.4 成本维度在 Sprint 规划中的应用

```
Sprint 规划视图:

可用预算:
  Token: 500K / 人类工时: 28h / PM 时间: 8h

待规划任务:
  T-142  AI: 15K token ¥4.5  │  人类: 4h ¥400   │ 建议: AI    │ ✓ 已规划
  T-143  AI: 12K token ¥3.6  │  人类: 3h ¥300   │ 建议: AI    │ ✓ 已规划
  T-150  AI: 不适用          │  人类: 2h ¥200   │ 建议: 人类  │ ✓ 已规划
  T-155  AI: 25K token ¥7.5  │  人类: 8h ¥800   │ 建议: 人类  │ 合规任务
  T-160  AI: 8K token ¥2.4   │  人类: 2h ¥200   │ 建议: AI    │ ✓ 已规划

当前预算使用:
  Token: 35K / 500K (7%)    │  人类: 6h / 28h (21%)
  预计结余: Token 465K + 人类 14h → 可再拉取 3-5 个任务
```

## 三、差异化层二：动态风险感知

### 3.1 核心概念

风险不是 PM 手动标记的静态标签，而是系统基于实时执行数据**持续计算和传播**的动态信号。

### 3.2 四类风险信号

#### 3.2.1 Agent 性能风险

当 Agent 的执行质量出现下降趋势时触发。

**检测逻辑**：
- 最近 5 次执行的平均综合评估分 < 历史平均的 80%
- 最近 3 次执行中出现 2 次以上失败
- 信任分在过去 24 小时内下降超过 10 分

**影响范围**：该 Agent 当前被分配的所有待执行任务 + 该 Agent 在相关模块的未来派发

**系统行为**：
- 自动暂停该 Agent 在受影响模块的任务派发
- 通知 PM，建议人工介入或切换 Agent
- 已在执行中的任务提升监控频率

#### 3.2.2 依赖链风险

当关键路径上的任务出现延迟或质量问题时，风险沿依赖链传播。

**检测逻辑**：
- 关键路径上的任务执行时间 > 预估时间 × 2
- 关键路径上的任务执行质量评估分 < 3.0
- 阻塞任务数 > 3

**影响范围**：下游所有依赖任务

**系统行为**：
- 下游任务风险等级自动提升
- 如果存在并行路径，建议 PM 启动替代路径
- 预估对 Sprint 目标的影响

#### 3.2.3 资源预算风险

当 Token 消耗或人类工时消耗超出预期速率时触发。

**检测逻辑**：
- Token 消耗速率 > 预算线性速率 × 1.3
- Sprint 前半段已消耗 > 60% 的 Token 预算
- 人类工时消耗超出计划

**系统行为**：
- 预警并展示消耗热力图（哪类任务最耗 token）
- 建议节省策略：切换更经济的模型、压缩上下文、减少低价值任务
- 如果无法调整，建议 PM 重新评估 Sprint Scope

#### 3.2.4 质量趋势风险

某类任务或某个模块的整体质量持续走低。

**检测逻辑**：
- 特定模块（如 auth）最近 10 次执行的平均评估分持续下降
- 某类任务（如 bug_fix）的成功率低于历史基准
- 审批拒绝率上升

**系统行为**：
- 标记受影响的模块/任务类型
- 建议调整上下文配方（可能上下文不够充分）
- 建议切换 Agent 或引入人类审查

### 3.3 风险传播

风险不是孤立的——一个信号会沿依赖关系传播：

```
Agent A 在 auth 模块质量下降
    ↓
auth 模块所有进行中任务升级风险
    ↓
依赖 auth 模块的下游任务（T-143, T-155）升级风险
    ↓
如果 T-143 在关键路径上 → Sprint 目标风险升级
```

### 3.4 风险可视化

PM 看到的不是红黄绿灯，而是**实时风险雷达**：

```
风险雷达:
┌──────────────────────────────────────────┐
│ 🔴 高风险 (2)                             │
│ • auth 模块: Agent 质量下降，3 任务受影响  │
│ • 关键路径: T-142 延迟风险传导至 T-160     │
│                                           │
│ 🟡 中风险 (3)                             │
│ • Token 消耗: 当前速率比预估快 18%         │
│ • T-155: 合规任务，建议人类审查            │
│ • Agent B: 新接入项目，尚无信任数据        │
│                                           │
│ 🟢 健康 (6)                               │
│ • 后端模块: 执行通过率 94%                │
│ • Sprint 整体: 健康度 78/100             │
│ • 3 个低风险审批已自动放行                 │
└──────────────────────────────────────────┘
```

### 3.5 数据模型

```prisma

## 四、差异化层三：自动知识传递

### 4.1 核心概念

传统项目中知识传递靠文档和会议。AI 项目中，**每次执行的产出自动结构化存入知识库，后续任务自动检索和注入**。

### 4.2 知识提取

每次 ExecutionRun 完成后，系统自动提取：

| 提取物 | 来源 | 用途 |
|-------|------|------|
| 执行经验 | ExecutionEvaluation.humanNote + AI 评估 | 同类任务的参考建议 |
| 踩坑记录 | ExecutionRun.errorDetail + 解决方式 | 避免重复踩坑 |
| 产出物清单 | ExecutionArtifact | 标记哪些文件/接口被修改 |
| 影响范围 | ExecutionStep 的文件操作记录 | 依赖分析 |
| 上下文有效性 | 上下文配方 + 评估分 | 哪种配方对该类任务最有效 |

### 4.3 知识检索与注入

后续任务启动时，ContextBuilder 的 Layer 3 自动检索：

```
任务 T-160（更新 API 文档）启动
    ↓
ContextBuilder 检索知识库:
├─ 查找同模块（runtime）最近执行记录
│   → T-142 完成 ExecutionService (评分 4.2★)
│   → 关键经验: "先创建 DTO 再实现 Service"
├─ 查找涉及相同文件的执行记录
│   → T-139 设计了 ExecutionRun schema
│   → 产出: schema.prisma 新增了 10 个 v2 Model
└─ 查找同类型任务（doc_writing）的配方效果
    → doc_writing 配方最近 5 次平均评估分 4.0
    → PM 偏好: 包含 API 契约引用
```

### 4.4 知识的生命周期

- **新鲜期**（7 天内）：权重 1.0，优先推荐
- **参考期**（7-30 天）：权重 0.7，仍然相关
- **归档期**（30 天以上）：权重 0.3，仅在被主动检索时出现
- **失效**：关联的代码文件已被大幅修改 → 标记为 stale，不再推荐

### 4.5 与上下文管理系统的联动

知识传递是上下文管理 Layer 3 的核心数据源之一：

```
Layer 3 知识层内容:
├─ 相关代码文件（来自 Runtime 文件索引）     ← 已设计
├─ 相关决策记录（来自 DecisionLog）         ← 已设计
├─ 历史执行参考（来自知识库）               ★ 本节新增
│   ├─ 执行经验（一句话关键经验）
│   ├─ 踩坑记录（避免重复犯错）
│   └─ 产出物变更（接口签名变化等）
└─ 相关文档引用                            ← 已设计
```

## 五、差异化层四：PM 决策驾驶舱

### 5.1 核心概念

PM 的默认视图不是任务看板，而是**项目驾驶舱**——聚合所有信号，只展示需要 PM 注意的事项和系统建议的决策。

### 5.2 驾驶舱四区域

│  ✅ T-142 Agent C 完成 (评分 4.5★)                   │

│  💡 T-143 和 T-144 可并行 → 预计节省 40% 时间        │
│  💡 Agent C 后端任务信任分已达 L3 阈值 → 建议升级     │
│  💡 本 Sprint Token 消耗趋势良好 → 可再拉取 3 个任务  │

```

### 5.3 设计原则

- **注意力稀缺**：PM 的时间是最贵的资源（驾驶舱只展示需要决策的事项）
- **行动导向**：每个通知都附带建议的下一步操作
- **透明可查**：自动处理的操作全部可展开查看细节
- **渐进信任**：PM 对系统的信任来自"自动处理的操作都是对的"

## 六、实验性功能：自适应 Sprint

### 6.1 概念

不固定 Sprint Scope，而是设定目标和预算。系统根据实时执行情况动态调整任务优先级和 Agent 分配。

### 6.2 适用场景

- 购买了固定 Token 额度的团队
- 有明确预算上限的项目
- AI Agent 参与度高（>70% 任务由 AI 执行）的 Sprint

### 6.3 运作逻辑

```
PM 设定 Sprint 目标:
  "完成 v2 后端改造的 ExecutionRun 核心闭环"
  预算: Token 500K + 人类 20h
  成功标准: 8 个核心任务全部 completed + 测试通过

系统自动编排:
  1. 按任务依赖关系和成本估算排序
  2. 将可并行的任务分配给不同 Agent 同时执行
  3. 实时监控执行质量：
     ├─ 质量好 → 拉取更多任务，可能升级 Agent 信任等级
     └─ 质量差 → 缩小 Scope，集中预算在核心任务上
  4. PM 只在系统无法自主决策时介入
```

### 6.4 质量下降处理（当前难点）

当执行质量下降时，系统面临的困境：
- 是 Agent 的问题（需要切换 Agent）？
- 是上下文的问题（需要调整配方）？
- 是任务本身的问题（需要重新拆解）？

**当前策略**（保守）：
- 质量下降时暂停自动派发，通知 PM 介入
- 不尝试自动修复，只做问题检测和诊断

**未来策略**（实验性）：
- 自动尝试切换 Agent
- 自动调整上下文配方（增加 Layer 3 内容）
- 自动降低任务粒度（拆分为更小的子任务）

### 6.5 Feature Flag

通过 `feature:adaptive-sprint` 控制。默认关闭，仅在 PM 明确选择"自适应模式"时启用。

## 七、差异化能力的技术依赖

| 差异化能力 | 依赖的基础设施 | 实现前提 |
|-----------|-------------|---------|
| 双轨成本模型 | ExecutionRun 历史数据 + ExecutionEvaluation | v2 后端改造完成 + 至少 50 次执行记录 |
| 动态风险感知 | AgentTrustProfile + ExecutionEvaluation + TaskDependency | 信任模型上线 + 上下文系统上线 |
| 自动知识传递 | ContextPackSnapshot + ExecutionArtifact + ProjectKnowledgeBase | 上下文管理系统上线 |
| PM 决策驾驶舱 | 以上三者 + 聚合查询层 | 所有基础能力就绪 |
| 自适应 Sprint | 以上四者 + 编排引擎 | 实验性，长期目标 |

### 实施优先级

```
Phase 1（当前）:
  信任模型基础框架 + 上下文管理系统基础
  → 积累 ExecutionRun 数据

Phase 2:
  双轨成本模型 + 基础风险信号
  → PM 能看到成本估算和风险预警

Phase 3:
  自动知识传递 + PM 决策驾驶舱
  → 完整的 PM 体验闭环

Phase 4:
  自适应 Sprint（实验性）
  → 根据数据积累情况决定是否推进
```

## 九、开放问题

1. **成本货币化**：Token 成本是否需要在系统中配置具体的货币换算？还是只显示 token 数量，由 PM 自行换算？
2. **人类工时的自动估算**：是否需要根据任务类型和历史数据自动估算人类工时？还是完全依赖 PM 手动填写？
3. **风险信号的阈值调优**：风险触发的阈值（如"质量下降 20%"）是否需要支持 PM 自定义？
4. **知识库的存储实现**：知识库是用独立的 Prisma 模型（ProjectKnowledgeEntry），还是复用 ExecutionEvaluation + ExecutionArtifact 的组合查询？
