# 需求承接管道（CAP-P-01）设计纪要草案 v0

> **✅ 裁决归档（2026-09-09）：采用方案 C 混合渐进**——一期 AI 预填访谈（剧本骨架 + 静默场景生成访谈答案候选，零新编排层）已开工登记（CAP-P-01 doing，GAP-T-09），二期组合件批卡、三期动态追问随一期验收后推进。裁决记录见 ADR-010。
> 本文档 §一现状盘点与 §二方案取舍继续作为实施基线；§三开放问题在一期内仅需裁决 #1（入口沿用 office 剧本页 InterviewDialog）与 #4（criteria.source 溯源枚举），#2/#6 随二期动工前裁决。
> 依据 [[能力清单-v1]] CAP-P-01（主线，状态 planned）：小白给一句需求 → AI 同事访谈澄清 → 拆解为工程任务 + 生成验收清单（三段式）→ 人确认进 issue 族 + acceptance——管道①②产品化。
> 产出方式：2026-09-09 夜航对 playbook / ai-hub / context / acceptance 四模块的代码级现状勘察 + 既有设计纪要盘点。

## 一、现状盘点

### 1.1 playbook（剧本/访谈向导）——「访谈→工件→闸门→游标」骨架已通

- 内置注册表 `BUILTIN_PLAYBOOKS`（`playbook.registry.ts`）：`software-full-cycle`（六阶段）与 `maintenance-light`（三阶段）；每阶段 = 访谈问题组（人话提问 + hint + 术语对照）+ 产出文档模板 + 闸门卡定义。
- 数据流：`mount` 写 `Project.playbookRef` + `lifecycleStage`（游标）→ 用户在前端访谈 Dialog 填静态表单 → `submitInterview` **确定性转写**为 Document → 建 `DecisionProposal(kind='gate')` 闸门卡（后果预演四段式）→ 人在决策收件箱拍板 → 游标前移（事件派生）。
- **可复用**：整个骨架与 CAP-P-01 形态同构；术语对照、编号机制、后果预演卡全部现成。
- **缺口**：访谈是**静态表单**（问题写死在注册表，无 LLM 参与）；「拆解」阶段只产出文档，闸门确认后**没有 applier 自动建卡**；无「由一句需求自动生成访谈问题」的能力。

### 1.2 ai-hub assistant（会话面）——「拆解 + 落库」的执行手已齐

- 工具目录约 50 个，其中直接相关三件套：`create_task`（支持 parentIssueId 子任务）、`create_acceptance`（criteria 支持 functional/technical + category + weight + severity）、`propose_decision(kind='plan')`（PlanCard，采纳后批量建子任务——决策卡路线图批次①②已落地）。
- 静默 AI 协议（`POST /ai/assistant/silent`）：场景注册表现有五场景（quick-prompts / create-suggestions / project-score / anchor-qa / memory-digest），结构化 JSON 返回、不落消息、AIUsageLog 记账，支持服务端侦查钩子 `prepareContext`。
- **可复用**：工具三件套正好覆盖「拆解 + 验收清单 + 落库提案」；静默场景注册表是「一句话需求 → AI 生成访谈问题清单」的理想挂点（加一个 scenario 即可）。
- **缺口**：assistant **无 playbook 感知**（buildTools 只接 projectId/userId，不知剧本与游标）；无 `mount_playbook` / `submit_interview` 类工具；PlanCard 的 applier 只建子任务，**不生成 acceptance**。

### 1.3 context（上下文策展）——通道在，无「需求承接专用」组装

- 旧 `context.service` 已整体 DEPRECATED；正式接入点是 ai-hub 的 `ContextBuilderService`（项目摘要 / 任务详情 / 近期动态 / DocRegistry 知识摘要，永不装正文），另有 `buildTaskExecutionContext`（含 acceptance criteria + 审计报告注入，供 AI Worker 派发）。
- **可复用**：dispatch/assistant 拿项目上下文的通道已齐。
- **缺口**：访谈/拆解场景拿到的是通用档案简报；剧本阶段产物（调研纪要、需求文档）**不会定向注入**给 assistant。

### 1.4 acceptance + completeness——三段式落库格式与审计门禁现成

- `AcceptanceService.create`：draft 起 + completionType 推断 + criteria 批量建（functional/technical 分层 + category/weight/severity）。
- 完整性审计 red 时 `acceptCompletion` 直接拒绝接收（执行前 Gate，GAP-T-03 测试已补）。
- **可复用**：三段式标准结构、权重/严重度、审计门禁全部现成——「三段式验收清单」无需新设计。
- **缺口**：acceptance 挂在**单个 issue**，无「需求级 acceptance 族」（多任务共享一份验收基准）；criteria 的 `source` 无 `ai-generated-from-interview` 溯源标记。

### 1.5 管道五环节现成度小结

| 环节 | 现有承载物 | 缺口 |
|------|-----------|------|
| ① 访谈澄清 | playbook 静态表单 + InterviewDialog；silent 场景注册表可挂 AI | AI 动态追问无承载；assistant 无剧本工具 |
| ② 拆解 | breakdown 阶段产 Document；create_task / PlanCard 可批量建子任务 | 闸门 accept 后无 applier 自动建卡；拆解与 PlanCard 通道未打通 |
| ③ 验收清单生成 | create_acceptance（functional/technical）；系统完备性清单 | 无「由访谈成功指标生成三段式清单」生成器；无需求级 acceptance 族 |
| ④ 人确认 | 决策收件箱 DecisionProposal(kind=gate) + 后果预演卡（现成） | 卡 payload 需扩展承载「任务族 + 验收清单」组合件 |
| ⑤ 落库 | Document + Issue + Acceptance + Store B 各自通道齐备 | 缺一个事务化编排层把四者串成一次 accept 的原子动作 |

**总体判断：骨架复用度高（闸门卡、游标、工具三件套、审计门禁）；最大空白在「①动态访谈」与「②③⑤的编排/溯源」两处。**

## 二、方案选项与取舍（待裁决）

### 方案 A：剧本承载（Playbook-Native）

把「需求承接」做成注册表新剧本（research→clarify→breakdown→acceptance-draft），访谈问题组由 AI **离线预填**答案候选（仍是静态问题集，人改后提交），沿用现有闸门卡确认，applier 补「建任务族 + 建验收」。

- 优点：复用最大（剧本 DSL / 闸门 / 游标 / 访谈 Dialog 全现成）；无实时 LLM 编排复杂度；审计与信任面最干净（每步确定性可回放）。
- 代价：动态追问弱（问题集预定义，「澄清」深度受限）；新增剧本的表达力受 DSL 约束；「AI 同事感」最弱。
- 适合：先求「管道能用」，体验迭代靠后。

### 方案 B：Assistant-Native（静默场景 + 实时工具编排）

新增静默场景（如 `requirement-intake`）：一句话需求 → AI 生成访谈问题清单 → 用户逐答 → AI 实时调工具三件套组装「任务族 + 验收清单」→ 经扩展的 PlanCard 一次批卡原子落库（新 applier：事务化建 issues + acceptance + 文档）。assistant 增加 playbook 感知（游标/阶段注入上下文）。

- 优点：最接近产品主轴的「AI 同事访谈」体验；动态追问天然支持；静默场景模式现成。
- 代价：工作量最大（编排层、组合件 applier、上下文定向注入、playbook 感知）；ai-hub 已被点名警惕 god module，编排逻辑放进去有架构风险；LLM 实时编排的失败面与成本面都要设计。
- 适合：把主线当产品核心全力投入时。

### 方案 C：混合渐进（三期推进）

1. **一期（AI 预填访谈）**：方案 A 的剧本骨架 + 一个静默场景只做「按需求生成/修订访谈答案候选」，人改后走现有 submitInterview——零新编排层。
2. **二期（组合件提案）**：扩展 PlanCard payload 承载「任务族 + acceptance 清单」，accept 后由最小 applier 事务化落库（复用 assistant 工具的领域逻辑，不放 ai-hub）。
3. **三期（动态访谈）**：静默场景升级为多轮追问（prepareContext 注入剧本阶段产物），访谈 Dialog 换 AI 会话形态。

- 优点：每期独立可验收（一期即可让小白走通管道）；编排层延到三期，ai-hub 压力后置；与 C 线供血判据兼容（assistant 供血 B 线落库）。
- 代价：三期总成本高于 A；一期的「AI 感」仍弱（预填而非对话）。
- 适合：主轴全力但要求每步可回退的节奏。

### 取舍一览

| 维度 | A 剧本承载 | B Assistant-Native | C 混合渐进 |
|------|-----------|--------------------|-----------|
| 首个可用里程碑 | 快 | 慢 | 最快（一期） |
| 动态澄清能力 | 弱 | 强 | 三期后强 |
| 新增编排复杂度 | 低 | 高 | 中（延后） |
| god module 风险 | 无 | 有（ai-hub） | 低（applier 独立） |
| 审计/回放友好 | 最好 | 需设计 | 好 |

## 三、开放问题清单（全部待用户裁决）

1. **交互入口**：访谈放哪——office 剧本页（现 InterviewDialog）/ assistant 侧板 / 项目 init 向导，还是三者皆可达？
2. **需求级 acceptance 族**：一份需求验收基准挂多任务，是新建实体（Requirement/acceptance 族）还是 acceptance 复用 + 关联扩展？触及数据形状，动工前必须裁决。
3. **人确认粒度**：组合件整包一次批卡，还是任务/标准逐项批卡？后者更稳但交互成本高。
4. **溯源标记**：criteria.source 是否增 `ai-generated-from-interview` 一类枚举，供审计区分 AI 代写与人写？
5. **与 requirement-intake skill 的分工**：该 skill 管「功能点治理入口（能力清单账本）」，CAP-P-01 管「工程需求承接管道」——两者边界声明与互相引用方式。
6. **PlanCard 文法扩展**：payload 承载任务族 + 验收清单是否引入新卡型（如 IntakeCard），还是扩展 kind=plan？影响决策卡文法系统。
7. **acceptance 供血对齐**：访谈产出的验收标准进入审计清单（completeness-checklist）比对的口径——按 category 归并还是按来源隔离？
