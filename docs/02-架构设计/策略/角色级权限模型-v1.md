# 角色-等级-权限模型草案

## 1. 文档目的

本文件用于回答五个问题：

1. 系统中有哪些主体
2. 主体承担哪些角色
3. 角色和等级如何组合
4. 权限如何授予与限制
5. 审批边界如何定义

本文件是正式 PRD、执行模型和权限模型的上游文档。

## 2. 主体模型

平台中存在三类核心主体：

### 2.1 人类成员

定义：

- 在平台中长期存在的人类组织成员
- 负责管理、审批、执行、评审、接管等工作

特点：

- 拥有稳定身份
- 可以承担多个角色
- 可以作为审批人、任务 owner、项目 owner

### 2.2 平台内 AI 成员

定义：

- 在平台内部注册、长期存在、可复用的 AI 组织成员

特点：

- 有稳定 identity
- 有角色、等级、默认提示、默认工具策略
- 可以跨任务复用
- 生命周期由平台管理

### 2.3 外部接入 Agent

定义：

- 通过 MCP、CLI、API、Plugin 等方式接入平台的外部 AI 工具或代理实例

特点：

- 身份可能是会话级、连接级或工具级
- 执行能力强依赖外部产品
- 生命周期通常由外部工具决定
- 平台只管理其项目范围、权限和执行审计

## 3. 显式区分原则

平台内 AI 成员和外部接入 Agent 必须显式区分。

### 3.1 区分原因

- 生命周期不同
- 所属关系不同
- 权限授予方式不同
- 审计展示方式不同
- 后续能力成长路径不同

### 3.2 不可混淆的字段

后续模型中应至少显式区分：

- `subjectType`
  - `human`
  - `platform_ai_member`
  - `external_agent`
- `identitySource`
  - `internal`
  - `mcp`
  - `cli`
  - `api`
  - `plugin`

## 4. 角色模型

角色定义“成员承担什么工作”，不定义自治程度。

### 4.1 通用角色清单（首批建议）

- 项目经理
- 项目助理
- 需求分析师
- 前端开发
- 后端开发
- 全栈开发
- 测试工程师
- 架构师
- 发布/运维协作角色

### 4.2 角色职责示例

#### 项目经理
- 创建与维护目标
- 拆解与分配任务
- 审批关键动作
- 控制节奏与风险

#### 项目助理
- 维护任务状态
- 汇总报告
- 跟踪执行进度
- 协助整理上下文

#### 开发角色
- 阅读上下文
- 生成实现计划
- 提交变更建议
- 执行受控代码与工程动作

#### 测试角色
- 生成测试计划
- 分析失败输出
- 维护测试结果与证据

#### 架构角色
- 评估方案
- 分析依赖影响
- 给出架构级建议

## 5. 等级模型

等级定义“可以做到什么程度”，不定义职责范围。

### 5.1 建议等级

- Intern
- Junior
- Intermediate
- Senior
- Lead
- Architect-grade

### 5.2 等级语义

#### Intern
- 以读为主
- 可以生成建议
- 不应直接发起高风险动作

#### Junior
- 可在明确边界内发起低风险写操作申请
- 需要较多审批

#### Intermediate
- 可承担常规任务闭环
- 可在规则内发起多步执行

#### Senior
- 可处理跨模块复杂任务
- 可在更高配额下使用更多工具

#### Lead / Architect-grade
- 可参与方案设计、风险评估、复杂编排
- 仍不代表默认免审批

## 6. 角色与等级正交原则

角色和等级必须分离。

### 6.1 正确建模

例如：

- 角色：后端开发
- 等级：Junior

与：

- 角色：后端开发
- 等级：Senior

共享同一职责模型，但权限、可见范围和审批要求不同。

### 6.2 不推荐建模

不推荐直接做大量组合角色：

- AI前端实习生
- AI后端初级开发
- AI测试资深工程师

这会导致模型膨胀和维护困难。

## 7. 权限模型

权限必须同时由三个维度共同决定：

1. 主体类型
2. 角色
3. 等级

并受项目策略覆盖。

### 7.1 权限层级

建议权限至少分三层：

- `read`
- `write`
- `high-risk`

### 7.2 工具权限示例

#### Task
- `task.read`
- `task.write`
- `task.approve`

#### Project
- `project.read`
- `project.write`

#### Git
- `git.read`
- `git.write`
- `git.high-risk`

#### Terminal
- `terminal.read`
- `terminal.execute`
- `terminal.high-risk`

> 说明：原 Terminal 模块（Feat007）已废弃，命令执行能力降级并入 Runtime（Feat014）。
> 上述权限语义对应 Runtime 执行层：`terminal.read` → `runtime.read`、`terminal.execute` → `runtime.execute`、`terminal.high-risk` → `runtime.high-risk`。
> 权限模型保留 `terminal.*` 命名作为历史兼容，落地时归入 Runtime 执行层治理。

#### Integration
- `integration.read`
- `integration.write`

## 8. 审批模型

审批不是成员等级的替代，而是风险治理手段。

### 8.1 默认原则

- 默认安全模式：`建议 + 待确认`
- 写操作默认进入审批
- 高风险动作必须审批

### 8.2 审批粒度

审批建议按“动作级别”定义，而不是只按角色定义。

例如：

- 更新任务状态：低风险写操作
- 写回任务结果：中风险写操作
- 执行 Git 写操作：高风险动作
- 执行终端危险命令：高风险动作

### 8.3 审批人与等级关系

- Human owner / maintainer 可作为审批人
- AI 成员默认不作为最终审批人
- 后续如果要支持 AI 审批，也必须是显式受限场景

## 9. Phase 1 约束

Phase 1 只先服务：

- 人类项目经理
- 外部 AI 开发工具

因此 Phase 1 中本文件最重要的内容是：

- 如何给外部 Agent 映射角色
- 如何给外部 Agent 限定等级
- 如何给外部 Agent 配置权限包
- 如何让所有写操作进入审批

## 10. MVP 建议映射

### 10.1 Human Surface 首批角色

- 项目经理
- 审批人
- 评审人

### 10.2 外部 Agent 首批角色

- 开发工程师
- 测试工程师
- 项目助理

### 10.3 外部 Agent 首批等级

- Intern
- Junior
- Senior

### 10.4 首批放权建议

#### Intern
- 可读上下文
- 可生成计划
- 不直接发起写操作

#### Junior
- 可发起低风险写操作审批
- 可执行明确边界内任务

#### Senior
- 可处理复杂任务闭环
- 可发起更多动作审批
- 仍不默认跳过审批

## 11. 待确认问题

1. 平台内 AI 成员是否沿用同一角色/等级体系
2. 等级晋升是否完全手动
3. 是否需要项目级自定义角色模板
4. 是否需要按工具单独配置等级阈值
