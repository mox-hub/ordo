# 渐进式信任模型设计

> 本文档定义 Agent Project Manager 的渐进式信任体系——通过角色驱动的评估标准、跨项目经验迁移和动态信任等级，实现从"所有操作需审批"到"高信任 Agent 自主执行"的平滑过渡。

## 一、设计动机

### 1.1 问题

当前审批模型是静态的：所有 AI 写操作默认"建议 + 待确认"。这在 Phase 1 是合理的安全策略，但会产生两个问题：

- **审批疲劳**：PM 需要逐一审批每个操作，随着 Agent 活动增加，审批队列成为瓶颈
- **能力浪费**：已经在项目中证明了自己的 Agent，仍然被当作"新人"对待

### 1.2 目标

- 让 PM 的注意力聚焦在高风险和新模式上，而不是重复审批已知可靠的 Agent
- 让 Agent 通过持续的良好表现逐步获得更高的自主权
- 保持安全底线：信任可以渐进提升，但可以即时降级

### 1.3 设计原则

1. **角色驱动**：不同角色有不同的评估标准（代码质量 vs 文档质量）
2. **渐进提升，即时降级**：升级需要持续证明，降级一次严重事故即可触发
3. **经验可迁移**：Agent 在项目 A 积累的信任，可以折算为项目 B 的初始分
4. **AI 辅助，人类决策**：AI 评估作为参考，PM 掌握最终评判权

## 二、信任粒度与等级

### 2.1 信任的三维粒度

信任的基本单位是三元组：**(Agent × Role × Project)**

- **Agent**：具体的 AI 主体（通过 subjectId 标识）
- **Role**：项目角色（Backend Dev、Frontend Dev、Tech Writer、QA Engineer、DevOps 等）
- **Project**：项目上下文（不同项目的技术栈和约束不同）

这意味着同一个 Agent 在不同项目中、不同角色上的信任度是独立的。

### 2.2 信任等级

| 等级 | 名称 | 信任分范围 | 审批策略 |
|------|------|-----------|---------|
| L0 | 见习（Probation） | 0-20 | 所有操作（含读取）需人工审批 |
| L1 | 标准（Standard） | 21-50 | 读取自动放行，写操作需审批 |
| L2 | 可信（Trusted） | 51-80 | 低风险写操作自动放行，高风险需审批 |
| L3 | 自主（Autonomous） | 81-100 | 仅破坏性操作需审批，其余自动放行 |

### 2.3 信任分计算

底层维护一个连续的信任分（0-100），等级是信任分的区间映射：

```
trustScore = max(0, min(100, baseScore + performanceBonus - penaltyDecay))
```

- **baseScore**：由历史执行成功率驱动
  ```
  baseScore = (successfulExecutions / totalExecutions) × 60
  ```
  最低 10 次执行后开始计算，不足 10 次时 baseScore = 0

- **performanceBonus**：由角色相关的综合评估分驱动
  ```
  performanceBonus = avgCompositeScore × 8
  ```
  avgCompositeScore 是最近 N 次执行的评估综合分（满分 5 分），乘以系数 8 映射到 0-40 分

- **penaltyDecay**：长时间不活跃的轻微衰减
  ```
  penaltyDecay = max(0, weeksInactive × 1.5)
  ```
  超过 2 周无执行记录时开始衰减，每周 -1.5 分，衰减后信任分不低于 baseScore

### 2.4 等级升降规则

**升级条件**（必须同时满足）：

| 升级 | 最低执行次数 | 信任分阈值 | 附加条件 |
|------|------------|-----------|---------|
| L0 → L1 | 3 次成功 | ≥ 21 | 无被拒绝的审批 |
| L1 → L2 | 10 次成功 | ≥ 51 | 最近 10 次通过率 ≥ 80% |
| L2 → L3 | 20 次成功 | ≥ 81 | 最近 20 次通过率 ≥ 90%，综合评估分 ≥ 3.5 |

**降级条件**（任一触发立即生效）：

| 降级 | 触发条件 |
|------|---------|
| L3 → L2 | 信任分跌破 81，或出现一次严重事故 |
| L2 → L1 | 信任分跌破 51 |
| L1 → L0 | 信任分跌破 21，或连续 3 次审批被拒 |
| 任意 → L0 | PM 手动降级（不受规则限制） |

**严重事故定义**：
- 导致构建/部署失败
- 引入安全漏洞
- 破坏性操作导致数据丢失
- PM 在审批中标记为"严重问题"

## 三、跨项目信任迁移

### 3.1 经验折算法

当 Agent 首次以某个角色进入新项目时，系统会查找该 Agent 在其他项目中同角色的信任记录，折算为初始信任分。

**计算公式：**

```
initialScore = L0_BASE + experienceBonus

experienceBonus = maxScoreFromOtherProjects × transferRate × recencyFactor

recencyFactor = max(0.3, 1.0 - monthsInactive × 0.1)
```

参数：

| 参数 | 默认值 | 说明 |
|------|-------|------|
| L0_BASE | 10 | 所有新 Agent 的基础分 |
| transferRate | 0.5 | 跨项目经验折算率 |
| recencyFactor | 1.0（30天内） | 时间衰减因子，每月衰减 0.1，最低 0.3 |

**上限约束**：初始分不超过 `maxScoreFromOtherProjects × 0.7`，即最高只能从 L2 起步。

### 3.2 迁移场景示例

**场景 A：高信任 Agent 进入新项目**
```
Agent 在项目 B 做前端开发，信任分 85（L3），最近活跃
→ initialScore = 10 + 85 × 0.5 × 1.0 = 52.5
→ 上限约束 = 85 × 0.7 = 59.5
→ 最终 = 52.5 → L2（可信）
```

**场景 B：有经验但长期不活跃**
```
Agent 在项目 B 做前端开发，信任分 60（L2），3个月未活动
→ initialScore = 10 + 60 × 0.5 × 0.7 = 31
→ 上限约束 = 60 × 0.7 = 42
→ 最终 = 31 → L1（标准）
```

**场景 C：完全无同角色经验**
```
Agent 从未做过前端开发
→ initialScore = 10 + 0 = 10 → L0（见习）
```

**场景 D：Agent 在多个项目中都有同角色经验**
```
Agent 在项目 B 前端信任分 70，在项目 D 前端信任分 85
→ maxScoreFromOtherProjects = 85
→ initialScore = 10 + 85 × 0.5 × 1.0 = 52.5 → L2
```

### 3.3 无历史数据时的处理

当系统中没有任何同角色的信任记录时，Agent 从 L0 起步。但 PM 可以手动设置初始信任等级（如已知可靠的外部工具），手动设置不受折算规则限制。

## 四、角色驱动的评估体系

### 4.1 评估触发

每次 ExecutionRun 终态（completed / failed）时触发评估。

### 4.2 三层评估来源

#### 第一层：自动化指标（系统采集）

| 角色 | 指标 | 数据来源 | 权重 |
|------|------|---------|------|
| Backend Dev | TypeScript 编译通过率 | ExecutionArtifact（build output） | 20% |
| Backend Dev | 单元测试通过率 | ExecutionArtifact（test result） | 20% |
| Backend Dev | Lint 评分 | ExecutionArtifact（lint output） | 10% |
| Backend Dev | 审批通过率 | ApprovalRequest 统计 | 10% |
| Frontend Dev | 构建成功率 | ExecutionArtifact（build output） | 15% |
| Frontend Dev | 无障碍检查通过率 | ExecutionArtifact（a11y check） | 10% |
| Frontend Dev | Lint 评分 | ExecutionArtifact（lint output） | 10% |
| Frontend Dev | 审批通过率 | ApprovalRequest 统计 | 15% |
| Tech Writer | 文档结构完整性 | 结构化检查 | 10% |
| Tech Writer | 链接有效性 | 链接检查 | 5% |
| QA Engineer | 测试覆盖率变化 | ExecutionArtifact（coverage report） | 20% |
| QA Engineer | Flaky 测试率 | ExecutionArtifact（test result） | 15% |
| QA Engineer | Bug 发现率 | ExecutionArtifact（test result） | 15% |
| DevOps | 部署成功率 | ExecutionArtifact（deploy output） | 25% |
| DevOps | 回滚率 | ExecutionArtifact（deploy output） | 10% |
| 通用 | 执行耗时 vs 预估 | ExecutionRun 时间字段 | 5% |
| 通用 | 人工干预率 | TaskActivity 统计 | 5% |

#### 第二层：AI 辅助评估（可选）

系统使用独立的评估 AI 对执行结果进行质量审查。定位为**辅助参考**，不直接决定信任分。

AI 评估产出：

```typescript
interface AIEvaluationReport {
  score: number;           // 1-5 分
  dimensions: {
    correctness: number;   // 正确性
    completeness: number;  // 完整性
    convention: number;    // 规范性
    efficiency: number;    // 效率
  };
  highlights: string[];    // 做得好的地方
  concerns: string[];      // 需要关注的地方
  suggestedAction: 'approve' | 'review' | 'reject';
}
```

**代码类角色的 AI 评估关注点**：
- 代码是否符合项目约定（读取 coding-standards.md 后对比）
- 是否引入不必要的复杂度
- 边界情况处理是否充分
- 是否有安全隐患

**文档类角色的 AI 评估关注点**：
- 技术描述是否准确
- 是否有遗漏的关键信息
- 格式是否符合项目文档规范

> **实验性功能**：AI 评估结果参与自动审批决策（当 AI 给出高分 + 自动化指标过关时自动放行）作为实验性功能保留，默认关闭，通过 Feature Flag `feature:trust-ai-auto-approve` 控制。

#### 第三层：人类 PM 评判

PM 的评判有两种形式：

**隐式评判**（自动采集，无需 PM 额外操作）：

| 审批结果 | 信任分影响 |
|---------|-----------|
| 通过 | +正面信号 |
| 修改后通过 | 中性偏负（第一版不够好） |
| 拒绝 | -负面信号 |

**显式评判**（PM 主动提供，可选）：

PM 在审批时可以打分（1-5 星）并写评语。这些数据直接纳入信任分计算。显式评判不强制——不提供时使用隐式评判。

### 4.3 各角色的评估权重

| 角色 | 自动化指标 | AI 评估 | 人类评判 |
|------|-----------|--------|---------|
| Backend Dev | 60% | 25% | 15% |
| Frontend Dev | 50% | 30% | 20% |
| Tech Writer | 15% | 35% | 50% |
| QA Engineer | 70% | 15% | 15% |
| DevOps | 40% | 20% | 40% |

### 4.4 综合得分计算

```
compositeScore = automatedScore × autoWeight
               + aiScore × aiWeight
               + humanScore × humanWeight
```

其中：
- `automatedScore`：自动化指标归一化到 1-5 分
- `aiScore`：AI 评估的 score 字段
- `humanScore`：显式打分，或从隐式评判推断（通过=4, 修改后通过=3, 拒绝=1）

## 五、审批策略矩阵

### 5.1 操作风险分类

| 风险级别 | actionType 示例 | 说明 |
|---------|----------------|------|
| read | 查看文件、读取配置 | 只读操作 |
| write_low | 修改文档、添加测试、更新注释 | 低影响写操作 |
| write_high | 修改核心代码、变更 schema、修改依赖 | 高影响写操作 |
| destructive | 删除文件、强制推送、生产部署、数据库迁移 | 破坏性操作 |

### 5.2 策略矩阵

```
trustLevel  | read      | write_low    | write_high   | destructive
------------|-----------|--------------|--------------|------------
L0          | 审批      | 审批         | 审批         | 拒绝
L1          | 自动放行  | 审批         | 审批         | 审批
L2          | 自动放行  | 自动放行     | 审批         | 审批
L3          | 自动放行  | 自动放行     | 自动放行     | 审批
```

### 5.3 策略输出

```typescript
type TrustPolicyResult = {
  action: 'auto_approve' | 'require_approval' | 'blocked';
  reason: string;
  trustLevel: TrustLevel;
  trustScore: number;
};

// 自动放行时仍然创建 ApprovalRequest，但 status 设为 'auto_approved'
// 保持审计完整性
```

## 六、数据模型

### 6.1 新增 Prisma 模型

#### AgentTrustProfile

信任档案，粒度为 (agentId × projectId × role)。

```prisma
model AgentTrustProfile {
  id                    String   @id @default(cuid())
  agentId               String   // subjectId
  projectId             String
  role                  String   // Backend Dev, Frontend Dev, Tech Writer, QA, DevOps...
  trustScore            Float    @default(10)  // 0-100
  trustLevel            String   @default("L0") // L0, L1, L2, L3
  totalExecutions       Int      @default(0)
  successfulExecutions  Int      @default(0)
  rejectedApprovals     Int      @default(0)
  avgEvaluationScore    Float?   // 综合评估分均值（1-5）
  lastEvaluatedAt       DateTime?
  lastExecutionAt       DateTime?
  promotedAt            DateTime?
  demotedAt             DateTime?
  demotionReason        String?
  manuallySetBy         String?  // PM 手动设置时记录
  metadata              Json?

  // 关联
  evaluations           ExecutionEvaluation[]
  trustEvents           TrustEvent[]

  project               Project  @relation(fields: [projectId], references: [id])

  @@unique([agentId, projectId, role])
  @@index([agentId, role])         // 跨项目查询用
  @@index([projectId, trustLevel]) // 按项目查信任等级分布
  @@index([trustScore])
  @@map("agent_trust_profiles")
}
```

#### ExecutionEvaluation

每次执行后的评估记录。

```prisma
model ExecutionEvaluation {
  id                String   @id @default(cuid())
  executionRunId    String   @unique
  projectId         String
  agentId           String
  role              String

  // 三层评估数据
  automatedMetrics  Json?    // 自动化指标详情
  automatedScore    Float?   // 自动化得分（1-5）
  aiEvaluation      Json?    // AI 评估报告
  aiScore           Float?   // AI 评估得分（1-5）
  humanScore        Int?     // PM 打分（1-5，可选）
  humanNote         String?  // PM 评语
  humanJudgmentType String?  // explicit（显式）/ implicit（隐式推断）

  // 综合得分
  compositeScore    Float    // 加权综合分（1-5）

  // 信任分变化记录
  trustScoreBefore  Float
  trustScoreAfter   Float
  trustLevelBefore  String
  trustLevelAfter   String
  levelChanged      Boolean  @default(false)

  evaluatedAt       DateTime @default(now())

  // 关联
  executionRun      ExecutionRun      @relation(fields: [executionRunId], references: [id])
  trustProfile      AgentTrustProfile @relation(fields: [agentId, projectId, role], references: [agentId, projectId, role])

  @@index([agentId, projectId, role])
  @@index([evaluatedAt])
  @@map("execution_evaluations")
}
```

#### TrustEvent

信任等级变化事件，用于审计和通知。

```prisma
model TrustEvent {
  id              String   @id @default(cuid())
  agentId         String
  projectId       String
  role            String
  eventType       String   // promoted, demoted, score_changed, manual_override, migrated
  trustLevelBefore String?
  trustLevelAfter  String?
  trustScoreBefore Float?
  trustScoreAfter  Float?
  reason          String
  triggeredBy     String?  // system / pm:userId / migration
  metadata        Json?

  createdAt       DateTime @default(now())

  trustProfile    AgentTrustProfile @relation(fields: [agentId, projectId, role], references: [agentId, projectId, role])

  @@index([agentId, projectId, role])
  @@index([createdAt])
  @@map("trust_events")
}
```

### 7.3 与现有服务的集成点

#### ApprovalService 改造

```typescript
// 改造前：
async createApproval(data: CreateApprovalData): Promise<ApprovalRequest> {
  return this.prisma.approvalRequest.create({ data: { ...data, status: 'pending' } });
}

// 改造后：
async createApproval(data: CreateApprovalData): Promise<ApprovalRequest> {
  // 先做信任策略判断
  const policy = await this.trustPolicy.evaluatePolicy({
    agentId: data.agentId,
    projectId: data.projectId,
    role: data.role,
    actionType: data.actionType,
    riskLevel: data.riskLevel,
  });

  if (policy.action === 'blocked') {
    throw new ForbiddenException(`Agent trust level insufficient: ${policy.reason}`);
  }

  return this.prisma.approvalRequest.create({
    data: {
      ...data,
      status: policy.action === 'auto_approve' ? 'auto_approved' : 'pending',
      autoApprovedReason: policy.action === 'auto_approve' ? policy.reason : null,
      trustLevelAtRequest: policy.trustLevel,
    },
  });
}
```

## 八、实施路线

### Phase 1：基础信任框架（与 v2 后端改造同步）

**目标**：建立信任模型的基础设施，但不改变现有审批行为。

1. 新增 `AgentTrustProfile`、`ExecutionEvaluation`、`TrustEvent` 三个 Prisma 模型
2. 实现 `TrustEvaluatorService`：评估管道（自动化指标 + AI 辅助 + 人类评判）
3. 实现 `TrustMigrationService`：跨项目信任迁移
4. 订阅 `execution.completed` / `execution.failed` 事件，开始积累信任数据
5. **此阶段所有审批策略仍走 v1 逻辑**（全部需人工审批），信任系统仅"观察学习"

**预计工作量**：12-15h

### Phase 2：策略激活

**目标**：启用基于信任等级的审批策略矩阵。

1. 实现 `TrustPolicyService`：策略矩阵判断
2. 改造 `ApprovalService`：集成 TrustPolicyService
3. Feature Flag 控制：`feature:trust-policy` 默认关闭
4. 开启后，已有足够信任数据的 Agent 按策略矩阵自动处理审批

**预计工作量**：6-8h

### Phase 3：前端展示

**目标**：让 PM 看到 Agent 的信任状态和评估报告。

1. Agent Console 中展示信任等级徽章和信任分趋势图
2. 审批界面展示 AI 辅助评估报告
3. Agent 详情页展示跨项目信任迁移历史
4. PM 可以手动调整信任等级

**预计工作量**：8-10h

## 九、GWT 验收场景

### 场景 1：新 Agent 进入项目

```
Given Agent A 从未在项目 X 中活动
When Agent A 被分配到项目 X 做后端开发
Then 系统查找 Agent A 在其他项目中的后端开发信任记录
  And 根据经验折算法计算初始信任分
  And 创建 AgentTrustProfile 记录
  And 记录 TrustEvent(type: 'migrated')
```

### 场景 2：Agent 通过执行积累信任

```
Given Agent A 在项目 X 中信任等级为 L0
When Agent A 连续完成 3 次成功的后端开发执行
  And 每次执行的评估综合分均 ≥ 3.0
  And 无审批被拒绝
Then 系统自动将 Agent A 升级为 L1
  And 后续读取操作自动放行
  And 发布 TrustEvent(type: 'promoted')
```

### 场景 3：严重事故降级

```
Given Agent A 在项目 X 中信任等级为 L3
When Agent A 的一次执行导致构建失败（严重事故）
Then 系统立即将 Agent A 降级为 L2
  And 发布 TrustEvent(type: 'demoted', reason: '严重事故：构建失败')
  And PM 收到降级通知
```

### 场景 4：PM 手动调整

```
Given Agent A 在项目 X 中信任等级为 L0
When PM 手动将 Agent A 的信任等级设为 L2
Then 系统更新 AgentTrustProfile
  And 记录 manuallySetBy = PM userId
  And 记录 TrustEvent(type: 'manual_override')
```

### 场景 5：AI 辅助评估（实验性）

```
Given Feature Flag 'feature:trust-ai-auto-approve' 已开启
When Agent A（L2）提交一个 write_low 操作
  And 自动化指标全部通过
  And AI 评估得分 ≥ 4.0
Then 系统自动放行该操作
  And 创建 ApprovalRequest(status: 'auto_approved', autoApprovedReason: 'trust_policy_auto')
```

## 十、开放问题

1. **评估 AI 的选型**：用于第二层评估的 AI 模型是否与平台已有的 AI Provider 共用，还是使用独立的评估专用模型？
2. **自动化指标的采集时机**：ExecutionArtifact 的格式目前没有统一规范，需要定义每种角色期望的 artifact 格式（如 build output 的 JSON schema）
3. **衰减策略**：不活跃衰减是否应该按项目维度独立计算，还是全局统一？
4. **多 Agent 协作场景**：如果一个任务由两个 Agent 协作完成，评估结果如何分配到各自的信任分？
