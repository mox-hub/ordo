## 1. 一句话共识

> APM 的定位是**全托管平台**（数据、文档、代码都由平台管理）。因此文档不是"要同步的附件"，而是**平台运行本身依赖的知识层**。三件事是同一件事：**文档内容 = 知识资产；受管注册表 = 资产的账本；AI 快读与平台自用 = 同一本账的两种查询**。所有"双向绑定"问题都应改写成"**分区单一真相源 + 对齐 + 冲突裁决**"，而非两份真相互写。

## 2. 三条铁律（贯穿全部结论）

1. **分区单一真相源**：每份契约、甚至文件里的每一段，只有一个事实拥有者；`docs/` 与 DB 之间做"对齐"，不做无差别双向。
2. **可执行契约**：文档一旦被平台逻辑消费（验收、contract check、changelog、AI prompt），它就从"文档"升级为"配置/代码"，须引入与代码同等的**角色、生命周期与审批门禁**。
3. **对齐以 git 事件为节拍，冲突一律升级人审、绝不静默覆盖**；实时 live-sync 是 merge 风暴根源，排除。

## 3. 核心原则一：按"读者"分两条真相车道

| 车道 | 读者 | 代表文件 | 事实真相 | 对齐节拍 |
|------|------|----------|----------|----------|
| **A 仓库契约** | 仓库外的 AI（codex/claude-code）与开发者 | AGENTS.md / CLAUDE.md / README / CHANGELOG.md | **git 工作树里的文件**（外部 AI 读的是磁盘文件，不是 DB） | git 提交 / PR / 合入边界做 diff 对齐 |
| **B 平台知识** | 平台内部人 + 平台自身 | PRD、架构、决策、docs 知识库 | **DB** | 文件仅作镜像/导入导出 |

推论：车道 A 认"文件为王"，DB 只镜像系统可管理的区块；车道 B 认"DB 为王"。认准这一点后，很多"双向同步"的心病消失——**在车道 A，worktree 文件是为外部工具物化的端口，不是系统中心。**

## 4. 核心原则二：文档信息三层拆分（镜像问题的钥匙）

"DB 富文档 vs 磁盘只能存 markdown"的冲突，根因是把所有信息都塞进同一个正文。正确拆成三层，每层只跟一侧绑定：

| 层 | 内容 | 存在哪 | 绑定强度 |
|----|------|--------|----------|
| **L1 正文** | Markdown 文本（唯一必须逐字节一致的东西） | DB `Document.content` + 磁盘 `.md` body | 强绑定（git 事件对齐） |
| **L2 信封** | 标题 / 稳定 id / 分类 / 标签 / 目录路径 / 状态 / 任务链接 id / 同步指纹(sha+时间戳) | **YAML frontmatter**（随文件走，可移植） | 强绑定 |
| **L3 派生索引与平台态** | 版本链、审批/评审、章节锚点、任务链接关系行、订阅、阅读、权限 | **只存 DB** | **永不进文件** |

- **同步被降维**：只需对"一条规范文本（frontmatter + body）"做 diff（纯文本对齐，git 天然处理），**无任何有损格式转换**。
- **DB 文档与磁盘文件是"由稳定 id + 正文相等性松散耦合的两个不同对象"**：文件身份=路径，DB 文档身份=id 与关系。不追求信息等价镜像。
- **乐观并发直接复用 Linear/Jira 模式**：文件侧 `externalVersion`=最后一次对齐 sha，DB 侧 `localUpdatedAt`（`Issue` 已有这套字段，照搬）。

## 5. 格式选型（DB 与文件用同一套规范序列化）

> DB 和磁盘**不是两套格式互转，而是同一个 `Markdown 正文 + YAML frontmatter` 规范串的两个存放点 + 一份只在 DB 的派生索引。**

- **DB 侧**：`Document.content` 保持 **UTF-8 Markdown（TEXT 列）**；元数据走显式列 + JSON；**列是真相，frontmatter 只是导出/导入时的序列化视图，不双写同一字段**。
- **禁用块级富文本（Notion/Slate/ProseMirror block-JSON AST）作为正文真相**。理由：AI 读写 markdown 可靠、md diff 可 review、零翻译层、全家桶已说 markdown。即便将来要逐块评论/协作光标，AST 也只当**编辑器层临时模型**（parse→edit→serialize），md 永远是持久真相。
- **文件侧布局**：`DocumentFolder` 树 ↔ 目录树 **1:1**（文件夹加稳定 slug）；一篇文档 = 一个 `.md`；文件名取人/AI 可读 slug（中文可行）且**可改名/移动**——DB 关联按 id、不按路径，故不断链；另生成可再生 `docmap.json`（id↔path）供跨文档链接改写。
- **附件/媒体**：放同镜像作用域内 `_assets/` 目录，md 用相对路径引用，DB 只存相对引用，**二进制永不进 content 列**。V1 最简：不上传大图，图片一律指 git 已提交的相对路径。
- **方言固定 + round-trip parser**：CommonMark + GFM 子集 + YAML frontmatter + 一种内部链接写法；parser 解析已知结构、**未知内容原样保留**（仓库内有大量 table/html 混排，必须容忍，否则一导出即毁文件）。

## 6. 契约文件"双向绑定"的落地形态

### 6.1 托管区块 + 自由区共存（lock 的粒度）

锁整份文件是一刀切的错误来源——这类文件部分是系统生成、部分是自由区。正解是 **frontmatter + 系统托管区间 + 自由区**：

```markdown
---
# 系统托管（frontmatter，来自 DB，勿手改）
apm_project_id: "cm..."
name: "APM"
tech_stack: ["nest", "react", "prisma"]
sync_mode: managed        # managed(系统锁定) | synced(可改) | detached(解绑)
---

<!-- BEGIN apm:managed:project-intro -->
APM 是一个 AI 驱动的项目管理工具……
<!-- END apm:managed:project-intro -->

## 开发约定   ← 自由区：人和 AI 随便写，系统永不触碰
```

- 系统只认识 frontmatter + `BEGIN/END apm:managed` 区间，自由区 verbatim 保留（round-trip）。
- 外部改了托管区 → 检出差异 → 提示，或在 git 事件边界还原 + 记冲突升级，**绝不静默覆盖**。

### 6.2 三态 sync_mode 状态机

| 状态 | 含义 | 谁写托管区 |
|------|------|-----------|
| `managed`（锁定） | 系统唯一写入托管区；自由区仍可手动 | 仅系统 |
| `synced`（不锁定） | 允许外部改，靠格式校验提示 + `apm format` 自动格式化 | 系统 + 人（受格式约束） |
| `detached`（解绑） | 系统彻底不碰 | 人 |

### 6.3 统一实体雏形（每个绑定文件一份）

```
ContractFileBinding
  projectId, fileType        # agents | claude_alias | changelog | readme | docs_dir
  filePath / relRootScope    # workspaceRoot 下相对路径；docs 用目录级
  syncMode                   # managed | synced | detached
  managedBlocks              # [{id, marker, source(DB字段), generator}]
  truthOwner                 # file_git(车道A) | system(车道B)
  baseline                   # 上次对齐的文件 sha / git commit
  conflictState / lastWriter # 冲突升级用
  hooks: [{event, pluginId, action}]   # 复用平台事件总线，勿再造 hook 机制
```

### 6.4 内置 hooks / 根目录自动绑定的两个坑

- **别直接塞 `.git/hooks`**（clone 即丢）。git 侧护栏用 `git config core.hooksPath` 指向仓库内托管目录（如 `.apm/githooks/`）做 pre-commit 格式化/校验；系统行为触发走**已有 Plugin 系统 + 事件总线**（`release.created`→再生 changelog；`project.updated`→刷 frontmatter）。
- **"根目录"有多个**：`Project.workspace.localPath`、`Repository.localPath/workspacePath`、`Project.documentsRepoPath`、`CliSession.workspaceRoot` 并存。AGENTS/CLAUDE 必须放 **Agent CLI 实际启动的 workspaceRoot**；文件操作/watch 走**拥有该工作区的 Runtime 节点**（apm 守护进程/MCP 网关）做 fs 代理，**Server 不直连磁盘**。
- **monorepo 冲突**：repo 根只归唯一项目；多项目共仓时把 AI 指令文件降到各自子目录作用域。

## 7. 不同契约文件的差异化策略（收敛后）

| 文件 | 定位 | 真相 | 绑定 |
|------|------|------|------|
| **CHANGELOG.md** | 发版日志 | **派生自 Release 实体**（schema 尚未有，见 §12） | **单向导出**；MD→DB 只支持"严格导入 → 草稿 → 审批落库" |
| **AGENTS.md** | 跨工具 AI 通用指令 | **单一手写真相** | 系统只写托管区；默认 `managed` |
| **CLAUDE.md** | Claude 专属 | **派生别名**（`@import`/指向 AGENTS 的薄文件） | 不允许人手维护，避免漂移 |
| **README** | 对外简介 | 文件 | 简介区字段镜像到托管区 |
| **docs/ 知识库** | 车道 B 文档 | DB | 活体绑定 / 归档镜像（§8） |

- **两个 docs 概念要区分，勿混目录**：
  - **归档镜像**（现有 `DocsGitService`：DB 快照单向 commit 进独立 doc 仓库，作冗余/可移植备份）→ 保留；
  - **活体绑定**（新能力：AI 在项目主仓库 `docs/` 里协作，双向、git 节拍、冲突升级）→ 新建。每项目二选一。
- docs 目录 V1 **砍到"轻量镜像 + 冲突标记"**：支持一次性导入成 Document 树 + 导出，**不做持续双向**（Document 模型有 sections/审批/任务链接等 DB 专属语义，与磁盘 md 非双射，强行双向必丢语义或造巨型引擎）。

## 8. 受管知识注册表 DocRegistry（全托管模型的"账本"）

三种消费面都经由注册表取数，不各自爬目录：

```
                        ┌─ 消费面1：人 → 文档 UI 页
                        │
   受管知识注册表 ───────┼─ 消费面2：AI → subset/digest + 链接（不读全文）
   DocRegistry          │
   （真相/角色/版本/      │
     位置/指纹）   ───────┼─ 消费面3：平台自身 → contract check、
                        │       changelog 生成、验收、dispatch 上下文
                        │
   内容存储（DB Document / 文件）← 从属，不直接面向消费者
```

要点：
1. **注册表是派生索引，永远可重建**——只存稳定 docId、角色、truthOwner、绑定模式、路径/DB 引用、版本、checksum、AI 指纹；**绝不做第二个要人/CI 伺候的清单**。
2. **统一寻址**：文档纳入 shortId（复用 Issue 的 `GlobalSequence` 体系），得到 `apm://{projectCode}/doc/{shortId}` 稳定地址。文件改名/移动不断链（链接指 id，路径只是别名）；AI/代码/页面/验收证据/memory atom 全用同一套地址。**"给 AI 一套完整链接" = 把注册表导出成 catalog**。
3. 收敛现有 `ProjectDocLink.aiIndexed`、`docs-sync-manifest.json` 职责进注册表。

## 9. AI 两条分发通道（Registry 的共同下游）

| 通道 | 载体 | 适用 | 已有种子 |
|------|------|------|----------|
| A. 仓库内文件 | docs 子树物化进 worktree，agent 自取 | codex/claude-code 在仓内、想自己翻 | 根 CLAUDE.md、DocsGitService |
| B. 平台注入 | dispatch 时把 Registry 组装成 ContextPack 塞 prompt | 平台侧 AI、不让 agent 乱翻 | `context/` 模块 + `ContextPackSnapshot` |

两条通道**同源**（都由内容派生），故不会"A 文件改了 B digest 还是旧"。

## 10. 文档角色 × 生命周期（消费决定治理）

**别设计大而全枚举。谁消费它 → 决定真相/锁定/门禁/AI 读取。** 两条正交轴：

- **轴1 内容域**：复用现有 `Document.category`（requirement/design/api/testing/guide/custom），只管"写的是什么"。
- **轴2 治理角色 `docRole`**：一小撮"契约原型"，每个把 `{真相/绑定/门禁/主消费者/AI读取}` 打包。首批 6 个：

| docRole | 典型文档 | 真相 | 默认绑定 | 发布门禁 | 发布后 | 主消费者 | AI 读取 |
|---|---|---|---|---|---|---|---|
| `charter` | AGENTS/CLAUDE.md 入口 | 文件 | managed | 无 | 可继续改 | AI 会话启动、onboarding | 每次入 context 全量 |
| `spec` | PRD / FR 需求 | DB（approved 版） | 文件仅导出镜像 | **必须 approved** | **双版本**：published 冻结 + 新 draft | acceptance、任务模板、FR 编号 | subset/digest 优先；改动不静默 |
| `design` | architecture.md、模块设计 | DB | synced | review | 可改但记变更 | context pack、docs-sync | 结构子集 + 按需全文 |
| `decision` | 决策日志 / ADR | DB | 手写为主 | 无（append-only） | 只追加不改写 | 审计、AI 避重议 | 检索命中即全文 |
| `release-log` | CHANGELOG | **派生自 Release** | 单向导出 | 不需审批 | — | 发版页、审计 | 结构子集 |
| `reference` | guide/api spec | DB | synced | 无 | 随时改 | 人 + AI 检索(aiIndexed) | 检索，不进默认 pack |

- **`provenance: authored | derived` 单列**：derived 文档（release-log、charter 的 frontmatter）不适用 lock/审批，只该"触发重新生成"。
- **生命周期不按角色各造状态机**：共用 `draft→reviewing→published→rejected`，差异收敛成**"角色×门禁规则表"**（`DocumentApproval.version` 已为"审的是哪版"铺路）。
- **`spec` 支持 published 冻结版 + 编辑中 draft 双版本并存**，验收引用"审批时版本"当证据，避免引用漂移。

## 11. subset / digest：懒物化的视图，不是文档属性

- **谁生成**：平台摘要服务（复用 AI 管线，`AIUsageLog` 计量，`createdBy=system:summarizer`）；沿用 MemoryAtom 的**模型产物溯源**（带 sourceChecksum/生成时间，可一键重生成/修正）。digest 是派生物、非手写真相。
- **何时生成——三级触发，绝不做"每存一篇就摘要一篇"**：

| 级别 | 触发 | 成本 |
|---|---|---|
| T0 物化提升 | 文档 `published/approved`、被 acceptance/issue 引用、进 release/里程碑（**开始被消费那刻**） | 一次 |
| T1 按需惰性 | 首次取 subset 无 cache：先返回**廉价结构子集**（元数据+标题+锚点+首段，零 AI 成本），异步排队生成 AI digest 后热替换 | 读延迟≈0 |
| T2 增量失效 | 每文档 `sourceChecksum`，**摘要只在 checksum 变化时重算** | ≈0 |

  配置 `digestPolicy`（`off | on-promote | on-demand | always`，默认 `on-promote + on-demand`）。

- **分层降本**：`leaf digest`（单篇）→ `role/文件夹聚合 digest`（**组合 leaf**，绝不对全量重跑 AI）→ `顶层项目知识索引`（≈ CLAUDE.md 入口，手工指针 + 机器生成的 doc catalog）。读 20 篇 requirement = 20 次 leaf 命中 + 1 次廉价归并。
- **digest 永不装正文**，只装元数据/摘要/关键点/锚点引用；正文永远单真相。freshness 复用 `realtime | cached | stale`。
- **接入点**：`ContextService.buildContextPack()` 的 `collectSources()` 加 `docs` provider（从 Registry 取 catalog + 命中 digest），不新造管线。
- **老库回填 = 一次性后台 job**（batch + 成本估算 + 可中断），非运行时行为。

## 12. 现有资产盘点（可直接复用 / 待补缺口）

可直接复用：
- `Document`/`DocumentFolder`/`DocumentSection`/`DocumentVersion`/`DocumentApproval`（含 version 字段）/`DocumentTaskLink`/`DocumentReviewer` —— 车道 B 存储与审批底座。
- `ImportExportService.generateMarkdown()`（已产 YAML frontmatter）、`parseMarkdown()`（标题/摘要/锚点）。
- `DocsGitService`（DB→git 单向 commit，作为"归档镜像"）。
- `context/` 模块 + `ContextPackSnapshot`（通道 B、digest 接入点）。
- `Issue` 的 `externalVersion/localUpdatedAt` 乐观并发字段模式（冲突检测照抄）。
- `GlobalSequence` + Issue shortId（文档寻址复用）。
- `ProjectDocLink.aiIndexed`、根目录 `docs-sync-manifest.json`/`contract:check`（注册表与契约校验雏形）。
- 根目录 CLAUDE.md / CHANGELOG.md 的 YAML frontmatter（title/id/category/status/version/scope/ai-*）——**AI 文档路由元数据约定**，收敛复用。
- Plugin 系统 + 事件总线（hook 触发）、DecisionProposal / ApprovalRequest（冲突与契约变更升级人审）。

待补缺口：
- **`Release`（版本/发版）实体**——CHANGELOG 真相目前悬空，schema 尚无；由"里程碑收口 + 验收通过 + git tag + 质量门禁"聚合。
- **DocRegistry / DocRole / provenance / docmap 相关 schema 增量**。
- **契约文件 template 引擎**（基于项目画像：`ProjectAIContext` techStack/languages + `ProjectRoleDefinition` 角色 + teamPrompt 注入）。

## 13. 落地分期建议

| 阶段 | 内容 | 出口标准 |
|------|------|----------|
| **一期：契约三件套闭环** | AGENTS.md/CLAUDE.md/CHANGELOG.md 生成 + 托管区 frontmatter 镜像 + `managed` 默认 + `Release` 实体 + CHANGELOG 单向导出 | 建项目自动种出三件套；release 收口自动更新 CHANGELOG.md；改动经 git 对齐 |
