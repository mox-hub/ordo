# 执行与审批模型草案

> **术语注（2026-09-06）**：本文定义的对象模型仍有效；核心实体 `ExecutionRun` 已随 fix/core-model-refactor 重构更名为 `Execution`（Prisma 模型与外部 API 均已翻转），下文出现 ExecutionRun 处一律按 Execution 理解。

## 1. 文档目的

本文件用于定义平台中 AI 参与任务协作时的执行主线。

它重点回答以下问题：

1. 一次 AI 执行在系统中如何被建模
2. 审批请求与执行过程是什么关系
3. 上下文如何提供给执行主体
4. 结果、证据、失败和回放如何落地

本文件是 PRD、接入协议、后续 API 契约和数据模型设计的上游文档。

## 2. 模型定位

平台中 AI 协作的中心对象不是“聊天会话”，而是“执行”。

因此系统应围绕以下核心对象建模：

- `ExecutionRun`
- `ApprovalRequest`
- `ContextPack`
- `ExecutionStep`
- `ExecutionArtifact`
- `ExecutionEvidence`
- `ExecutionOutcome`

## 3. ExecutionRun

### 3.1 定义

`ExecutionRun` 表示某个主体围绕某个任务或目标发起的一次可追踪执行。

它不是单一工具调用，而是一个完整执行实例。

### 3.2 核心语义

每个 `ExecutionRun` 必须回答：

- 谁在执行
- 为了什么目标执行
- 基于什么上下文执行
- 做了哪些步骤
- 哪些步骤需要审批
- 最终产出了什么
- 是否成功、失败、中断或被接管

### 3.3 最小字段建议

- `id`
- `projectId`
- `taskId`
- `subjectType`
- `subjectId`
- `identitySource`
- `goal`
- `role`
- `level`
- `status`
- `contextSnapshotId`
- `startedAt`
- `completedAt`
- `terminatedAt`
- `createdBy`

### 3.4 状态建议

- `draft`
- `planned`
- `in_progress`
- `pending_approval`
- `blocked`
- `completed`
- `failed`
- `cancelled`
- `superseded`

### 3.5 状态设计原则

- `pending_approval` 代表执行被审批门阻塞，而不是整体失败
- `blocked` 表示遇到依赖缺失、工具不可用、上下文不足等阻塞
- `superseded` 表示旧执行被新执行替代，但保留审计价值

## 4. ApprovalRequest

### 4.1 定义

`ApprovalRequest` 表示执行过程中某个动作因为风险级别、权限边界或项目策略而进入待确认状态。

### 4.2 核心语义

审批不是独立流程，而是执行流程中的治理节点。

它必须明确：

- 请求主体是谁
- 依附于哪个 `ExecutionRun`
- 请求执行什么动作
- 为什么需要审批
- 谁有权审批
- 审批结果是什么

### 4.3 最小字段建议

- `id`
- `executionRunId`
- `projectId`
- `taskId`
- `requestedAction`
- `riskLevel`
- `reason`
- `status`
- `approverPolicy`
- `approvedBy`
- `rejectedBy`
- `requestedAt`
- `resolvedAt`
- `resolutionNote`

### 4.4 状态建议

- `pending`
- `approved`
- `rejected`
- `expired`
- `cancelled`

### 4.5 审批设计原则

- 写操作默认进入审批
- 高风险动作必须审批
- 审批应按动作级别定义，不按“成员是谁”一刀切
- 一个 `ExecutionRun` 允许存在多个 `ApprovalRequest`

## 5. ContextPack

### 5.1 定义

`ContextPack` 表示平台为执行主体提供的一组结构化上下文快照。

它不是页面拼接文本，而是执行期可审计的上下文载体。

### 5.2 核心组成

- `project`
- `task`
- `iteration`
- `git`
- `terminal`
- `activity`
- `documents`
- `constraints`

### 5.3 设计原则

- 默认只提供当前执行所需的最小上下文
- 上下文必须可裁剪、可追踪、可回放
- 上下文提供行为本身也应进入审计记录
- 外部 Agent 不依赖前端页面结构获取上下文

## 6. ExecutionStep

### 6.1 定义

`ExecutionStep` 表示一次执行中的可追踪步骤。

每一步可以是：

- 计划生成
- 上下文读取
- 工具调用
- 审批请求
- 结果写回
- 失败记录

### 6.2 最小字段建议

- `id`
- `executionRunId`
- `stepType`
- `toolName`
- `status`
- `startedAt`
- `completedAt`
- `inputSummary`
- `outputSummary`
- `errorSummary`

### 6.3 设计原则

- 步骤日志应偏结构化，不只是一段长文本
- 步骤粒度不应细到每个 token，也不应粗到整个执行只有一条记录
- 审批请求应能关联到触发它的步骤

## 7. Artifact / Evidence / Outcome

### 7.1 ExecutionArtifact

`ExecutionArtifact` 表示执行产出的对象，例如：

- 执行计划
- 代码 patch
- 测试报告
- 风险摘要
- 日报周报

### 7.2 ExecutionEvidence

`ExecutionEvidence` 表示用于支持执行结果的证据，例如：

- Git diff 摘要
- 终端输出摘要
- 测试结果
- 日志片段
- 外部同步结果

### 7.3 ExecutionOutcome

`ExecutionOutcome` 表示一次执行最终的结果归纳，例如：

- 是否完成目标
- 产生了哪些交付物
- 还剩哪些未完成项
- 是否建议继续下一次执行

## 8. Failure / Retry / Takeover

### 8.1 Failure

执行失败必须被明确记录，而不是用一句“失败了”替代。

建议区分：

- 权限失败
- 审批拒绝
- 工具调用失败
- 上下文不足
- 外部依赖失败
- 逻辑失败

### 8.2 Retry

平台应允许在同一任务下创建新的 `ExecutionRun` 作为重试，而不是粗暴复用旧执行。

重试时应保留：

- 原失败原因
- 继承或重建的上下文
- 与上一次执行的关联关系

### 8.3 Takeover

当 AI 执行异常、停滞或需要人工介入时，应支持人类接管。

接管至少应记录：

- 接管人
- 接管时间
- 接管原因
- 原执行状态

## 9. 审计与回放

### 9.1 审计最小要求

每次执行至少应可追溯到：

- `projectId`
- `taskId`
- `executionRunId`
- `subjectType`
- `subjectId`
- `identitySource`
- `approvalRequestIds`

### 9.2 回放目标

回放不是为了重现 token 级细节，而是为了回答：

- 这个执行是怎么开始的
- 期间做了哪些关键步骤
- 哪些动作被审批、批准或拒绝
- 最终产出了什么
- 为什么成功或失败

## 10. Phase 1 约束

Phase 1 只先服务：

- 人类项目经理
- 外部 AI 开发工具

因此 Phase 1 应优先支持：

- 基于任务的 `ExecutionRun`
- 动作级 `ApprovalRequest`
- 任务/项目级 `ContextPack`
- 结果、证据和审计记录

暂不要求 Phase 1 完整支持：

- 跨项目长生命周期执行编排
- 多 Agent 联合作业调度
- 平台内 AI 成员晋升体系联动
