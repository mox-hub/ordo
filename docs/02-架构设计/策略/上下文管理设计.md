# 上下文管理系统设计

> 本文档定义 Agent Project Manager 的上下文策展体系——从"有什么塞什么"升级为"按任务类型精选、分层压缩、按需加载"的智能上下文管理。

## 一、设计目标

| # | 目标 | 衡量标准 |
|---|------|---------|
| G1 | 用户轻松管理和调整上下文 | AI 自动策展覆盖 80-90% 内容，PM 只需微调 |
| G2 | 按任务类型适配上下文 | 不同任务类型有专属配方，内容和深度不同 |
| G3 | 用户可见、AI 可见 | 同一数据源，双视图呈现，PM 和 Agent 各取所需 |
| G4 | 简洁但不损失信息 | Token 预算控制，分层压缩，按需加载 |

## 二、现状与问题

### 2.1 当前实现

`ContextBuilderService`（~270 行）做了以下工作：

- 拼接项目摘要（Project 表字段 → 字符串）
- 拼接任务详情（Task 表字段 → 字符串）
- 拼接最近活动（TaskActivity → 字符串）
- `buildTaskExecutionContext()` 提供结构化版本（JSON），包含任务依赖和 ProjectAIContext

### 2.2 核心问题

| 问题 | 表现 |
|------|------|
| 无分层 | 所有内容平铺在一个 JSON 里，没有优先级 |
| 无适配 | Bug 修复和文档撰写收到相同结构的上下文 |
| 无压缩 | 任务描述全文、活动记录全文，大量 token 浪费 |
| 无交互 | PM 无法查看或调整传给 Agent 的上下文 |
| 无按需加载 | 一次性把所有内容推给 Agent，不能中途拉取更多 |

## 三、分层策展架构

### 3.1 四层上下文结构

```
┌─────────────────────────────────────┐
│  Layer 1: 基础层 (Foundation)        │  始终包含，~200 token
│  项目名片：技术栈、当前迭代、关键约束  │
├─────────────────────────────────────┤
│  Layer 2: 任务层 (Task Scope)        │  按任务类型动态组装，~300-800 token
│  任务信息、依赖、上下文约束            │
├─────────────────────────────────────┤
│  Layer 3: 知识层 (Knowledge)         │  AI 策展，按相关性排序，~500-1500 token
│  相关代码摘要、决策记录、历史执行参考   │
├─────────────────────────────────────┤
│  Layer 4: 扩展层 (Extended)          │  按需加载，Agent 主动请求
│  完整文件源码、详细文档、完整历史       │
└─────────────────────────────────────┘
```

### 3.2 Layer 1 — 基础层

始终包含，无论什么任务类型。内容极精简。

**数据源**：Project 表 + ProjectAIContext 表

**格式（AI 视图）**：
```
## Project
Agent Project Manager | NestJS+React+Prisma+PostgreSQL | Sprint 5
Stack: TypeScript, Prisma 6, NestJS 10, React 19, TailwindCSS
Iteration: 2026-05-15 ~ 2026-05-29 | Progress: 12/20 tasks done
Convention: coding-standards.md | Constraint: AI write ops require approval
```

**字段选择规则**：
- 项目名、描述（≤50字）
- 技术栈关键词（不超过 8 个）
- 当前迭代时间窗口和进度
- 1-2 条最关键的约束或规范引用

### 3.3 Layer 2 — 任务层

围绕当前任务展开，内容根据任务类型动态调整。

**数据源**：Task 表 + TaskDependency + TaskTag + ParentTask

**通用字段**（所有任务类型都包含）：
- 任务标题、描述（摘要而非全文）
- 状态、优先级、指派人
- 依赖任务（仅 ID + 标题 + 状态）
- 阻塞任务（仅 ID + 标题 + 状态）
- 标签

**按任务类型的附加内容**：

| 任务类型 | 附加内容 | 来源 |
|---------|---------|------|
| Bug 修复 | 错误描述、复现步骤、影响范围、错误日志片段 | Task.description + ExecutionArtifact |
| 功能开发 | 需求文档引用、API 契约引用、设计文档引用 | Task.metadata + 关联文档 |
| 代码审查 | 待审查 diff（精简版）、变更文件列表 | Git 集成 |
| 文档撰写 | 文档目标、受众定义、现有文档大纲 | Task.metadata + 文档仓库扫描 |
| 测试编写 | 测试目标、被测代码摘要、覆盖率要求 | Task.metadata + 代码索引 |
| 重构 | 重构目标、影响范围声明、约束条件 | Task.metadata + 依赖分析 |

### 3.4 Layer 3 — 知识层

由 AI 自动策展，按相关性排序。这是省 token 的关键层。

**内容类型**：

1. **相关代码文件**（来自 Runtime 文件索引）
   ```
   - src/modules/runtime/runtime.service.ts (744L, rel:0.92)
     Runtime registration, dispatch, approval. All state in appConfig JSON.
   - src/core/database/prisma.service.ts (45L, rel:0.71)
     Database connection singleton.
   ```

2. **相关决策记录**（来自 DecisionLog）
   ```
   - [ADR-003] Prisma chosen over TypeORM (2026-02-15)
   - [ADR-007] AI execution uses approval gate pattern (2026-03-01)
   ```

3. **历史执行参考**（来自 ExecutionEvaluation）
   ```
   - exec_abc123 "Create TaskService" (3d ago, 4.2★)
     Key learning: Create DTOs before implementing Service
   ```

4. **相关文档引用**（来自项目文档索引）
   ```
   - docs/meta/v2-后端重构计划.md (530L)
     v1→v2 migration: 9 steps, ~26h estimate
   ```

**压缩策略**：

| 压缩级别 | 格式 | 适用场景 | Token 节省 |
|---------|------|---------|-----------|
| full | 完整内容 | 任务描述、编码约束 | 0% |
| summary | 一句话摘要 + 元信息 | 代码文件、文档 | ~80% |
| reference | 仅路径/ID + 相关性分数 | 低相关性文件、远历史 | ~95% |

### 3.5 Layer 4 — 扩展层

不默认包含，Agent 通过 MCP Tool 按需请求。

**MCP Tool 定义**：

```typescript
// Tool: get_context
{
  name: "get_context",
  description: "Request extended context for current execution",
  inputSchema: {
    type: "object",
    properties: {
      target: {
        type: "string",
        description: "What to retrieve",
        enum: ["file_content", "file_tree", "doc_content", "execution_detail", "decision_detail"]
      },
      ref: {
        type: "string",
        description: "Reference identifier (file path, doc ID, execution ID, decision ID)"
      },
      range: {
        type: "object",
        description: "Optional range for file content",
        properties: {
          startLine: { type: "integer" },
          endLine: { type: "integer" }
        }
      }
    },
    required: ["target", "ref"]
  }
}
```

Agent 在执行过程中需要更多上下文时，调用此 Tool。Runtime 收到请求后：
1. 从本地文件系统读取内容（文件类）
2. 从 Control Plane API 查询内容（文档、决策、执行记录类）
3. 返回给 Agent

**优先通过 MCP 支持此能力**。后续可扩展为 CLI 命令或 API 端点。

## 四、上下文配方（Context Recipe）

### 4.1 配方概念

每种任务类型对应一个配方，定义四层中各包含什么内容、压缩到什么程度、token 预算是多少。

### 4.2 预定义配方

| 配方 | Token 预算 | Layer 2 重点 | Layer 3 重点 |
|------|-----------|-------------|-------------|
| bug_fix | 1500 | 错误描述 + 复现步骤 + 日志 | 相关代码文件（summary）+ 最近修改 |
| feature | 2500 | 需求 + API 契约 + 设计引用 | 相关模块代码（summary）+ 编码规范 + 类似功能历史 |
| code_review | 2000 | Diff + 变更文件列表 | 编码规范 + 项目约定 + 相关测试 |
| doc_writing | 1000 | 文档目标 + 受众 + 现有结构 | 相关技术文档 + 术语表 |
| testing | 1500 | 测试目标 + 被测代码摘要 | 测试框架约定 + 现有测试模式 |
| refactor | 3000 | 重构目标 + 影响范围 + 约束 | 被重构代码完整摘要 + 依赖图 + 历史重构经验 |
| default | 2000 | 任务基础信息 | 按相关性自动选择 |

### 4.3 配方匹配逻辑

```
1. 检查任务标签中是否包含配方关键词（bug, feature, refactor...）
2. 检查任务 metadata 中是否有 taskType 字段
3. 检查父任务的类型
4. 匹配失败则使用 default 配方
```

PM 可以手动为任务指定配方（覆盖自动匹配）。

### 4.4 自定义配方

PM 可以创建自定义配方，保存后可复用。自定义配方存储在 `ContextRecipe` 表中。

## 五、策展流程

### 5.1 完整流程

```
任务分配给 Agent
    ↓
Step 1: 匹配配方（根据任务类型自动匹配或 PM 手动指定）
    ↓
Step 2: 采集候选内容
    ├─ Layer 1: 从 Project + ProjectAIContext 采集（固定逻辑）
    ├─ Layer 2: 从 Task + Dependency + Tag 采集（按配方规则）
    ├─ Layer 3: 从多个源采集候选
    │   ├─ Runtime 文件索引 → 相关代码文件
    │   ├─ DecisionLog → 相关决策
    │   ├─ ExecutionEvaluation → 历史执行参考
    │   └─ 文档索引 → 相关文档
    └─ Layer 4: 生成可扩展资源列表（仅引用，不加载内容）
    ↓
Step 3: 相关性排序与压缩
    ├─ 对 Layer 3 候选项做相关性打分（0-1）
    ├─ 按分数排序
    ├─ 按 token 预算截断
    └─ 对每项内容应用压缩策略（full / summary / reference）
    ↓
Step 4: 组装上下文包
    ├─ 创建 ContextPackSnapshot 记录
    ├─ 为每个内容项创建 ContextItem 记录
    └─ 计算 token 估算总量
    ↓
Step 5: PM 审阅（可选）
    ├─ PM 查看人类视图
    ├─ 调整内容（增/删/改压缩级别）
    └─ 确认后锁定上下文包
    ↓
Step 6: 渲染并传递
    ├─ AI 视图 → 通过 MCP/CLI 传递给 Agent
    └─ 人类视图 → 在 Web UI 的执行详情页展示
    ↓
Step 7: 执行中按需扩展
    └─ Agent 调用 get_context Tool → 拉取 Layer 4 资源
```

### 5.2 相关性打分算法

Layer 3 内容的相关性打分考虑四个因素：

```typescript
relevanceScore =
  keywordOverlap * 0.3     // 任务描述与文件内容的关键词重叠度
  + gitRecency * 0.2       // 文件最近被修改的时效性
  + executionHistory * 0.3 // 类似任务的历史执行是否引用过此文件
  + pathProximity * 0.2    // 文件路径与任务涉及模块的距离
```

**keywordOverlap**：提取任务描述中的技术关键词，与文件路径、文件中的符号名做匹配。

**gitRecency**：最近 7 天内修改过的文件权重 1.0，每超过 7 天衰减 0.2，最低 0.2。

**executionHistory**：查找与当前任务标签/类型相同的历史 ExecutionRun，统计各文件被引用的频率。

**pathProximity**：如果任务 metadata 中指定了涉及模块（如 `modules/runtime`），该路径下的文件权重 1.0，相邻路径 0.7，更远路径 0.3。

## 七、Token 预算管理

### 7.1 预算计算

```typescript
calculateBudget(params: {
  recipe: ContextRecipe;
  trustLevel: TrustLevel;
  taskComplexity: number; // 依赖数 + 涉及模块数
}): number {
  let budget = recipe.tokenBudget; // 配方基础预算

  // 信任等级加成：高信任 Agent 承担更复杂任务，需要更多上下文
  const trustMultiplier = { L0: 1.0, L1: 1.2, L2: 1.5, L3: 2.0 };
  budget *= trustMultiplier[params.trustLevel];

  // 复杂度微调
  if (params.taskComplexity > 5) budget -= 200;
  if (params.taskComplexity > 10) budget -= 300;

  return Math.round(budget);
}
```

### 7.2 预算分配

四层的默认 token 分配：

| 层 | 占比 | 说明 |
|---|------|------|
| Layer 1 基础层 | 8-10% | 固定内容，约 200 token |
| Layer 2 任务层 | 20-30% | 任务核心信息 |
| Layer 3 知识层 | 40-60% | 主要弹性空间 |
| Layer 4 扩展层 | 0%（预留预算外） | 不计入预算，按需加载 |

### 7.3 超预算处理

策展结果超出预算时，按以下顺序压缩：

1. Layer 3 中相关性最低的内容项降级为 reference
2. Layer 3 中剩余 reference 项移除
3. Layer 2 的附加内容降级为 summary
4. 如果仍超预算，Layer 3 的 summary 项逐个移除（从最低相关性开始）

## 八、Runtime 代码索引

### 8.1 定位

代码文件索引是 Runtime 的一个 Capability，不是桌面壳的独有功能。

桌面壳（Electron，ADR-014）是 Runtime 的打包和分发方式之一（提供系统集成、自动更新等桌面体验），但代码索引功能不绑定桌面壳——用户通过 CLI 启动 Runtime 也能获得代码索引。

### 8.2 索引构建流程

```
Runtime 启动 / 检测到文件变更
    ↓
扫描 workspaceRoots 下的项目文件
    ↓
构建轻量索引（增量扫描，仅处理变更文件）
    ├─ 文件路径
    ├─ 文件大小、最后修改时间
    ├─ 语言类型（从后缀推断）
    ├─ 导入关系（TypeScript import、Python import 语句级）
    └─ 符号索引（类名、函数名、常量名，正则提取）
    ↓
通过 runtime.capability.update 事件上报 Control Plane
    ↓
Control Plane 存储索引摘要到 RuntimeCapabilitySnapshot
    ↓
ContextBuilder 使用索引摘要做 Layer 3 的文件相关性打分
    ↓
Agent 需要完整文件内容时，通过 MCP Tool get_context 按需拉取
```

### 8.3 索引数据结构

```typescript
interface FileIndex {
  path: string;             // 相对于 workspaceRoot 的路径
  language: string;         // typescript, python, rust, etc.
  size: number;             // 字节数
  lastModified: string;     // ISO timestamp
  lineCount: number;        // 行数
  symbols: string[];        // 导出的符号名
  imports: string[];        // 导入的模块路径
  directory: string;        // 所属目录（用于路径距离计算）
}

interface CodeIndexReport {
  workspaceRoot: string;
  totalFiles: number;
  indexedFiles: number;
  indexVersion: string;     // 递增版本号，用于增量更新
  files: FileIndex[];
  generatedAt: string;
}
```

### 8.4 索引与上下文的交互

```
ContextBuilder 需要 Layer 3 代码文件
    ↓
查询 RuntimeCapabilitySnapshot 中最新的文件索引
    ↓
用相关性算法对文件打分排序
    ↓
选取 top-N 文件（在 token 预算内）
    ↓
每个文件生成 summary 压缩内容：
  - 路径 + 行数（来自索引）
  - 一句话摘要（来自最近一次 AI 评估或文件头部注释）
    ↓
Agent 需要完整内容时通过 MCP get_context("file_content", path) 拉取
```

## 九、数据模型

### 9.1 新增模型

#### ContextRecipe — 上下文配方

```prisma
model ContextRecipe {
  id              String   @id @default(cuid())
  taskType        String   @unique  // bug_fix, feature, code_review, doc_writing, testing, refactor, default
  name            String
  description     String
  tokenBudget     Int      @default(2000)
  layerConfig     Json     // 四层配置：每层包含的源、压缩策略、权重
  isActive        Boolean  @default(true)
  isSystem        Boolean  @default(false)  // 系统预定义 vs PM 自定义
  createdBy       String?
  createdAt       DateTime @default(now())
  updatedAt       DateTime @updatedAt

  @@map("context_recipes")
}
```

**layerConfig 结构示例**：
```json
{
  "foundation": { "sources": ["project", "tech_stack", "convention"] },
  "task": {
    "sources": ["task_basic", "dependencies", "description"],
    "extras_by_type": {
      "bug_fix": ["error_log", "reproduce_steps"],
      "feature": ["api_contract", "design_doc_ref"]
    }
  },
  "knowledge": {
    "sources": ["code_files", "decisions", "execution_history", "docs"],
    "compression": { "code_files": "summary", "decisions": "summary", "docs": "reference" },
    "max_items": 10
  },
  "extended": { "on_demand_only": true }
}
```

#### ContextItem — 上下文内容项

```prisma
model ContextItem {
  id                String   @id @default(cuid())
  snapshotId        String
  layer             String   // foundation / task / knowledge / extended
  sourceType        String   // task_field / code_file / decision / execution_history / document / git_ref / error_log
  sourceRef         String   // 引用标识（文件路径、决策 ID、执行 ID 等）
  relevanceScore    Float    @default(0)  // 相关性得分 0-1
  compressionLevel  String   @default("summary")  // full / summary / reference
  content           Json     // 结构化内容
  tokenEstimate     Int      @default(0)  // 预估 token 数
  manuallyAdded     Boolean  @default(false)
  manuallyRemoved   Boolean  @default(false)
  sortOrder         Int      @default(0)

  snapshot          ContextPackSnapshot @relation(fields: [snapshotId], references: [id])

  @@index([snapshotId, layer])
  @@index([sourceType, sourceRef])
  @@map("context_items")
}
```

```typescript
// Runtime MCP Tool 注册
{
  name: "get_context",
  description: "Request extended context for current execution",
  handler: async (params) => {
    switch (params.target) {

        return runtime.readFile(params.ref, params.range);
      case "file_tree":
        return runtime.getFileTree(params.ref);
```

## 十一、与信任模型的联动

| 联动点 | 说明 |
|-------|------|
| Token 预算加成 | L0 ×1.0 → L3 ×2.0，高信任 Agent 获得更充分的上下文 |
| 知识层精度 | 高信任 Agent 历史执行更丰富，Layer 3 的历史参考更精准 |
| 评估反馈 | ExecutionEvaluation 的结果反馈到上下文策展：高评分的执行所用的上下文配方权重提升 |
| 自动策展学习 | PM 调整上下文的比例越低，说明自动策展越准确，策展置信度越高 |

## 十二、PM 调整与偏好学习

### 12.1 Phase 1：独立调整

每次 PM 调整上下文都是独立的，不形成偏好规则。但调整行为会被记录：

```typescript
interface CurationAdjustment {
  snapshotId: string;
  adjustments: Array<{
    action: "added" | "removed" | "compression_changed";
    itemId?: string;
    sourceType: string;
    sourceRef: string;
    fromCompression?: string;
    toCompression?: string;
  }>;
  adjustedBy: string;  // PM userId
  adjustedAt: Date;
}
```

### 12.2 Phase 2：偏好规则（实验性）

当积累足够多的调整记录后，系统自动提取偏好模式：

- PM 倾向于添加某类文档（如 API 契约）
- PM 倾向于移除某类内容（如过旧的决策记录）
- PM 倾向于把某类代码文件从 summary 升级为 full

提取的偏好规则存储为配方覆盖项，应用于后续自动策展。

通过 Feature Flag `feature:context-preference-learning` 控制。

## 十四、GWT 验收场景

### 场景 1：Bug 修复任务的上下文策展

```
Given 项目中存在 Bug 修复任务 #T-200，标签包含 "bug"

Then 系统自动匹配 bug_fix 配方
  And Layer 2 包含错误描述和复现步骤
  And Layer 3 包含相关代码文件摘要（按相关性排序）
  And Token 总量控制在 1500 以内
```

### 场景 2：PM 调整上下文

```
Given 系统为任务 #T-142 自动策展了上下文包
When PM 查看人类视图并移除一个低相关性的代码文件
  And PM 添加一个系统未选中的文档
  And PM 将某文件从 summary 升级为 full
Then 系统更新 ContextItem 记录
  And 重新计算 token 估算
  And PM 锁定后上下文包不可再修改
```

### 场景 3：Agent 按需拉取扩展上下文

```

Then Runtime 从本地文件系统读取文件内容
  And 返回给 Agent
  And 记录到 ContextItem（Layer 4, compression: full）
```

```
Given Agent A 在项目 X 中信任等级为 L3
When 系统为 Agent A 的任务策展上下文
Then Token 预算 = 配方基础 × 2.0（L3 加成）
  And 知识层包含更丰富的历史执行参考
```
