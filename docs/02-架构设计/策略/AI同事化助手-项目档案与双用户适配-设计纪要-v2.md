# AI 同事化助手 —— 项目档案与双用户适配 设计纪要 v2

> 日期：2026-09-07
> 性质：头脑风暴纪要 / 设计方向底稿（未实现，代码零改动）
> 前篇：`AI同事化助手-界面分工记忆交接-设计纪要-v1.md`（界面谱系 / 角色分工 / 记忆架构 / 交接机制，本文直接引用不重复）
> 关联文档：`产品需求文档-v3.md` §8 工程完备性清单、`渐进式信任模型.md`、`上下文管理设计.md`、`执行审批模型-v1.md`
> 范围说明：本文覆盖三次连续讨论——①双类用户适配（新手全流程托管 / 老手半途导入）；②项目档案底座（简报的去腐化设计）；③模板与档案的管理界面。对话外的已认可方案不在记录范围。

## 1. 一句话共识

> 新手要的是「AI 懂专业并且教我」，老手要的是「AI 懂我的项目并且不烦我」。**两者不是两套功能，而是同一个系统的两个端点**：前端靠档位与教学夹层区分，后端收敛到同一套决策卡、同一份项目简报、同一个办公室。

## 2. 双用户适配：三个统一机制

两类目标用户：①对项目管理零基础的新手——需要 AI 全流程托管（需求调研 → 分析 → 设计 → 拆解 → 执行 → 验收），并把知识点掰开揉碎，让用户在理解中做判断；②有项目/开发经验、带半途项目入库维护的老手——需要 AI 先懂项目再克制协航。真实世界更复杂：新手会成长；老手也会在自己不熟的领域当新手（资深开发者面对验收标准可能是小白）；同一个项目可能同时有这两类人。因此**不建模"两种用户"，建模一个可演化的维度**。

### 2.1 机制一：专长度是向量，不是二分类

- 按 **人 × 领域** 记录专长度（项目管理 / 技术实现 / 验收测试 / 成本预算……），不是一个全局"新手/老手"开关。
- **不靠问卷标注，靠行为静默学习**：知识层被折叠忽略 3 次 → 该领域密度自动下降（复用 v1 §6"被忽略 3 次不再提"规则）；用户主动追问概念 → 密度回升。
- 随时可手动纠偏：知识卡上留"我已了解，别再解释这类"按钮，直写偏好原子。
- 档位按**人**存、不按项目存——同一张决策卡对不同人渲染不同夹层，天然解决"新手项目 + 老手协作者"混场。

### 2.2 机制二：决策卡是唯一统一载体，知识层是可折叠夹层

在 v1 §4-B"操作按钮贴着答案"的基础上，知识态决策卡为四段式：

| 层 | 内容 |
|----|------|
| 提案 | AI 推荐什么（默认高亮，可一键采纳——保住低摩擦拍板） |
| 理由 | 为什么推荐它，而不是别的 |
| 知识夹层 | "验收标准是什么？为什么这步不能省？"——可折叠，链接知识原子 |
| 后果预演 | "如果你选 B，后面会发生什么" |

硬约束：知识夹层**永远不主动弹开**（沿用 v1 §7"不做主动弹 AI 提示"）；**学习发生在决策现场**（just-in-time），不做独立教程系统。知识原子本身落 Store B（`type: knowledge`，带领域 tag），决策卡与文档只引用不复制。

### 2.3 机制三：补课是双向的

- 对新手：AI 给**人**补课（教学——对照翻译、知识夹层）。
- 对老手的半途项目：AI 给**自己**补课（考古入记忆）。
- 两个方向殊途同归：**最终 AI 与人对项目的理解一致**，之后走完全相同的日常协作（决策卡 / 办公室 / 行内问答）。这是 v1 handover brief 的对称复用：brief 本来给"新加入的 AI worker"读，翻转受众就是老手导入项目时的 onboarding 文档。

### 2.4 新手体验：AI 主驾，闸门依然是人的

- **全流程托管 = 剧本（Playbook），不是聊天**。管家挂载生命周期剧本（调研 → 需求分析 → 设计 → 拆解 → 执行 → 验收），每阶段固定行为模式：一两句解释本阶段目的 → 结构化访谈收集信息 → 产出正式工件 → 闸门决策卡。剧本落 skills 模块，阶段产物即 Document 族，闸门即 DecisionProposal。
- **掰开揉碎的正确姿势 = 对照翻译，不是名词解释**：AI 访谈说人话（"用户忘了密码怎么办？"），用户随口答；AI 把回答翻译成正式需求文档，同时标注对照（"你说的'账号登不进去要能找回来'，专业上叫账号恢复，我写进了非功能需求第 3 节"）；每份 AI 产出的工件带"人话对照"开关，专家模式直接关。用户亲眼看到"我的话 → 专业工件"的映射，下次自己就会用术语。

### 2.5 老手体验：AI 先给自己补课，然后闭嘴干活

- **半途接入的入口是"导入考古"，不是"新建项目引导"**。四步：连接 Git 仓库（+ 可选 Linear/GitHub 导入）→ 派 researcher 型 CLI Agent 考古（读 README/CLAUDE.md/代码结构/提交史，产出项目简报）→ **人校对简报（校对即建模，修正沉淀为项目记忆与约定）** → 增量维护。
- **增量原则**：只导活跃面（在途的事、维护中模块），**绝不要求回填历史**。
- 老手日常态 = 既有功能 + 参数差异：决策卡折叠知识层、解释密度 terse、行内问答直答不科普、主动汇报只报异常与待决。**档位不需要新的 UI 状态机，它就是 Store C 上下文装配器的注入策略差异**。
- 半途项目三个特有价值点（纯新手项目遇不到，老手的"值回票价"点）：
  1. **变更影响分析**：AI 有模块地图，改 A 前提示 B/C 受波及；
  2. **决策因果补录**：考古只能猜出"是什么"猜不出"当年为什么"，AI 在日常协作中顺口追问并记入项目记忆——给未来交接买保险；
  3. **带教下一个新成员**：简报是活的，新人类成员入职由管家用 brief 带教，消掉"每次换人都得我口述一遍项目背景"。

### 2.6 风险清单

| 风险 | 对冲 |
|------|------|
| 教学话痨：句句解释，三分钟就烦 | 知识层只挂决策卡与工件对照，聊天流永远 terse；折叠忽略 3 次降密度 |
| **AI 事实上替新手做项目决策**（托管滑向越权，最危险） | 剧本每闸门强制落决策卡 + "一键采纳"降低拍板成本；闸门在人铁律（v1 §5 三不边界）对新手尤其不松 |
| 导入时强推模板、要求重造结构 | "尊重现状"写进考古 Agent 任务包约束；只建增量 |
| 专长度误判（老手被当新手科普） | 降密度静默且可手动改；"别再解释这类"直写偏好 |
| 新手项目 + 老手协作者混场 | 档位按人存，天然隔离 |

## 3. 项目档案底座（简报的去腐化设计）

### 3.1 核心定调：简报是视图，不是存储实体

"项目简报"（模块地图 / 技术栈 / 活跃热点 / 风险区 / 技术债）若设计成 AI 写一份静态文档存起来，就是**第二个会腐烂的真相源**，直接违反 v1 §8 铁律（"凡 DB 能实时查的只存指针不存值"）。正确形态：**底层存结构化原子，简报 = 运行时装配的视图**——每次渲染（人看 / 注入 AI / 导出）都现装配，永远不存在"简报说 X 但实际是 Y"。按变化速度分层：

| 内容 | 变化速度 | 形态 |
|------|---------|------|
| 活跃热点 | 每次提交都在变 | **不存**。纯派生量：git 提交热力 × issue 密度，查询时现算 |
| 模块地图 / 技术栈 | 慢（月级） | 存，带 `refreshedAt`，事件触发刷新 |
| 项目约定 | 慢 | 存 |
| 风险区 / 技术债 | 慢但会过期 | 存，带 confidence，可 superseded |
| "当年为什么这么设计" | 只增不改 | 存，最珍贵的一类 |

### 3.2 槽位 schema 管结构，记忆原子管内容

不新造实体族：**MemoryAtom**（memory 模块，project scope）即容器，v1 §8 原子壳（scope / type / confidence / sourceEventId / refs）现成。只新增一层轻量**档案槽位注册表**：

```
档案 schema（版本化，系统内置）
  槽位：tech-stack │ module-map │ conventions │ risks │ tech-debts │ causal-notes │ …
  每槽位定义：内容结构（JSON schema）、完备度判定、刷新策略、填充方式

MemoryAtom（project scope, type ∈ 档案类型）
  content 按槽位 schema 结构化
  confidence + sourceEventId + status(active|superseded|archived) + refreshedAt

派生视图（代码算，永不落库）：
  activityHotspots()      ← git 统计 + issue 分布
  completeness()          ← 槽位填充率（工程完备清单的数字化形态）
  briefing()              ← 装配叙述，给人和 AI 看
```

为什么必须加槽位层：自由原子召回质量对 LLM 不稳定（每次捞上来的不一样），而 AI 分析、完备度统计、引导访谈都需要**确定接口**。schema 管槽位、原子管内容——统计页面能数"风险区 3 条、2 条已过期"，AI 装配时能精确取"项目约定切片"。**工程完备清单在此获得精确位置：完备度 = 槽位填充率，派生量**；新手模式空槽位 → 剧本访谈补齐；导入模式 → 考古 Agent 草填 → 人校对。两条路径、同一个 schema，校对记录即 AI 学习该项目的训练数据。

### 3.3 统计管道与 AI 叙事管道分离

- 统计吃 **Store A 事实层**（issues / executions / events / AIUsageLog / git），精确数字，SQL 聚合；
- 简报/档案只服务 AI 装配与人的阅读；
- **统计永远不读 AI 写的档案原子**。

理由：档案原子带 confidence、会过期、是 LLM 生成物；统计若吃它，"AI 的话"变成报表真相，一条错误的技术债判断会同时出现在 AI 建议和统计图表里互相背书。健康流向是反向引用：档案需要数字处**引用**统计结果（存指针不存值）。

### 3.4 剧本：流程状态是"游标"，不是"牢笼"

1. **剧本是可选挂载物，不是项目模型的刚性结构**：`Project` 上只放两个可空字段——`playbookRef`（挂哪个剧本）+ `lifecycleStage`（游标）。不挂 = 自由模式；老手项目默认不挂（或只挂"维护型"轻剧本：变更 → 影响分析 → 审批 → 执行 → 验收）。剧本定义版本化放 skills 模块，与档案 schema 同为系统内置数据。
2. **阶段可跳过，跳过是事件**：用户跳过设计阶段则放行，但记 `stage-skipped` 事件——后面验收出问题时 AI 有据可查地提醒"当时跳过了设计评审"。
3. 新手/导入在模型层完全对称：**同一档案 schema、同一剧本挂载机制，区别只是初始填充路径（访谈 vs 考古）与默认剧本（全流程 vs 维护型）**。

### 3.5 写回纪律

- **初始**：考古 Agent（草稿、低 confidence）或引导访谈（用户亲述、高 confidence）；
- **日常不重写**：消化器**事件驱动**（里程碑完成、某模块大改、Worker 交回增量时才触发对应槽位整理），不随任务更新话痨化；
- **Worker 永不直写**：交增量 → 消化器升维成档案原子（v1 §10 写回闭环，防双系统互咬）；
- **人随时可推翻**：superseded 而非删除，保住"为什么当时这么判断"的可溯性。

## 4. 管理界面：模板与档案的分工

### 4.1 两种本质 × 三层位置

**完备清单、剧本、档案槽位 schema 是同一种东西——模板（定义）**：生命周期独立于项目、可版本化、可分享。**档案原子、剧本运行态是另一种东西——项目实例（数据）**：项目私有、不可分享。所有管理界面按此切开：

```
系统内置层     发布自带，只读，不可删，可被上层覆盖/复制
    ↓ 复制
工作区自定义层  团队沉淀，可 CRUD，可导出分享（远期：社区市场）
    ↓ 挂载 / 填充
项目实例层     项目私有：挂载的剧本运行态、档案原子、完备度快照
```

此三层模式仓库已跑通（core-config 四 manager、`completeness-checklist.service.ts` 系统/团队/技术栈/应用四级），**剧本模板与档案 schema 直接加入 core-config 模板家族，UI 复用 template-manager 形态，不发明新范式**。

### 4.2 用户界面落位

| 层 | 界面 |
|----|------|
| 模板层（设置区，core-config 家族） | 完备清单管理（已有）；**playbook-manager**：阶段序列 + 每阶段访谈问题集 + 闸门定义 + 工件模板；**schema-manager**：槽位清单/结构/完备度判定。均支持"项目类型 × 技术栈"维度自动匹配（Java 后端项目自动配 Java 清单 + 后端剧本）。分享 = 导出/导入带 schemaVersion 的 JSON（与清单共用机制） |
| 项目实例层 | **剧本运行态**：项目详情页"流程卡"——阶段时间线、当前游标、闸门记录（含跳过）。只读进度视图，闸门动作仍去决策收件箱完成（不开第二个拍板入口）。**项目档案页**：详情页新 tab——按槽位分组的原子列表 + 置信度标识 + `refreshedAt` 新鲜度 + 溯源链接（可点开看"这条是谁/哪个事件写的"）+ 顶部完备度环 + **草稿区**（AI 产出唯一落点）。人可直接编辑任何槽位，编辑即最高置信度 |
| 权限 | 模板管理 = workspace owner/admin；档案编辑 = project maintainer+ |

### 4.3 AI 界面：不新增面板，工具 + 草稿回流

**AI 侧不出现第二个管理界面**。档案与剧本只是给 v1 亲密度谱喂新内容：

| 亲密度 | 档案/剧本在 AI 侧的样子 |
|--------|------------------------|
| 耳语（行内问答） | 选中槽位问"这是什么"→ terse 回答（老手日常态） |
| 工位（细聊） | "帮我更新风险区"→ AI 改的是档案原子的草稿，不直接落库 |
| 办公室 | 管家视角：档案完备度、过期槽位、剧本卡在哪一步 |
| 主动汇报 | 新鲜度告警（"模块地图 3 个月没更新，该区域近期提交活跃，要重扫吗？"）——结构化卡片，可忽略 |

写入纪律落到 UI 一句话：**AI 的一切产出只进草稿区/决策收件箱，人批准才 active**。考古产物、消化器沉淀、Worker 增量升维全部如此；批准动作复用决策卡四段式，不新发明审批 UI。

### 4.4 分析：全部派生，反哺模板层

三组派生指标，零新增存储：

1. **档案健康**：完备度（槽位填充率）、新鲜度分布、置信度分布、AI 命中率（原子壳 `hits` 现成）——落 dashboard + 档案页顶部；
2. **剧本效果**：各阶段平均耗时、**跳过率**、闸门退回率。跳过率高的阶段 = 剧本设计问题（冗余或时机不对），数据直接反哺剧本模板迭代；
3. **模板使用统计**：每个清单/剧本被多少项目挂载、审计通过率、效果对比——社区分享机制的地基（PRD 把清单社区定位为护城河，榜单没有使用数据就是空谈）。

**消化器的升维动作应能跨项目提炼模板**：三个项目都出现同一条清单项/约定时，管家主动问"要保存为团队自定义模板吗？"。分享流向就此盘活：**项目实例中提炼 → 工作区模板 → 社区**，AI 是流水线上的搬运工，不是每层各管各的孤岛。

## 5. 决策摘要

| 项 | 结论 |
|----|------|
| 双用户不建模为两种用户 | ✅ 专长度向量（人 × 领域）+ 静默学习演化 + 手动纠偏 |
| 决策卡四段式（提案/理由/知识夹层/后果预演） | ✅ 知识夹层永不主动弹开；学习发生在决策现场 |
| 对照翻译式教学（人话访谈 → 专业工件 + 对照标注 + 人话开关） | ✅ 掰开揉碎的首选形态 |
| 老手接入 = 导入考古（连接 → 考古 → 人校对 → 增量维护） | ✅ 只导活跃面，绝不回填历史 |
| 补课双向对称（AI 教人 / AI 考古给自己补课） | ✅ handover brief 翻转复用 |
| 简报 = 运行时装配视图，不是存储实体 | ✅ 活跃热点纯派生不存；其余按变化速度分层存储 |
| 档案 = 槽位 schema（系统内置版本化）+ MemoryAtom 原子 | ✅ 不新造实体族 |
| 统计吃事实层，永不读 AI 档案原子 | ✅ 两管道分离，档案可反向引用统计 |
| 剧本 = 可选挂载（playbookRef + lifecycleStage 游标），阶段可跳过（记事件） | ✅ 流程状态是游标不是牢笼 |
| 写回纪律（初始访谈/考古、消化器事件驱动、Worker 不直写、人可推翻 superseded） | ✅ |
| 模板（清单/剧本/schema）vs 实例（原子/运行态）分开管理 | ✅ 模板入 core-config 家族复用 template-manager 形态；三层位置：内置 → 工作区自定义 → 项目实例 |
| AI 侧不新增管理面板 | ✅ 工具 + 草稿回流（草稿区/决策收件箱），批准复用决策卡 |
