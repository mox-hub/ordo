## ADR-001: 产品采用“项目管理底盘 + AI 接入协作平台”路线

- 状态：active
- 日期：2026-03-20
- 上下文：
  - 现有系统已经具备项目管理与工程协作模块，但产品叙事仍偏传统人类 UI 中心
  - 市面上已经存在成熟的 AI 编码与代理工具，平台没有必要重复造轮子
  - 产品仍需要保留传统项目管理和工程经验的价值
- 决策：
  - 产品先以“项目管理底盘”作为稳定基础
  - 在其上建设“AI 接入与协作平台”
  - 平台优先让外部优秀 AI 工具接入并参与任务执行，而不是先做全栈自有 AI 终态
- 后果：
  - 正面：
    - 产品边界更清晰
    - MVP 更可落地
    - 可复用现有项目管理能力
  - 负面：
    - 短期内平台能力会强于自有 AI 成员能力
    - 需要在文档与架构上明确“平台内 AI 成员”和“外部接入 Agent”的差异

## ADR-002: Phase 1 优先服务“人类项目经理 + 外部 AI 开发工具”

- 状态：active
- 日期：2026-03-20
- 上下文：
  - 完整 AI 团队管理目标跨度过大
  - 第一阶段需要一个足够聚焦的用户组合来验证平台价值
- 决策：
  - Phase 1 明确先服务“人类项目经理 + 外部 AI 开发工具”
  - 先打通任务执行闭环，不把完整 AI 组织能力列为首阶段完成标准
- 后果：
  - 正面：
    - 路线更可控
    - 易于做出可用 MVP
  - 负面：
    - 平台内长期 AI 成员能力将延后进入产品主线

## ADR-003: 外部 AI 接入优先级固定为 MCP > CLI > API/Plugin > 其他

- 状态：active
- 日期：2026-03-20
- 上下文：
  - 平台需要优先支持最适合 Agent 深度接入的方式
  - 不同接入方式的抽象和维护成本不同
- 决策：
  - 首批接入优先级固定为 `MCP > CLI > API/Plugin > 其他`
  - 新能力设计时默认优先保证 MCP 与 CLI 两条路径
- 后果：
  - 正面：
    - 接入策略更稳定
    - 平台接口设计更统一
  - 负面：
    - 插件生态和其他接入方式在第一阶段不是最高优先级

## ADR-004: 必须显式区分“平台内 AI 成员”和“外部接入 Agent”

- 状态：active
- 日期：2026-03-20
- 上下文：
  - 平台既希望支持长期 AI 成员，也希望支持外部优秀 AI 工具接入
  - 如果不显式区分，后续权限、生命周期、治理模型会混乱
- 决策：
  - 产品、PRD、架构、权限模型中必须显式区分：
    - 平台内 AI 成员
    - 外部接入 Agent
- 后果：
  - 正面：
    - 身份和治理边界更清楚
    - 后续放权策略更容易设计
  - 负面：
    - 数据模型与 UI 设计复杂度会上升

## ADR-005: 平台长期接入优先级保持 MCP > CLI，但 Phase 1 先落地 CLI

- 状态：active

  - 正面：

    - 更容易先形成可用 MVP
  - 负面：
    - 文档中必须明确区分“长期架构优先级”和“短期实施顺序”

## ADR-008: 产品形态采用 Web 控制面 + Local Runtime，后续演进到 Desktop Shell

- 状态：active
- 日期：2026-03-20
- 上下文：

  - 但纯 Web 无法很好承载本地文件、Git、Terminal、CLI Agent 等执行场景

  - 当前阶段采用方案 C：

    - Local Runtime
    - Desktop Shell

  - 正面：

    - 需要额外设计本地连接、权限和跨平台抽象

## ADR-009: 控制能力与执行能力分层，而不是按 Web / Client 二元切分

- 状态：active
- 日期：2026-03-20
- 上下文：
  - 如果直接按“网页代码”和“客户端代码”来切，会让产品边界模糊
  - 真正需要区分的是控制面职责与执行面职责
- 决策：
  - 控制能力归 Web 控制面：
    - 项目
    - 任务
    - 迭代
    - 审批
    - 审计
    - 配置
  - 执行能力归 Local Runtime：
    - 文件
    - Git
    - Terminal
    - CLI
    - Workspace
  - Desktop Shell 只作为体验增强层，不成为新的业务核心
- 后果：
  - 正面：
    - 分层更稳定
    - 有利于后续跨平台和桌面壳演进
  - 负面：
    - 初期需要建立更清晰的协议层和边界文档

## ADR-010: CAP-P-01 主线采用方案 C 混合渐进（三期推进）

- 日期：2026-09-09
- 背景：需求承接与拆解管道（管道①②）是 2026-09-08 需求治理裁决的全力主线；设计纪要草案 v0 给出三方案（A 剧本承载 / B Assistant-Native / C 混合渐进）与七条开放问题，待用户裁决后开工。
- 决策：采用方案 C 混合渐进——
  - 一期：AI 预填访谈。剧本骨架（注册表新剧本 research→clarify→breakdown→acceptance-draft）+ 一个静默场景只做「按需求生成/修订访谈答案候选」，人改后走现有 submitInterview，零新编排层。
  - 二期：组合件提案。扩展 PlanCard payload 承载「任务族 + acceptance 清单」，accept 后由最小 applier 事务化落库（复用 assistant 工具领域逻辑，不放 ai-hub）。
  - 三期：动态访谈。静默场景升级多轮追问（prepareContext 注入剧本阶段产物），访谈 Dialog 换 AI 会话形态。
- 理由：一期即可让小白走通完整管道（最快可用里程碑）；编排层延到三期规避 ai-hub god module 风险；每期独立可验收可回退；方案 B 的体验是三期的自然终点，非二选一。
- 后果：
  - 正面：管道①②最快产品化；ai-hub 压力后置；审计/回放面友好（一期每步确定性可回放）。
  - 负面：一期「AI 感」仍弱（预填而非对话）；三期总成本高于方案 A。
  - 待办：开放问题 #2（需求级 acceptance 族数据形状）与 #6（卡型扩展）须在二期动工前裁决；一期需裁决 #1 入口（默认沿用 office 剧本页 InterviewDialog）与 #4（criteria.source 溯源枚举）。

## ADR-011: CAP-P-01 一期入口前移——统一创建面板 AI 代理模式（grill 澄清前置）

- 日期：2026-09-09
- 背景：一期方案 C（AI 预填访谈）开工前，用户提出在访谈之前还需「grill」环节——通过 AI 连续追问明确原始需求；且 grill 依托 skills 承载（现有 skills 管理面仅 list/update 两端点，无增删、无内容/路径字段，需补全）。
- 决策：
  - 统一创建面板 project 类型双模式：手动模式保留现状；AI 代理模式 = 创建面板内对话框 + 交互选项弹窗，经 grill 连续追问澄清需求，确认后建项目 → 跳 init 页自动 mount「需求承接」剧本。
  - skill 载体语义：SkillConfig 加 content（物化入 DB）+ sourcePath（本地 SKILL.md 路径留档，导入时读文件入 DB）双字段。
  - grill 驱动：静默场景无状态多轮（每轮全量传已问答，AI 出下一问 + 猜测选项），不扩展浮窗协议；skill 指令由服务端 prepareContext 读取注入，不经前端往返。
  - grill 产出持久化：确认建项时同步落「需求澄清纪要」Document，供剧本访谈预填引用。
  - 节奏：三切片连续（skills 管理补全 → grill 会话 → 确认落库+自动挂载+访谈预填），逐片提交。
- 后果：
  - 正面：grill 产出直接喂给剧本访谈（与方案 C 一期无缝衔接）；skills 管理面补全使本机 70+ 技能可经路径导入接入。
  - 负面：一期范围扩大，skills 迁移与契约变更为新增量。
  - 边界：浮窗协议扩展、skill 版本化、授权下发链改动均不做（见计划「明确不做」）。

## ADR-012: CAP-P-01 二期组合件提案——三设计点裁决

- 日期：2026-09-10
- 背景：二期动工前草案开放问题 #2（需求级 acceptance 族数据形状）与 #6（卡型扩展）锁定必须裁决。
- 决策（用户未逐项答复，按推荐项执行）：
  - #2 验收族：**每任务复制一份 acceptance**（零 schema 迁移，验收粒度=每任务独立过闸，兼容 acceptCompletion 单任务收口）；组合件 payload 中每任务可选自带 acceptance 段；criteria.source 落 `ai-generated-from-interview` 溯源（顺带清偿开放问题 #4）。
  - #6 卡型：**扩展 kind='plan'** 为组合件超集——payload.issueId 变可选（顶级任务族）、added[] 每项可带 acceptance 段；前端 PlanCard 槽位渲染增量展示，kind 动作表/apply() 路由全部不动。
  - 范围：切片 1=组合件 applier（applyPlan 升级，事务内建任务族+acceptance+criteria）+ PlanCard 渲染 + 测试；切片 2=intake-composite 静默场景（acceptance-draft 闸门后从拆解/验收草案两文档生成组合件提案进收件箱）+ 剧本页入口。
- 约束：acceptance.module 已 imports DecisionModule——ProposalService **不得**反向注入 AcceptanceService（成环），组合件建验收像 applyPlan 一样直接 prisma 事务写。
- 后果：零迁移零新卡型，向后兼容（旧 plan payload 行为不变）；需求层实体（Requirement/family）留待验收体系重构时再评估。

## ADR-012 补记：二期实施落点（2026-09-10）

- 组合件 payload 形状：`{ added: [{ title, description?, estimate?, assigneeMemberId?, acceptance?: { title?, completionType?, criteria[] } }] }`（issueId 可选；未引入独立 tasks 段，added 单字段承载两种语义）。
- 溯源常量 `ACCEPTANCE_SOURCE_AI_INTERVIEW = 'ai-generated-from-interview'` 由 proposal.service.ts 导出（决策模块为源，避免跨模块反向依赖）。
- intake-composite 场景输入为显式文档指针（breakdownDocumentId/acceptanceDocumentId），前端从剧本 stages[].documentId 取——服务端不做剧本感知，保持 ai-hub 与 playbook 解耦。

## ADR-010 补记：三期（动态访谈）实施落点（2026-09-10）

- 场景：`interview-dynamic` 静默场景，协议沿用 grill-next 无状态多轮（每轮全量传 history，零服务端会话态）；与 grill 的差异仅在三处——问题组（questions）必填、收敛输出为问题组完整答案集（复用 interview-prefill 的防御性过滤与「绝不编造」纪律）、prepareContext 支持阶段工件文档 id 注入（artifactDocumentIds，可空）。
- 前端：InterviewDialog 双形态——「AI 会话访谈」（默认，interview-chat.tsx：气泡流 + choices chips 即答 + 收敛后答案只填空回填表单并自动切换）与「直接填写」（原静态表单+预填，兜底）；提交链不动（submitInterview 确定性转写 + 闸门卡）。
- 边界：不扩展浮窗协议、无服务端会话态、8 轮追问上限（前端护栏，超限引导切表单）、chat 答案回填不覆盖已手填内容（尊重人工输入）。
- 至此方案 C 三期全部落地：管道①（访谈澄清）由「静态表单+预填」升级为「AI 会话动态追问为主、表单兜底」，管道②③④⑤（拆解/验收清单/人确认/落库）已由一期二期贯通。

## ADR-013: Select 下拉框 label 显示的组件级契约——`items` 是必填契约而非可选优化

- 状态：active
- 日期：2026-09-11
- 背景：全站下拉框 trigger 显示的是原始 value（id）而不是选项名称，空值状态下还会把内部哨兵 `__native_select_empty__` 当文本渲染出来。排查确认是组件层缺省行为，不是个别调用点写错。
- 根因（实测证据，非推断）：
  - `components/ui/select.tsx` 的 `Select` 只是 `SelectPrimitive.Root` 的别名，**全仓 `items` / `itemToStringLabel` 传参次数为 0**；base-ui 的 `Select.Value` 在拿不到二者时回退 `stringifyAsLabel → String(value)`，直接显示 value。
  - 无法从 `SelectItem` 反推 label：**弹层关闭时 item 根本不挂载**（jsdom 实证 `ITEMS_IN_DOM = 0`），注册表类方案在首次渲染时必然为空。
  - `__native_select_empty__` 不是 base-ui 的字符串，而是 `ui/native-select.tsx` 自定义的「空值哨兵」，被当 value 传下去后经同一 fallback 渲染成文本。
- 决策：
  - **`NativeSelect`**：在组件层把已解析的 `{ value, label }`（含 optgroup 与哨兵项）作为 `items` 交给 Root——一处修复覆盖全部 121 处用法，调用方零改动；未提供空选项时给哨兵补空 label，杜绝标记泄漏。
  - **裸 `Select`**：确立硬规则——**value ≠ 展示文本时必须显式传 `items`**（`{ value, label }[]` 或 `Record<value, label>`），或改用 `SelectValue` 的函数式 children `{(value) => label}`；value 与展示文本相同（role 字符串、字体名等）可不传。本次按此补齐 10 处 value≠label 站点。
  - 契约写入 `apps/frontend/COMPONENTS.md`（agent 与人共用索引），使新写下拉框时无需重踩。
- 后果：
  - 正面：全站下拉框显示名称；规则落在版本控制的组件清单里，可被后续会话检索；`SelectValue` 显式 children 优先级最高，7 处老写法行为不变。
  - 负面：裸 `Select` 多了一份必须人工维护的 `items` 与 `SelectItem` 双写（`SelectItem` 仍不可省——它才是弹层里的可选项）；漏传则静默显示 id，无编译期护栏。后续可考虑加 lint 规则或在 `Select` 封装层做开发期告警。
- 边界：不引入 label 注册表（已证伪）；不改 base-ui；本地化（把 `member` 显示成「成员」）不在本次范围。

## ADR-014: CAP-A-14 桌面壳选型变更——Tauri 转向 Electron 验证（spike 优先）

- 状态：active
- 日期：2026-09-12
- 背景：Tauri 路径切片①②③已完成并固化（feat/desktop-packaging-v0.6.1@519baf2：自包含资源 + 密钥持久化 + 一键打包链，自包含 staging 冷启动冒烟通过）。收口前选型复评发现 Tauri 的核心卖点在本项目形态下不成立：①**包体**——实测打包资源中 server node_modules 386MB 主导总包体，Tauri 壳（~10MB）对 Electron 基座（安装包口径 ~90MB）的差异被稀释为 ~30-50MB（约 20%），「薄壳」本是当初选型初衷；②**架构**——APM 桌面端本质是「桌面发行版」（托管完整 NestJS+Prisma 运行时），Rust 层全部工作（spawn node.exe、env 注入、端口探测、db push）是在用 Rust 模拟 Node 原生能力，形成全仓唯一 Rust 代码孤岛；③**速度**——用户裁决现阶段快速交付关键，Rust 胶水层（~千行）任何变更需重编译 + IPC 两端对齐 + capabilities 配置，拖慢桌面壳跟随 server/前端迭代的响应；④**UI**——WebView2 Evergreen 版本随系统漂移、渲染引擎不可锁定，未来 mac/linux 需对三套 WebView 回归设计系统，Electron 全平台锁定同一 Chromium。

  - 新开分支 `feat/desktop-electron-spike` 验证 Electron 路径；执行计划见 `docs/roadmap/electron-desktop-v0.6.1-plan.md`。
  - `feat/desktop-packaging-v0.6.1` **归档保留**（成果固化于 519baf2，不合并、不删除）——pack.mjs 资源准备、start:prod 入口修正、prisma 移入 dependencies、密钥首启生成方案、端口探测/健康检查语义全部直接复用或翻译。
  - CAP-A-14 能力目标与 v0.6.1 版号不变，仅实现壳变更：Electron + electron-builder（NSIS）+ TypeScript main/preload；server 承载方式由切片 E① 实验裁决（首选 Electron 内嵌 Node 直接运行 server dist，省随包 node.exe ~75MB；回退 spawn 随包 node.exe——与 Tauri 已冒烟路径同构）。

- 后果：
  - 正面：桌面壳回归全仓 TS 单语言栈（turbo/vitest/esbuild 工具链直通，main/preload 可进 vitest）；apm-runtime（utilityProcess）与 CLI adapters（child_process）同 AI 执行面模型天然同构，二期接入成本大降；包体反而可能更小（内嵌路径省 ~75MB node.exe）。
  - 负面：安装包内存基线 +150-250MB（对重负载桌面工具可接受）；contextIsolation/preload 安全面需自行配置到位；electron 依赖须登记 pnpm catalog 与 allowBuilds。
  - 风险：Prisma query engine（dll.node）在 Electron ABI 下的兼容性是 E① 首验项——引擎为 N-API 构建理论无关，实测不过即切回 spawn 随包 node.exe 路径，不影响选型成立。
- 边界：不签名 / 不自动更新 / AI 执行面不随包 / 不做便携模式——与 CAP-A-14 卡既有四裁决点一致，本轮不变。

## ADR-015: 桌面壳分发与生命周期强化（P0/P1 收口；推翻「不自动更新」边界）

- 状态：active
- 日期：2026-09-12
- 背景：桌面壳定版 Electron（ADR-014 补记）后与成熟桌面应用对标盘点，识别出「进程编排已扎实、分发与生命周期半边缺失」：无自动更新（升级=手动重下 241MB）、无双开防护（双开双拉 server 抢同一数据根）、三条崩溃路径（server/daemon/渲染进程）全部无自愈、无托盘常驻（关窗=全杀，与 AI 执行面长任务常驻的产品形态冲突）、窗口状态不持久化、页内导航未拦截、secrets 明文落盘、卸载后 ~/.apm 无处置、无诊断导出、壳测试全靠手动 CDP。用户拍板：P0+P1 全量落地，**代码签名跳过单独解决**。
- 决策：
  - **推翻 ADR-014 边界「不自动更新」**：electron-updater + GitHub Releases feed（mox-hub/agent-project-manager）。消费端已落地：打包模式启动 30s 后静默首轮检查（避开冷启动）、设置页手动检查、下载完成弹窗询问立即重启安装、未确认则退出时自动安装；dev/未打包优雅禁用。**发布端（tag 触发 CI 构建 → 上传 exe + latest.yml 到 Releases）为待办**，feed 缺失时更新检查落 error 状态不影响主流程。
  - **生命周期**：单实例锁（`requestSingleInstanceLock`，second-instance 唤起既有窗口）；server 意外退出自动重启 + daemon 意外退出自动重拉（指数退避 1s→30s 封顶，连续 5 次熔断防 crash loop，手动启动成功即清零）；渲染进程崩溃白屏自动重载（60s 窗口内 ≥3 次熔断）；主进程 `uncaughtException`/`unhandledRejection` 兜底记日志不弹崩溃框。
  - **托盘与关闭语义**：`close_to_tray` 默认开——关窗最小化到托盘、服务保活；托盘菜单（显示主窗口/检查更新/退出）；托盘图标缺失时回退「关窗即退出」。窗口位置尺寸持久化到 desktop-state.json（getNormalBounds，下次启动恢复）。
  - **安全加固**：`will-navigate` 白名单（仅本应用源，其余转系统浏览器）；IPC 面轻校验（参数必须对象/≤64KB/拒绝 `__proto__` 等原型污染键，深递归校验不做）；secrets.json 经 safeStorage（Windows=DPAPI）加密落盘——旧版明文兼容读入不强制重加密；加密格式但解密失败（跨机器拷贝）时**报错拒绝启动，绝不静默重新生成**（JWT_SECRET 变更踢全量登录态、INTEGRATION_ENCRYPTION_KEY 变更毁集成密文）。
  - **卸载语义**：NSIS `customUnInstall` 询问是否删除 `~/.apm`（默认保留供下次复用）——数据根不在 NSIS「删除应用数据」管辖内（其只认 %APPDATA%），不询问则要么永久残留要么无提示删光。
  - **诊断导出**：`export_diagnostics` 命令（壳日志 + 运行元数据 + 进程快照打 zip；PowerShell Compress-Archive 免压缩依赖；密钥/凭证明确不进包）。
  - **壳级 e2e**：`scripts/e2e-shell.mjs`（Playwright `_electron` 拉起真实壳，断言窗口/IPC 契约/desktop-state 读写/更新禁用，`APM_DATA_DIR` 指临时目录隔离真实数据）——当日实跑 ALL PASS。进 CI（quality-gate）待办。
  - **数据根**（同日安装包三调整，与本 ADR 同批）：固定 `~/.apm`（`APM_DATA_DIR` 环境变量仅测试/CI 隔离用）；守护进程配置与锁在 `~/.apm/desktop/` 子目录与手动 CLI 锁隔离；Chromium profile 在 `~/.apm/electron/`；v0.6.1 旧 %APPDATA% 数据白名单自动迁移留 `.migrated.bak`；安装期 `customInit` 检测既有数据目录提示升级安装。
  - **代码签名**：用户裁决**跳过、单独解决**——未签名包的 SmartScreen 警告与杀毒误报风险接受现状，本轮不做过渡方案。
- 后果：
  - 正面：分发闭环只剩发布端 CI 一段；三条崩溃路径有自愈兜底，长任务场景服务常驻不再被关窗打断；安全面补齐导航劫持与密钥明文两个洞；卸载/迁移/诊断有完整用户语义；壳有可进 CI 的 e2e 基建。
  - 负面：electron-updater 新增运行时依赖（须确认进包，`desktop:pack` 后验证 node_modules/electron-updater）；退出路径多 `isQuitting` 状态机；诊断导出依赖 PowerShell（壳本就 Windows-only）；托盘/更新行为无实机安装版回归（本轮 dev e2e 覆盖，安装版冒烟随下次打包）。
  - 风险：更新 feed 指向 GitHub Releases，未签名包走更新链路时 SmartScreen 语义与首装一致（用户已接受）；自动更新下载大包体（~241MB）无差量（NSIS 差量更新后续可开 differentialPackage）。
- 边界：crashReporter 符号化上报、使用遥测、deep link（apm://）、server 运行时瘦身（esbuild bundle）、优雅关闭（SIGTERM 宽限 + WAL checkpoint）、更新发布端 CI 接线、签名采购——均不在本轮，按后续切片立项。

## ADR-015 补记 2：包体瘦身验证与落地（2026-09-12，安装包 242MB → 188MB）

- 验证结论（先验证后落地，用户裁决）：
  - 体积构成：staging server 471MB 里 Prisma 全家桶 228MB 占 52%（CLI 58 + @prisma/engines 77 + .prisma/client 32 + @prisma/client 58）；CLI/engines 只服务「用户机首启 db push」。
  - **bundle 路线证伪**：esbuild 打包已编译 dist 不减体积（依赖代码只是换合并方式，NestJS 动态 DI 无 tree-shake 收益）——弃。
  - **定向剪除验证通过**：剪 prisma CLI + @prisma/engines 后 server 启动、健康探活、真实 DB 读（login 401 业务响应）与写（register 201 + JWT 签发）全部正常——运行时唯一依赖 = @prisma/client + .prisma/client 的 query engine dll（PRISMA_CLIENT_ENGINE_TYPE=library）。
  - **顺带发现数据泄露**：pack.mjs 整目录拷 prisma/ 把开发者 dev.db(14MB)+dev.db-wal(5MB)+*.bak(3MB) 打进了安装包——已修（白名单拷贝 schema/migrations/template.db）。git 侧无泄露（.gitignore 已挡）。
- 落地（pack.mjs 四改 + 壳侧一改）：
  1. prisma 目录白名单拷贝（schema.prisma/migrations/template.db），泄露封死；
  2. staging package.json 剥 `prisma` 依赖（CLI 不随包）；
  3. 打包时用开发区 CLI 生成 default-template.db（干净库模板，file: 相对 schema 目录解析）+ prisma generate 后再剪 CLI/engines + stripNonRuntime 挪到 generate 后（覆盖 8MB index.d.ts 等生成产物）；
  4. 壳侧 runDbPushIfNeeded → restoreDefaultDbIfNeeded：首启拷贝模板（秒级）替代 40s 现场建库；已有库跳过不变；dev 无模板回退原 db push；打包模式模板缺失报包损坏。
  - electron-builder.yml：删除 uninstallerHeader/uninstallerSidebar（NSIS schema 无此项，校验失败）；output 迁 dist-release-3（锁目录坑惯例）。
- 实测：安装包 **242MB → 188MB（-54MB/-22%）**；staging server 471→245MB；新增 cli staging 18MB 仍在总减之内。首启建库从 ~40s 降为秒级拷贝。
- 边界：swagger-ui-dist（5MB，生产禁用但顶层 import 链保留）、@linear(16MB)、mastra/effect 链为功能依赖不动；schema 演进 migrate deploy 待办与模板机制不冲突（升级场景仍是「已有库跳过」）。

- 执行：①**七版 draft 按序 Publish**（v0.7.7→v0.7.13，`gh release edit --draft=false`；按序保证 Latest 标签落 0.7.13），GitHub Releases feed 正式生效——repo 为 PUBLIC，electron-updater 匿名拉 latest.yml 免认证，差分链（exe+blockmap 三件套全版本齐备）成立；②**壳侧**：UpdateStatus 扩 `releaseNotes`（electron-updater 三形态归一，GitHub Release body 随 available/downloaded 透传）+ 状态实时广播（`setUpdateStatusBroadcaster` 注入回调解耦窗口层 → `webContents.send('desktop:update-status')` → preload `onUpdateStatus` 通道；下载进度同态 150ms 节流）+ **checkForUpdates 重入防御**（checking/downloading/downloaded 状态拦截重复触发——原实现下载中手动再检查会抛错把进行中状态误覆盖成 error）；③**前端**：设置新增「关于」页（`/app/settings/about`，系统组导航，about-section）——产品信息卡（运行模式徽标 + 壳版本对照 + Releases/仓库外链；web 模式不显示版本号：发版主版本随 desktop 包 bump，frontend/server 包版本 0.6.2 落后会误导）+ **桌面偏好卡整卡自 runtime 页收编**（更新区正式化：版本对照/下载进度条 ui/progress/更新日志折叠展示/挂载时恢复壳侧进行中状态/壳推送实时刷新——旧壳无通道空订阅不轮询：壳与前端同包分发不存在「新前端配旧壳」；检查按钮 checking/downloading/downloaded 态禁用）；runtime 页删除该卡挂载（守护进程/机器管理语义更纯）。**坑**：base-ui Button `render` 到 `<a>` 运行时显式挂 `role="button"` 覆盖隐式 link 语义，而 `jsx-a11y/no-redundant-roles` 又禁静态显式 `role="link"`——规则与运行时冲突，按全仓既有模式（invite-page）不加 role，测试按 href 断言；ui/button 层的语义修复（render a 时自动 role=link）留作组件库级裁决。
- test_evidence：frontend `tsc -b` 0 错 + desktop-preferences-card 9 例全绿（版本对照/推送进度+按钮禁用/downloaded 更新日志为新增例）；desktop `tsc --noEmit` + eslint + tsup 构建全绿。

## ADR-016: GitHub 证据回流统一落默认库，跨库迁移随「集成配置入工作区」一次性收口（2026-09-13）

- 背景（CAP-B-08 二期裁决项）：GitHub webhook 请求不带 `x-workspace-id` 头，ALS 为空，PrismaService 结构性回落 base 实例（默认库）；`IntegrationConfig` 仅有 `scope: global|project`，无 workspace 维度，按 repo→目标库解析的前提不存在。一期已按「同 github-sync 口径落默认库」实现并在 subscriber 头注释声明边界。
- 裁决：**二期起把「证据回流落默认库」从注释级边界升格为正式裁决**——RemotePullRequest / IntegrationConfig / Acceptance 族证据（含二期新增 PR 中间态 completionEvidence、pr_review 证据）统一落默认库；在此之前不新增按库分叉的临时方案（不做影子表、不做双写）；跨库迁移待「集成配置入工作区」（IntegrationConfig 扩 workspace 维度 + repo→workspace 解析 + 存量证据迁移脚本）立项后一次性完成。
- 影响口径：多库工作区的质量把关数据暂在默认库可见（与「全局单 GitHub 集成」现状一致）；前端证据展示不受影响（同一 API 面）。
- 关联：`apps/server/src/modules/acceptance/github-evidence.subscriber.ts` 头注释、`docs/02-架构设计/architecture/integration/集成接入规范-v0.md` E2（webhook→gateway 按 workspace 房间转发，待集成配置入工作区后一并实现）。

## ADR-017: G5 执行隔离采用 per-Execution git worktree + 成果经 integration 决策卡人工合入（2026-10-01）

- 背景：需求重审 G5 缺口（并行执行无隔离无合并）自 2026-09-17 裁决 C 挂账「另立设计切片」；上线计划定版 v0.7.11 设计+v0.7.12 实现。设计稿 `docs/design/设计-G5执行隔离与合入-2026-10-01.md`（v1.0.0，勘察 file:line 全复核）。
- 用户裁决（AskUserQuestion 2026-10-01）：①合入门形态=**决策卡人工确认**（执行成功≠自动进主工作区，弃自动合入路线）；②隔离不可用降级=**回落共享根+显眼标记**（非 git 项目照常派发，`metadata.isolation={mode:'shared-root',reason}`，执行面板琥珀徽标，弃 fail-closed）。
- 工程自决三项（设计稿 §四）：worktree 落点=`<项目根>/.apm/worktrees/<shortId>`+幂等补 `.gitignore`（同盘符、可见可清理）；冲突探测=`git merge-tree --write-tree` 无副作用预检（真 merge 失败会污染主工作区现场）；失败执行 worktree 保留 7 天 TTL 由 reconcile 巡检清理。
- 关键架构事实（使方案大幅简化）：CLI 协议 `workspaceRoot` 单字段承载工作目录语义（protocol.ts:81-102），daemon worker 透明消费——**协议零变更**，worktree 路径填进派发载荷即让进程内+daemon 两路同时生效；决策卡 applier 按 kind 事务化分发模式现成（proposal.service），扩 kind=`integration`+applier 分支即新卡种；`approvedFingerprint`（CAP-C-04）复用为「分支头指纹」防批准后现场变化。
- 加固项：`issue.service.ts` 绕过 `createExecutionRun` 的直创路径收口单活跃互斥（必做）；SQLite partial unique index 列选做。git 操作新建受控白名单式 `ExecutionWorktreeService`（独立 execFile 通道，不走 GitCommandService 用户输入黑名单；分支删除硬编码 `apm/exec/` 前缀校验）。
- 关联：非目标继续有效（PRD §15 不做多 agent 协同调度编排，本设计只补最小隔离与合入）；A-18「AI 建议→人确认→可展开细节」样板由 integration 决策卡兑现前端呈现。

## ADR-018: 移动端技术路线采用 Expo + React Native 独立 App，产品定位「伴随式掌上治理台」（2026-10-11）

- 背景：移动端建设定于 0.8.0 之后启动、与 PC 发版并行。前期须先定技术路线与产品定位（需求治理登记见能力清单 §4.8 新立 M 线 `CAP-M-01…M-10`）；移动端是双表面架构的第三种人类表面，需复用既有契约资产（`openapi.json` 生成类型 + `@apm/shared` 协议镜像）。
- 用户裁决（AskUserQuestion 四题，2026-10-11）：①技术路线 = **Expo + React Native**（独立 App，一码双端；同 TS 语言可消费生成契约类型，EAS 一并解决云构建/签名/内测分发/OTA）；②产品定位 = **伴随式掌上治理台**（只读 + 轻写；非目标 = 代码编辑、工作区管理、流程画布、深度富文本编辑，一律回桌面）；③平台 = **iOS + Android 双端**（手机竖屏为主，平板降级不专门适配）；④节奏 = **设计先行 + 并行铺路**（0.8.x 内出全套材料 + 技术选型 spike，实现自 0.9 起分批）。
- 排除项与理由（详见 `docs/design/mobile/ADR-M-001-移动端技术路线.md` §2）：原生双端（两套代码 + 零 TS 契约复用）、PWA（iOS 推送/后台受限，与「被告知」核心场景冲突）、RN CLI bare（放弃 EAS 工具链收益不明显）、Flutter（Dart 零复用全仓 TS 资产）、Taro/uni-app（生态目标不匹配）。

## ADR-021: 架构体检批一 T2 方案修正——workspace 越权不加守卫级归属查询（2026-10-25）

- 背景：2026-10-24 全仓架构体检（五路并行，只读）将「x-workspace-id 认证前裸接受、无 membership 授权」列为 P0 安全旁路，修复计划（批一 T2）原定在全局 JwtAuthGuard 尾部加「principal 的 User 行存在于目标工作区库」校验。
- 修正：实现前复核发现该旁路**在策略层已闭合**——`x-workspace-id` 中间件进 ALS 后，passport 策略 `validateJwtPayload` 与 PAT 校验（`AccessTokenService.validate`）都按 ALS 路由库查 `User`/`Session`/`AccessToken`，跨库主体的 session/token 行在目标库不存在，策略层即 401。原体检结论过强（未核对策略层的库路由）。守卫级再加一次归属查询属冗余防御，代价是每请求多一次 PK 查询（与批二启动提速方向相反）。
- 裁决：T2 收缩为「双守卫收编」——59 处控制器级 `@UseGuards(JwtAuthGuard)`（modules/auth 版，与 common 版实现已漂移：PAT/dev-mock 分支只在 common 版）全量摘除，认证单源 APP_GUARD；隔离机制注记在 `apps/server/src/common/guards/jwt-auth.guard.ts` 头部。WS 推送可见性（EventVisibilityService）另落 T1。
- 关联：CHANGELOG Unreleased「架构体检批一热修」行；`fix/security-data-integrity` 分支 e6319b6f。
