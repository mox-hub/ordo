## 1. 一句话共识（承 v1，不变）

> APM 的定位是**全托管平台**。文档不是"要同步的附件"，而是**平台运行本身依赖的知识层**。所有"双向绑定"问题都改写为"**分区单一真相源 + 对齐 + 冲突裁决**"，而非两份真相互写。

## 2. 三条铁律（承 v1，不变）

1. **分区单一真相源**：每份契约、甚至每一段，只有一个事实拥有者；`docs/` 与 DB 之间做"对齐"，不做无差别双向。
2. **可执行契约**：文档一旦被平台逻辑消费（验收、contract check、changelog、AI prompt），即升级为"配置/代码"，引入与代码同等的角色、生命周期与审批门禁。
3. **对齐以 git 事件为节拍，冲突一律升级人审、绝不静默覆盖**；实时 live-sync 排除。

## 3. 两条真相车道（承 v1）

| 车道 | 读者 | 代表文件 | 事实真相 | 对齐节拍 |
|------|------|----------|----------|----------|
| **A 仓库契约** | 仓库外 AI 与开发者 | AGENTS / CLAUDE / README / CHANGELOG | **git 工作树文件** | git 提交 / PR / 合入边界 diff 对齐 |
| **B 平台知识** | 平台内部人 + 平台自身 | PRD、架构、docs 知识库 | **DB** | 文件仅镜像/导入导出 |

## 4. 文档信息三层拆分（承 v1）

| 层 | 内容 | 存哪 | 绑定强度 |
|----|------|------|----------|
| **L1 正文** | Markdown 文本 | DB `Document.content` + 磁盘 body | 强绑定（git 事件对齐） |
| **L2 信封** | 标题/稳定 id/分类/标签/路径/状态/同步指纹 | **YAML frontmatter** | 强绑定 |
| **L3 派生索引与平台态** | 版本链/审批/章节锚点/任务链接/订阅/权限 | **只存 DB** | **永不进文件** |

- 同步被降维为「一条规范文本（frontmatter + body）」的纯文本 diff，无有损格式转换。
- 文件身份=路径，DB 文档身份=id 与关系；两者由稳定 id + 正文相等性松散耦合，不追求信息等价镜像。
- 乐观并发复用 `Issue.externalVersion / localUpdatedAt` 模式（schema 已验证存在，`schema.prisma:600`）。

## 5. 【v2 修订】格式选型与 round-trip 区间引擎

### 5.1 方言固定（承 v1）

CommonMark + GFM 子集 + YAML frontmatter + **一种内部链接写法（v2 定为 `apm://`，见 §13）**。DB 侧 `Document.content` 保持 UTF-8 Markdown TEXT 列，列是真相；禁块级富文本 AST 作为正文真相（AST 仅可作编辑器临时模型，见 §14）。

### 5.2 引擎方案【v2 核心修订】

**现状勘误**：v1 称 `ImportExportService.generateMarkdown()`「已产 frontmatter」——实际为裸字符串拼接（`import-export.service.ts:144`，`title: ${title}` 直接插值，标题含冒号/引号即产生非法 YAML）；`parseMarkdown()` 只提取标题/摘要/锚点。**v1 §5 要求的「未知内容原样保留」在现有代码中零承接，引擎按不存在对待。**

**v2 方案：不做全文件 parse→serialize，做「区间引擎」**：

- 结构化处理范围仅限两块：**frontmatter**（gray-matter 或等价 YAML parser，须做转义）与 **`BEGIN/END apm:managed` 托管区间**（区间定位 + 原文替换）。
- **自由区字节 verbatim**——不进 parser、不参与任何序列化往返。
- 起步选型 gray-matter + 区间正则即可，**不引入完整 mdast**；全量 AST 仅在编辑器层出现（§14）。

**验收标准（1a 出口）**：round-trip 幂等测试集——对仓库现有 `AGENTS.md` + 若干含表格/HTML 混排的 docs 文档，`parse→serialize` 逐字节相等；managed 区间替换后自由区字节不变。**该测试集同时作为前端编辑器选型门槛（§14），一份投入两处收益。**

## 6. 【v2 修订】契约文件绑定的落地形态

### 6.1 托管区块 + 自由区（承 v1）

frontmatter（`apm_project_id / sync_mode / tech_stack…`）+ `<!-- BEGIN/END apm:managed:{id} -->` 区间 + 自由区；系统只认识前两者，自由区 round-trip 保留。三态 `sync_mode`（managed / synced / detached）不变；`synced` 态的格式化按 v2 总览 #5 收缩为「只校验 frontmatter + 托管区间完整性，自由区永不触碰」。

### 6.2 ContractFileBinding 实体（承 v1）

字段集不变（fileType / filePath / syncMode / managedBlocks / truthOwner / baseline / conflictState / lastWriter / hooks）。

### 6.3 【v2 修订】hook 事件基建口径

- v1 表述「复用 Plugin 系统 + 事件总线」**不准**：`plugin.service.ts` 仅安装/权限管理，无 hook 执行引擎；平台真实事件基础设施是 **`core/message-bus`**。
- **v2 口径**：hooks V1 = message-bus 的 server 内订阅者（如 `release.created` → 再生 CHANGELOG；`project.updated` → 刷 frontmatter；`execution.terminal` → 托管区 diff 检查）。Plugin 化（第三方插件订阅平台事件）留远期。
- git 侧护栏仍用 `git config core.hooksPath` → 仓库内 `.apm/githooks/`（clone 不丢），承 v1。

### 6.4 【v2 新增】对齐节拍的执行者

v1 定了节拍（git 事件）但没定执行者；server 不直连磁盘（fs 代理归 Runtime 节点），故：

- **主路径**：execution 状态机终态钩子（经 message-bus）触发托管区 diff 检查——agent 执行收口必然经过 execution，节拍天然存在。
- **兜底**：文档/项目页手动「同步检查」按钮。
- **排除**：fs watch、实时 live-sync（承 v1）。

### 6.5 【v2 新增】冲突升级容器

- 冲突定义为 **ApprovalRequest 的一个 subtype**，不复用容器则"升级人审"无 UI 承载。
- 证据视图：两侧 diff 并排（文件侧 vs DB 侧）。
- 裁决动作有限集：**采纳文件侧 / 采纳 DB 侧 / 人工编辑合并 / 转 detached**。裁决后更新 `baseline` 与 `conflictState`。

### 6.6 其他（承 v1）

根目录多口径（Agent CLI 实际启动的 workspaceRoot 为准；fs 操作走拥有该工作区的 Runtime 节点）；monorepo 时 AI 指令文件降级到子目录作用域。

【v2 补充】Windows / 中文路径坑：git `core.quotepath`、跨 OS 路径规范化——**docmap.json 的路径口径须在写第一行代码前定**（建议统一 POSIX 分隔符 + NFC 规范化）。

## 8. DocRegistry（承 v1，补 apm:// 方言衔接）

三种消费面（人文档 UI / AI subset+digest / 平台自用）都经注册表取数。注册表是**派生索引，永远可重建**；统一寻址 `apm://{projectCode}/doc/{shortId}`（shortId 复用 `GlobalSequence`，已验证为 per-workspace `key→lastSeq` 计数器，配 projectCode 命名空间够用）。

收敛现有 `ProjectDocLink.aiIndexed` 与 `docs-sync-manifest.json` 职责进注册表（承 v1）。

## 9. AI 两条分发通道（承 v1）

通道 A（仓库内文件，agent 自取）/ 通道 B（dispatch 时 ContextPack 注入），同源派生。接入点：`ContextService.buildContextPack()` 的 `collectSources()` 加 docs provider。

【v2 勘误】`collectSources()` 现为空壳（`context.service.ts:290`，`documents: [] as any[]`），`buildContextPack` 整体雏形——**二期前置切片：先补 context.service 的文档取数能力，再接 digest**。

## 10. 【v2 修订】文档角色 × 生命周期

两条正交轴不变（`Document.category` 内容域 × `docRole` 治理角色）；生命周期共用 `draft→reviewing→published→rejected`（`Document.status` 枚举已验证一致，零改造成本）；`spec` 双版本 + provenance 单列承 v1。

**v2 裁决——docRole 分批启用（跟消费面走，无消费面不定义）**：

| 批次 | docRole | 依赖 |
|------|---------|------|
| 一期 | `charter`、`release-log` | 1a 契约闭环 / 1b Release |
| 二期开头 | `spec`（approved 门禁 + 双版本） | DocRegistry |
| 三期 | `design`、`decision`、`reference` | 活体绑定 + 检索消费面 |

## 11. 【v2 修订】subset / digest

三级触发（T0 物化提升 / T1 惰性 / T2 checksum 失效）、digestPolicy、digest 永不装正文、`collectSources` 接入、老库回填一次性 job——均承 v1。

**v2 裁决：V1 只做 leaf digest + 顶层 catalog**（手工指针 + 机器生成 docmap）。leaf→aggregate 归并算法依赖文件夹/角色分组语义，**待三期活体绑定稳定后再定**，现在定是空中楼阁。

## 12. 【v2 修订】资产盘点核对结论（2026-09-08 实测）

**属实可复用**：Document 族底座（`schema.prisma:1524-1660`，sections/versions/approvals 含 version 字段/taskLinks/references）、`Document.status` 枚举即生命周期、`Issue.externalVersion/localUpdatedAt`、`GlobalSequence`（:2077）、`docs-git.service.ts`、`docs-sync-manifest.json`、`shared/route-preview/`（registry 8 类实体解析 + PreviewCard 分发）、根 AGENTS.md frontmatter 约定、`core/message-bus`。

**勘误三处**：
1. round-trip 引擎不存在（详见 §5.2）；
2. `collectSources` 空壳（详见 §9）；
3. 事件基建是 `core/message-bus` 而非 Plugin 系统（详见 §6.3）。

**schema 增量清单**：`ContractFileBinding`、`Release`、Document 增 `docRole/provenance/shortId/sourceChecksum/digestPolicy`、`DocumentFolder` 增 `slug`。

## 13. 【v2 新增】内嵌链接方言：`apm://` 统一实体引用

### 13.1 存储格式

```markdown
见 [验收门禁设计](apm://apm/doc/A17)，阻塞 [apm://apm/issue/A24]
```

**标准 CommonMark 链接语法 + `apm://{projectCode}/{kind}/{shortId}` href**。不选 wikilink（`[[doc:A17]]`）的理由：标准链接在 AI 读写、round-trip 引擎、逐字节 diff、现有 react-markdown 管线四处零成本；wikilink 四处各加一层扩展。外部 AI 在磁盘读到 `apm://` 凭 catalog 即可理解，无需专用工具——直接服务车道 A。

### 13.2 四层落地

| 层 | 实现 |
|----|------|
| 存储 | 正文 md 文本，逐字节稳定；链接指 shortId 不指路径（改名不断链） |
| 解析 | `apm://` → 既有路由（`/app/documents/:id` 等）展开函数放 **@apm/shared**（协议镜像层）；ContextPack 通道 B 展开为内联 digest，通道 A 展开为相对路径 |
| 渲染 | react-markdown `a` component 拦截 `apm://` → 内联 chip（图标+标题+状态色点）→ hover 走现成 RoutePreviewCard；预览数据 TanStack Query 按 id 批量取 |
| 编辑 | 随编辑器形态定（§14）：`@` 唤起候选选择器，chip 为不可拆分 inline 节点 |

`route-preview-registry` 从「解析路径」升级为「解析引用」：路由字符串与 `apm://` 两条入口汇入同一 `RoutePreviewMatch`。

### 13.3 @提及的重构归宿

现有 `MentionTextarea`（team-member 模块，textarea + 自制下拉）根本局限是 textarea 渲染不了卡片，修补无出路。**重构目标形态 = 统一实体引用子系统的一个实例**：同一候选选择器（人/文档/工单/审批同源）、同一 chip 渲染、同一 preview card；@人 = `apm://` 引用中 kind=member 的语法糖。排期随二期（依赖解析层 + chip 渲染就位）。

## 14. 【v2 新增】编辑器统一为所见即所得

### 14.1 现状澄清

**现在没有 WYSIWYG**：`mdx-editor.tsx` = CodeMirror 6 源码模式（语法高亮 markdown 编辑器），`mdx-renderer.tsx` = react-markdown 只读渲染，另有预览对话框——三种呈现实为源码编辑 / 渲染视图 / 预览三处并存。统一 WYSIWYG 是**引入新编辑器**的选型决策，不是收敛决策。

### 14.2 铁约束（与 §5.2 同源）

编辑器 serialize 出的 md 必须过保真度关：未知语法/HTML 块/表格原样保留、frontmatter 不动、managed 区间不碰。AST 仅作编辑器临时模型（parse→edit→serialize），md 永远是持久真相（承 v1 §5）。

### 14.3 两条路线

| 路线 | 代表 | 优势 | 风险 |
|------|------|------|------|
| **A 真 WYSIWYG** | Milkdown（remark 底座，与 §5.2 引擎同源则 parser 共享）/ Tiptap（HTML-first，md 序列化有损风险） | 体验上限高（块级拖拽、表格所见即编辑） | serialize 保真，ProseMirror 系著名雷区 |
| **B live-preview** | CodeMirror 6 装饰渲染（Obsidian editing view 模式） | 缓冲区始终是 md 纯文本，**round-trip 风险为零**，managed 区间天然安全，复用现有底座 | 重交互上限低（表格、块拖拽弱） |

**决策机制**：不纸上拍板——两条路线各做 spike，跑同一套 **§5.2 保真度测试集**（现有全部文档 round-trip 逐字节 + apm:// chip 内嵌渲染 + managed 区间安全），谁过关用谁。**spike 与 1a 并行，互不阻塞**。倾向备注：本项目核心诉求（md 持久真相 / AI 读写 markdown / git diff 可 review）与路线 B 风险曲线更匹配，路线 A 赢在体验上限。

### 14.4 渲染收敛

view/edit/preview-dialog 三处收敛为一个 `<DocumentSurface>`（只读/编辑两态）；源码视图保留为编辑器切换态（写表格/HTML 时仍需要）；`document-preview-dialog` 一并收编。
