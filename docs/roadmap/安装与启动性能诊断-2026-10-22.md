# 安装与启动性能诊断（2026-10-22）

> 用户反馈：新测试包（Ordo_0.8.0-beta_x64-setup.exe，228MB）「本地安装速度过慢、软件启动速度也慢」。本文档 = 实测数据 + 根因 + 已落地优化 + 分优先级建议。修复批 `fix/desktop-window-restore-perf`。

## 一、实测数据（本机打包产物，2026-10-22）

### 随包资源构成（build/desktop-pack 实测）

| 目录 | 文件数 | 体积 | 内容 |
|------|--------|------|------|
| server | **17,365** | 259MB | NestJS dist + npm 平铺 node_modules（已剥 .d.ts/.map/prisma CLI） |
| git | 347 | 112MB | MinGit 2.47.1（CAP-A-30 随包） |
| bin | 1,729 | 105MB | node.exe（~110MB 单文件）+ npm 运行时树 |
| cli | 1,664 | 18MB | ordo-runtime 守护进程 + shared |
| frontend | 151 | 14MB | 前端产物（**index chunk 6.7MB**） |
| 合计 | **≈21,200** | ≈508MB | 安装包 LZMA 压缩后 228MB |

### 启动链路耗时结构

| 环节 | 耗时 | 依据 |
|------|------|------|
| Electron 主进程初始化 + boot 屏 | <1s | 代码路径均为同步毫秒级 |
| server 冷启动（拉起→健康通过） | **8s~31s** | `backend.ts` 在案注释（杀毒扫描/机器负载抖动）；健康轮询 60s/500ms |
| ordo-runtime 守护进程拉起 | 1s~3s | node 冷启 + shared 加载；**修复前串行阻塞前端加载** |
| 前端加载 + 解析执行 | 1s~2s | 6.7MB 单 chunk 解析/编译为主（本机回环传输可忽略） |
| restoreDesktopSession（钉底+镜像恢复） | <0.3s（后端已就绪时） | 20×300ms 重试仅在服务未就绪时发生 |

## 二、根因结论

### 安装慢（主因排序）

1. **文件数 × Defender 实时扫描**：NSIS 解包 ~21,200 个文件，Windows Defender 对每个写入文件实时扫描——这是 Windows 上大量小文件解包慢的支配项，与 server node_modules 占 82% 文件数直接相关。
2. **LZMA 解压 CPU**：228MB 高压缩比包解压到 508MB 本身有秒级~十秒级 CPU 成本（机器相关）。
3. 逐文件代码签名（构建期「signing with signtool」日志数百次）只影响**打包**耗时，不影响用户安装。

### 启动慢（主因排序）

1. **server 冷启动 8s~31s**：Node 加载 NestJS 全模块图 + Defender 对 server 目录 259MB/17k 文件的扫描税（首启最重，后续有缓存会变快）。
2. **守护进程串行等待**（已修复）：`await autoStartRuntimeDaemon()` 在前端加载之前白罚 1~3s。
3. **前端 6.7MB 单 chunk**：router.tsx 对 ~40 个页面模块静态 import，全部打进 index chunk，每次启动都要解析执行。

## 三、已落地（本批）

| 优化 | 效果 | 位置 |
|------|------|------|
| 守护进程后台拉起，不再阻塞前端加载 | 每次启动省 1~3s；AI 执行面本就非首屏依赖，失败可设置页手动重试 | `main.ts` bootstrapServer |

## 四、建议清单（按性价比排序，未落地项待裁决）

| # | 建议 | 预期收益 | 代价/风险 | 建议 |
|---|------|---------|----------|------|
| 1 | **Defender 排除指引**：首启检测 boot 耗时超阈值时，在完成页/设置页提示把安装目录与 `~/.ordo` 加入 Defender 排除（附一键打开排除设置） | server 冷启动 8~31s 大幅收敛（尤其首启）；需用户操作 | 无代码风险 | **批内推荐，成本低** |
| 2 | **router 页面级 lazy 化**：比照 router 中既有 `lazy()` 模式把重页面（analytics/documents/executions/office 等）转按需 chunk | index chunk 6.7MB → 预计 2~3MB，启动解析省 0.5~1s，首屏 TTI 提前 | 机械改量大（~40 处 import），需回归 e2e | 独立小批 |
| 3 | **server 启动日志打点**：Nest bootstrap 各阶段（模块注册/Prisma 连接/迁移/静态托管）耗时日志，把「8~31s」拆解到环节 | 为后续优化提供数据；零风险 | 无 | 批内推荐 |
| 4 | 测试包用 `compression: "store"`（electron-builder）换安装速度 | 解压 CPU 归零，安装提速；包 228MB→~500MB（下载/分发体积变大） | 分发体积翻倍，正式包不宜 | 仅内测渠道可选 |
| 5 | server 模块惰性化（Nest lazy modules / Ragged routes） | 削减冷启动模块图加载 | 架构级改造，触及 43 模块 | 远期，不建议现在动 |
| 6 | asar 重新启用 | 仅覆盖 app 代码（几百文件），**不覆盖** extraResources（server/git/npm 占 96% 文件数） | 收益极小；且当初因 Defender 构建锁禁用 | 不做 |

## 五、给测试同学的立即可行建议（零代码）

- 首次安装前把 `%LOCALAPPDATA%\Programs\Ordo`（安装目录）与 `C:\Users\<user>\.ordo`（数据目录）加入 Defender 排除项，安装与首启速度会有量级改善；
- 观察二次启动（Defender 缓存已热）耗时作为基线，与首启分开反馈。
