# 组件库搭建调研（2026-10-27）

> 触发：自定义组件与旧组件持续膨胀后，design-system 页面无力承担展示；与标准 UI 库文档差距拉大。调研两个对标站点用什么搭建，并裁决是否自建组件库长期维护、供多项目运用。

## 一、两个对标站点拆解

### coss.com/ui（Coss UI）——与本仓技术栈几乎同源

- **维护方**：Cal.com, Inc. 团队；coss.com = Commercial Open Source Software 生态。GitHub `cosscom/ui` 约 10.8k stars。
- **站点搭建**：**Next.js + Fumadocs**（README 致谢明确写明 Fumadocs 驱动组件文档）。
- **仓库结构**：Turborepo monorepo——`apps/www`（主站）+ `apps/ui`（组件库文档站，独立端口 4000）+ `apps/origin`（被收购的 Origin UI 旧快照）+ `packages/ui`（共享组件包）+ `packages/typescript-config`。Bun 包管理 + Biome lint + husky。
- **组件技术**：**Base UI 原语 + Tailwind**（强调原生 Base UI，非 Radix 移植）——与 Ordo 前端选型完全同款。
- **分发**：shadcn 式 **copy-paste（registry + CLI 安装源码）**，不装 npm 包；提供 Copy Markdown / llms.txt / Skills 页，AI-first 定位。
- **架构分层**：Primitives（Base UI 无样式原语）→ Particles（组装成品模式）→ Atoms（连接外部 API 的智能组件）。

### affectui.com——单人作者的 Agent-ready 组件库

- 2026-10-26 已有深度调研（见同目录《affectui-调研报告-2026-10-26.md》《affectui-逆推与组件库缺口审视-2026-10-26.md》），本次补充站点技术事实：
- **站点搭建**：**Vite SPA 自建**（产物为 `/assets/index-*.js` 单页壳，无 Next/Nextra/Astro 特征，无文档框架）。
- **组件技术**：React 19 单 TSX 文件、零依赖、无 Tailwind、container queries。
- **分发**：shadcn registry + MCP server + llms.txt；MIT 免费层 40 件 + Pro 84 件 $199 买断。

## 二、成熟组件库的搭建范式（共性规律）

1. **源码交付而非 npm 依赖**（shadcn 范式已成主流）：registry.json 描述 + CLI 拷贝进用户项目，用户拥有源码。affectui / coss ui / shadcn / kibo-ui / origin-ui 全部如此。适合 AI 时代（agent 读写源码比装依赖更顺）。
2. **可访问性原语不自研**：要么用 headless 库（coss ui 用 Base UI），要么像 affectui 零依赖手写但只此一家。自己从零写 dialog/focus 管理 = 高危。
3. **文档站 = 独立 app**：Next.js 生态当前事实标准是 **Fumadocs**（coss ui 在用；shadcn 系文档站基本都是 Next.js 应用，Fumadocs/Nextra/自建皆有）；轻量派自建 Vite SPA（affectui）。无一例用主应用某个页面充当文档站。
4. **monorepo 结构**：`apps/docs`（或 apps/ui）+ `packages/ui`，组件源码在包里、文档 app 只负责渲染 demo。
5. **AI 友好界面成标配**：llms.txt / Copy Markdown / MCP / Skills 页。

## 三、Ordo 组件资产对账（2026-10-27 实测）

| 资产 | 规模 | 状态 |
|---|---|---|
| ui 层原子 | 64 件 | 已物理收编，画廊门禁覆盖 |
| semantic 层 | 54 件 | 业务语义层，含 B 档新五件（approval-card/exec-tree 等） |
| raw 层 | 3 件 | raw-button / raw-input / raw-select |
| registry | 351 条 | 门禁画廊 109/109=100% 机器强制 |
| 文档生成 | `gen-components-md.mjs` → `COMPONENTS.md` | 已有，= llms.txt 胚芽 |
| 护栏脚本 | check-palette / check-tailwind-arbitrary 等 | 已有 |
| **design-system 页面** | **design-system-page.tsx 单文件 7505 行** | **痛点本体：画廊模式，无 per-component 页 / Props API 表 / 代码复制 / playground** |

**结论：Ordo 不是「没有组件库」，而是已经有半个库（资产+护栏+文档生成器齐备），只是形态长错了地方——它长成了主应用里的一个巨型单页，而不是一个包 + 一个文档站。**

## 四、要不要自建组件库：要，但分三步，不要一步到「对外开源库」

### 决策依据

- 产品线战略 = **一套代码三版本**（monorepo 内多 app）→ 「多项目复用」的正确答案是 **monorepo 内 workspace 包**（源码共享、零版本协调成本），npm 发版反而是负担。
- `apps/mobile`（Expo/RN）已存在 → web 组件本体**不可**复用到 RN；可共享的边界是 tokens/主题/headless 逻辑，要诚实标注。
- 展示痛点 = 形态问题（页面模式），不是资产问题；先修形态，不必推倒重来。

### 三步走

**第一步（解燃眉，小批次）：design-system 页面路由化。**
7505 行单页拆为「分类索引页 + 每组件一页」路由（复用现有 registry.ts 数据源），每页补：变体演示 + Props 表（从 TS 类型自动生成）+ 代码复制。纯展示层改造，不动组件资产。参照物即 coss ui 的 per-component 页式样。

**第二步（服务三产品线，一个正式批次）：库化——`packages/ordo-ui`。**
把 raw 3 件 + ui 64 件 + 基础 hooks + Tailwind 4 主题（@theme CSS 变量）抽成 monorepo workspace 包，前端改走 workspace 依赖。**semantic 层（54 件）不抽**——它是 Ordo 业务语言（approval-card、exec-tree），抽出去会把业务概念泄漏成「库 API」，违反其存在本义。registry/画廊门禁脚本随包迁移，护栏不许断电。主要技术工作：Tailwind 4 跨包配置（@theme/@source）、约 119 处 import 机械替换、turbo 任务接线。基建（Turbo/catalog/husky/门禁）全部现成。
> 建议走 requirement-intake 正式立项；批内含一次 type-check/lint/test/gallery 门禁全绿收口。

**第三步（触发条件制，现在不做）：registry 化 + llms.txt。**
触发条件满足任一再做：① 组件要对生态第三方分发（含私有 shadcn registry 形态，不必开源）；② Ordo 自己的 AI agent 需要以 registry 协议读写组件。注意与「一套代码三版本」的张力：copy-paste 分发天然制造分叉，monorepo 源码共享不分叉——三产品线场景下 workspace 包才是对的，registry 只是「对外出口」选项。

### 明确不推荐

- **Storybook**：重、Tailwind 4 + base-ui 集成要折腾；且 Ordo 的 registry+画廊+覆盖率门禁体系（109/109 机器强制）已是 Storybook 在我们需求上的超集，引入是倒退。
- **现在就 npm 发版/公开库**：React 19 + base-ui + Tailwind 4 全是新栈，对外发布等于承诺兼容矩阵；等第二个真实消费者（三产品线的二号 app）出现再议。
- **semantic 层抽包**：见上。
