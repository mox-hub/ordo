## 一、问题一方案：内置 AI 配置硬引导

### 1.1 口径定义：AI 就绪三级（全方案的状态地基）

| 级别 | 判定（前端可推导） | 用户体感 |
|------|--------------------|----------|
| **L3 ready（就绪）** | ≥1 厂家 `enabled && hasApiKey`，且 `ai.defaultModel` 已设、指向厂家仍可用、且该厂家 `status !== 'error'` | 一切 AI 功能按预期工作 |
| **L2 degraded（口径缺失）** | 有可用厂家，但内置模型未设置 / 指向厂家已失效（禁用或清 key） | AI 功能静默回落首个厂家——能用，但不符合「内置模型」产品口径 |
| **L1 unavailable（完全不可用）** | 零个 `enabled && hasApiKey` 厂家 | AI 助理对话、静默生成、需求评估、验收起草**全部 400** |

附加态：`unverified`（内置模型指向厂家最近一次实测 `status==='error'`）归入 L2 提醒带。另有两类**不渲染**态：`loading`（查询中）与 `unknown`（查询失败/断线——断线时状态不可信，宁可沉默也不误报「未配置」，连接问题由 ConnectionBanner 负责）。

### 1.2 三层引导架构（引导内硬确认 + 引导外持续提醒 + 配置面唯一真相）

### 1.3 「配置内置 AI 助手」的口径澄清（写给方案评审）

系统助理**小周**固定存在且不可删停（`member.service.ts` 系统助理守卫），用户语境里的「配置内置 AI 助手」实为两件事：①**配置内置模型**（厂家 Key + 默认模型）——小周与全部静默链的供血；②（可选）**创建专属 AI 员工**——即问题二。引导 configure-ai 步已把①②串成一条链（测试通过→落库→设默认模型→建默认员工），问题一不需要为「助手」新增配置步，只需要把**没走完这条链的人找回来**——即三层架构的提醒面。

### 1.5 六问（问题一）

①**用户任务**：装好 Ordo 后不被「AI 功能全部报错」卡住，十分钟内让内置 AI 真实可用；②**AI 职责**：无——纯确定性状态推导与引导链（诚实化原则延续，A-18 引导切片系口径）；③**可信依据**：AIProviderConfig enabled+hasApiKey（适配器装载条件）+ AppConfig ai.defaultModel + provider.status 实测态，全部来自运行时真相；④**人类控制**：跳过永远可行（AlertDialog 只说明后果不剥夺选择）；配置哪家/哪个模型全用户决定；⑤**失败与降级**：查询失败/断线横幅沉默防误报；引导跳过后仍有多层提醒可找回；⑥**跨模块闭环**：输入=ai-hub 配置面产出，输出=去配置深链，配置完成横幅即时消失（同 query key 缓存共享 + 失效链）。

## 二、问题二设计：「AI 创建 AI 同事」专属页面

### 2.1 定位与价值

- CAP-A-18 主卡「统一创建面板双界面：手动 × AI 代理平行」在 **AI 员工实体上的完整实例**——现状 AI 员工只能走 member-create-dialog 十余字段手动填，而这恰恰是最不该手动的实体：既然内置 AI 已接入，就该让 AI 理解「我要一个什么样的同事」并代写全部档案，人确认后落库。
- 交互范式 = A-18 重审注记「AI 建议 → 人确认 → 可展开细节」，与 prompt-draft / acceptance-draft / release-notes-draft 同语法（「代写→人确认→把关」主轴第四实例）。
- **红线**：AI 只代写草稿，落库必须走人确认后的 `POST /members`（`aiModelConfigId` 硬校验不动）——与 create-draft 场景「草稿卡人确认后复用手动提交流」既有范式一致。

### 2.2 交互设计：三段式一页流（专属页面，非弹窗）

用户点名「一整套专属页面」——裁决为**独立页面**（非 Dialog）：创建 AI 同事是一次有仪式感的「入职」流程，且确认段需要展示 AI 依据与逐字段编辑，弹窗装不下；页面可深链、可从空态/引导/命令面板多入口到达。

路由：`/app/members/create/ai`（静态段，路由优先级天然高于 `members/:memberId`，在 router 的 members children 中注册）。

```
┌────────────────────────────────────────────────────────────────┐
│ SubPageToolbar（← 返回成员页 / 面包屑 成员 / 创建 AI 同事）        │
├────────────────────────────────────────────────────────────────┤
│ [段一 · 描述]  「你想要一位什么样的 AI 同事？」                     │
│  ┌──────────────────────────────────────────────────────────┐  │
│  │ AutoSizeTextarea：一句话描述（占位示例：「资深代码评审工程师，  │  │
│  │  严格但给建设性意见，用 GLM」）                    [AI 生成▶] │  │
│  └──────────────────────────────────────────────────────────┘  │
│  可选槽位（折叠）：职责方向（开发/评审/测试/项目管理，ChipSelect）   │
│                  绑定项目（可选，影响执行角色与项目绑定建议）        │
├────────────────────────────────────────────────────────────────┤
│ [段二 · 生成]  表盘式等待态（复用 Spinner + 阶段文案轮播：          │
│  「理解描述…→ 对照可用模型…→ 撰写个人提示词…」）                    │
│  失败态：结构化报错 + [重试] [手动创建（member-create-dialog）]     │
├────────────────────────────────────────────────────────────────┤
│ [段三 · 确认]  草稿分卡（每卡可展开编辑，「AI 依据」行灰字展示）：    │
│  ┌ 身份卡 ── displayName / handle / title / 头像建议色 ────────┐ │
│  ├ 模型卡 ── 建议厂家+模型（下拉可改，AI 依据：为何选它）─────────┤ │
│  ├ 提示词卡 ── personalPrompt（PromptEditor 只读预览+展开编辑，   │ │
│  │            AI 依据：提示词设计思路摘要）──────────────────── │ │
│  └ 执行卡 ── defaultCliProviderId / defaultExecutionRole /      │ │
│              thinkingLevel / tags ────────────────────────────  │
│  底栏：[重新生成（可附反馈）] [手动填写] [确认创建（主按钮）]        │
│  成功 → toast + 跳转成员详情页（/app/members/:id）                │
└────────────────────────────────────────────────────────────────┘
```

### 2.3 后端设计：SILENT_SCENARIOS 新场景 `member-profile-draft`（零新端点）

- **协议**：复用 `POST /ai/assistant/silent`，body `{ scenario: 'member-profile-draft', projectId?, context: { brief: string, focus?: string, feedback?: string } }`，响应 `{ scenario, data, usage? }`——与 release-notes-draft 等场景同构，遵守「不再各起端点」既定约定。
- **prepareContext（grounding，防杜撰）**：查 ① `AIModelConfig`（enabled，供模型卡候选）② `CliProviderConfig`（enabled，供执行卡候选）③ `ProjectRoleDefinition`（globalRoles，供执行角色候选）④ 既有 AI 员工样例 ≤3 条（displayName/title/personalPrompt 截断，供风格参照）——指令要求：所有建议字段只能从候选清单中选，选不出置 null 并在 rationale 里说明缺口。
- **输出 JSON schema**（instructions 约定 + `extractJsonObject` 容错）：

```json
{
  "displayName": "string",
  "handle": "kebab-case",
  "title": "string",
  "description": "string",
  "personalPrompt": "string（职责/风格/边界三段式，≤800 字）",
  "thinkingLevel": "minimal|low|medium|high|max",
  "defaultCliProviderId": "候选内 id 或 null",
  "defaultExecutionRole": "候选内 role 或 null",
  "suggestedProvider": "候选内 provider 或 null",
  "suggestedModel": "该 provider 下 enabled 模型或 null",
  "tags": ["string"],
  "rationale": { "model": "…", "role": "…", "prompt": "…" }
}
```

- **服务端后校验（白名单收口）**：`suggestedProvider/suggestedModel/defaultCliProviderId/defaultExecutionRole` 不在 prepareContext 候选清单内 → 置 null（不信任模型自由文本）；`thinkingLevel` 枚举外回落 `medium`；`handle` 做格式与保留字（`xiaozhou`/`ai-assistant`）规避。
- **记账**：AIUsageLog 由 `AssistantSilentService.run` 统一落（token + 估价），零额外工作。

### 2.5 六问（问题二）

①**用户任务**：拥有一个能干活的 AI 同事，而不是填一张十几个字段的表；②**AI 职责**：理解自然语言描述 → 代写全部档案字段 → 给出每个建议的依据——这是「AI 同事是手段」的直接兑现，AI 不可替代；③**可信依据**：prepareContext 注入的模型/CLI/角色候选清单（全部来自运行时库），建议只能出自候选，rationale 展示依据；④**人类控制**：逐字段可编辑、逐建议可展开看依据、确认创建是显式人令，落库走既有 POST /members 校验链——人真正过目而非机械确认；⑤**失败与降级**：见 2.4 降级链；⑥**跨模块闭环**：输入=用户 brief + 配置面候选；输出=Member 记录（后续被派发链/信任体系/用量归因消费）；创建后跳成员详情（可在详情页继续补工具授权/技能）。

### 2.6 测试义务与分期

- **批 1（server）**：silent 场景 spec——场景注册/prepareContext grounding 注入/输出字段白名单后校验（越界置 null）/thinkingLevel 回落/无适配器 400/AIUsageLog 落账。

### 3.2 形态裁决

- **顶部横幅（z-banner）而非悬浮球**：宪法 §8.4 该档用途明写「全局横幅（连接状态、离线提示）」；底部已被 BottomDock + AssistantFab 占用；ConnectionBanner 同款挂点（shell-layout 内 ConnectionBanner 旁），断线时横幅让位（订阅同一组连接事件，offline 不渲染——连接横幅优先 + 防误报）。
